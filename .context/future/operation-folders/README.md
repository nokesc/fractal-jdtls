# Operation folders: parked proposals (FUTURE, NOT PART OF THE DESIGN)

Parked by the governor on 2026-11-08 at Chris's request, during T002. **None of this is the design or planned work.** The implemented design is §11 "Operation folders" in [design.md](../../design.md). These are kept in case real failures later show a need for hardening.

From smallest to largest:

- [A-minimal-records-and-recovery-d1ba996.md](A-minimal-records-and-recovery-d1ba996.md): records plus `intent.json`, one `writeSetDigest`, an inline diff limit, an accepted-failures table, and Fractal Harness's recovery duties. Superseded for the first implementation by an even smaller cut, v5: the design in §11 now (ID generated by the endpoint, no `intent.json`, no caller UUID).
- [B-recompute-atomic-writes-journal-v3.md](B-recompute-atomic-writes-journal-v3.md): atomic per-file writes, a journal and backups in `-data`, startup recovery, an in-lock fresh check, a model-generation counter.
- [C-saved-plans-and-journal-d8f7e70.md](C-saved-plans-and-journal-d8f7e70.md): saved, digest-bound plans applied without recomputing, input fingerprints, outcome records, plus B's journal.

Chris rejected B and C as over-built: "We're building an elaborate crash-recovery and transaction system for something that should be an exceptional failure." His operating model: JDT LS provides semantic code operations; Fractal Harness manages worktrees and recovery; agents handle ordinary engineering failures; Git is the recovery mechanism; operational simplicity over transactional guarantees.

Also parked from T002.10: an Eclipse resource filter on the root project's `temp` folder (in its `.project`), which T002.10's first commit, 04766b0, built and its follow-up removed; it saves one full fixed point after each refactoring.

`reviews/` has Codex's five design reviews and their prompts (1–2 on C, 3–4 on B, 5 on the v4 proposal that became A).
