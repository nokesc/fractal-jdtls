# Proposal: operation folders, simplified (replaces the saved-plan design in commit d8f7e70)

Status: a proposal for Chris, not yet in design.md. Nothing is implemented. Revised after Codex's round-1 and round-2 reviews (design-review3.md S1–S5, design-review4.md: S3, S5, T1, T2).

## Why simplify

The design in `.context/design.md` §11 "Operation folders" (commit d8f7e70) grew a plan store, plan and diff digests, an inputs fingerprint, plan lifetimes, outcome records that outlive restarts, caps, and about eight new error codes. Most of that exists for one feature: applying a dry run's saved plan without computing it again. Its benefits are small: it saves one recomputation (0.7–1.7 s for a first rename, milliseconds after), and it guarantees that what's written is what was reviewed. Chris prefers stability over speed, and the worktree is a Git worktree in which agents (and Fractal Harness) already commit mid-task, so Git already provides history and undo.

## The proposal

1. **The operation folder stays, as a publication only.** Every refactoring request carries `operation` (a caller-chosen canonical lowercase UUID). The endpoint creates `<worktree>/temp/fractal-jdtls/<operation>/` exclusively (an existing folder is `operation-exists`, whichever process made it), with each path component opened without following links and files created relative to it (`operation-folder-unsafe` otherwise). It holds `request.json`, `diff.patch` (the full unified diff), and `response.json`; recovery data lives only in `-data` (point 4). The endpoint never reads the folder back to decide anything. `temp/fractal-jdtls/` is reserved: left out of the file record, refreshes, sync checks, resource-change handling and import discovery. The answer carries `operation`, `operationFolder`, `writeSetDigest` and `diffDigest` (point 2), and the diff inline up to a limit, with `diffTruncated`.

2. **Recompute and compare, no saved plans** (round 1, S1). A dry run returns two digests:
   - `writeSetDigest`, a SHA-256 over a versioned, unambiguous canonical form of the exact write set: worktree and module, each operation's kind, its source and destination paths, whether each is expected to exist, the SHA-256 of each file's full original and result bytes, and the metadata effects the writer promises. Not the request's `operation`, so a dry run and its apply can use different operation folders;
   - `diffDigest`, the SHA-256 of `diff.patch`'s bytes, for verifying the publication. A reader checks the file against the HTTP value; the inline diff is authoritative.

   An apply (`dryRun: false`) may send `expectWriteSetDigest`. The endpoint computes the edit as it does today, and if the write set's digest differs (a recomputed no-op included), writes nothing and answers `edit-changed` (409), with the new diff, so the caller reviews it. Without it, an apply works as today. Recomputing reruns JDT's current checks, so nothing about the dry run's inputs needs to be fingerprinted or stored. Binary or invalid text stays refused (`refactoring-refused`).

3. **No outcome store.** What a refactoring changed is in `git diff` and the folder's `response.json`; undo is Git's. The contract says plainly that after a lost answer the outcome is uncertain, and the caller reconciles (the folder, `git status`) before retrying; `operation-exists` means only that the folder exists. §10 gains: Fractal Harness checkpoints (commits) before a refactoring when the worktree has work in progress, and serializes other writers to a worktree while an apply runs (the endpoint's locks can't exclude editors, Git or agents).

4. **Writes and crash safety for every apply** (round 1, S2–S4).
   - **Each file is published atomically:** its new bytes go to a sibling temporary file (created exclusively, without following links), which is synced, given the original's mode, owner and group (a file whose owner or group the endpoint can't set is `refactoring-refused` before anything changes, never silently given new ones), then renamed over the original; then the folder is synced. A file is therefore always wholly its original or wholly its new bytes. This replaces T002.07's in-place writes, revising its approved promise: the inode changes. A file with more than one hard link, or with extended attributes or ACLs the endpoint can't carry over, is `refactoring-refused`, naming it. A file the endpoint couldn't write in place (read-only, as T002.07's `write-failed` test uses) is still refused: its writability is checked explicitly, since a rename would otherwise succeed. Creates and move destinations never replace an existing file.
   - **A journal in `-data`,** `<data>/.fractal-jdtls/applies/<id>/`, in a versioned, documented format (so it can also be read by hand), mode 0700/0600, holding each affected file's original bytes and metadata with their SHA-256, and the ordered operations with each path's state before and after. It's written and synced, with its folder and that folder's parent, before the first change.
   - **Order:** the journal; each file's atomic publication, in order, each step marked in the journal; every changed file and folder synced; then "sources done", synced, before the refresh and build. Once the request is answered, a completed journal is deleted (its backups too); startup deletes any completed journal left behind. Git and Harness hold history, so the endpoint keeps none (round 2, T2). If the refresh, build or join then fails, or a copy in the operation folder can't be written, the answer still says the edit was applied, naming the later failure separately. If "sources done" can't be recorded, the journal stays as unresolved, for recovery.
   - **Recovery, at startup, before imports or requests,** idempotent (it can itself be interrupted and run again): for each journal without "sources done", every path is checked, without following links and confined to its worktree, against its before and after states, including a rename's intermediate state (source absent, destination holding the source's original bytes). If every path is in a known state, the endpoint rolls back to the originals, step by step, recording each, syncs every restored file and affected folder, and only then removes the journal. If any path is in neither state (someone changed it after the crash), it changes nothing, keeps the journal and its backups, and the worktree's refactorings are refused with `apply-interrupted` (409), listing every path and its state and where its backup is, until the caller resolves it by hand and sends `POST /v1/refactor/resolve-interrupted` (worktree, journal ID), which removes the journal. The same block applies at once whenever a live rollback, or recording "sources done", fails and leaves a journal unresolved. Unresolved journals are never evicted. Each recovery shows in `/v1/status` and the log. Recovery runs before the port file appears, so nothing reaches the endpoint during it; §10 requires Fractal Harness to keep sessions from writing to a worktree served by an endpoint that is starting until its port file appears, and during a manual resolution (round 2, T1).
   - **Live-process rollback** (today's) uses the same journal; the current `EditWriter.create` registering its undo only after writing is fixed (the journal records the create before it).

5. **The git-ignore check stays** in the endpoint, bounded (as before), as a boundary assertion, not a security boundary.

6. **The fresh check inside the write lock, for every apply** (round 1, S5). Inside the apply's write lock and workspace rule, a fresh scan of the worktree's record is compared with an immutable copy of the computation's fixed-point record: any difference is `files-changed`, nothing written. The scan fails closed, the baseline's scan included: any traversal, discovery or stat failure (a recorded path, or a folder it can't enter, which could hide new inputs) is `files-changed`, naming the path, never skipped; today's `FileRecords.visitFileFailed` silently continues, and changes. And the Java model must not have changed in between: the endpoint keeps a generation counter, raised by JDT's element-changed events for classpath, project and options changes and by preference changes; if it moved between the computation and the writes, the apply is `model-changed` (409, retryable), nothing written. (Another worktree's import in the same process can change the workspace in that gap.)

## What this removes from d8f7e70

The plan store, `planDigest`, the inputs fingerprint and `planNotSavedBecause`, plan lifetimes and caps, the outcome table, `POST /v1/refactor/apply`, and the codes `plan-not-found`, `plan-applied`, `plan-mismatch` and `plan-stale`. Kept or new: `operation-exists`, `operation-folder-unsafe`, `operation-folder-not-ignored`, `git-failed`, `edit-changed`, `model-changed`, `apply-interrupted`, and `POST /v1/refactor/resolve-interrupted`.

## What stays from the earlier reviews

The read-only mapping checks before T002.10 (nothing changes the model between fixed points); the reserved subtree's exclusions (D6); no-follow writes (D5); the bounded Git call (D8); the scratch folder rules (D9, D10). The in-lock fresh check (D1) applies to every apply, not only to saved plans: today the edit is computed under the read lock after the first fixed point, and the write lock is taken afterwards, with per-file checks of the affected files only, so a new reference added to an unaffected file in between is missed. So inside the apply's write lock and workspace rule, a fresh scan of the worktree's record must equal the computation's fixed point's record (any difference: `files-changed`, nothing written), before the per-file checks and the writes.
