# T002.09 — Concurrency across sessions

Step 9 of [T002](T002.md).

## Why now

Sharing is the point of the endpoint. Every operation now exists, so this task tests them under load together, and sets the limits from measurements.

## Depends on

T002.07 and T002.08.

## Design

- [design.md](../design.md) §11, "Threading and queuing".
- [HTTP-FINDINGS](../research/jdtls-http-spike.md), question 6.

## Changes

- **Set the HTTP worker pool's size and queue length** from measurements, and record the numbers in §11 for Chris to review.
- **Timeouts and cancellation everywhere:**
  - the default and `timeoutMs`;
  - cancelling the LSP request or the Eclipse job's monitor when the timeout passes or the caller disconnects;
  - `timeout` and `busy` problems with `retryAfter`.
- **Readiness while a worktree imports,** as the spike measured: requests for other worktrees go on, or wait, as §11 says.
- **An integration scenario: several sessions at once.**
  - Four clients, one per worktree (`main`, `wt-a`, `wt-b`, and a fourth added during the run), run a mix in a loop for at least 10 minutes:
    - navigation;
    - edits on disk followed by `build`;
    - refactorings that are applied and then reverted with `git checkout`.
  - Meanwhile, one worktree is removed and added again.
  - Each client checks its own results against a single-client run of the same steps.
- **A slow-operation test:** an operation held past its timeout returns `timeout`, other sessions' requests keep being answered, and the endpoint recovers.

## Acceptance

Record real output for each item.

- **The several-sessions scenario:** every result matches the single-client run, and there are no `internal` problems.
  - Latency percentiles for each operation type are in the evidence.
  - The JVM's heap use at the start and the end is recorded.
- **Timeout and disconnect:** shown cancelling the work in JDT LS (from its log or the endpoint's), not just abandoning it.
- **`busy`:** shown when the queue is full, with `retryAfter`.
- **The chosen pool and queue sizes,** with the measurements behind them.
- `mise run validate` passes, with its wall time recorded. If the long scenario makes the gate too slow, it runs as a separate task, `mise run test:soak`, and Chris decides whether it's in the gate.

## Out of scope

- Performance work beyond setting the limits. Report hot spots for a later series.
