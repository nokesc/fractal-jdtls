# T001.02 — The pin tool and the 1.63.0 pin

Step 2 of [T001](T001.md).

## Why now

The installer and the launcher both read `pin.json`, and their tests need a real one.

## Depends on

T001.01.

## Design

[design.md](../design.md) §3: the pin, `tools/pin.py`, and the verified facts for 1.63.0.

## Changes

- **`tools/pin.py <jdtls-version>`** does every step in §3:
  - checks the tarball against Eclipse's `.sha256`;
  - records the hash of every file;
  - classifies each jar as Eclipse-signed, identical to Maven Central, or neither;
  - fetches and pins Byte Buddy `1.18.14`, checking its `.asc` when `gpg` and the key are available;
  - writes `pin.json` and a pin report.
- **`pin.json` for JDT LS 1.63.0** (`jdt-language-server-1.63.0-202610191322.tar.gz`). The minimum Java is 21.
- **The pin report** is committed under `.context/pins/1.63.0.md`. It lists every jar's classification, and names every file trusted only through the tarball's checksum.
- **Unit tests** for the classification and the output format, against a small fake tarball and a fake server.

## Acceptance

Record real output for each item.

- The tarball's SHA-256 equals `b1f2abe0b3cccb462cf64fb4a5587c7d09df60cf8be7748b152cbd89d018bdc4`, and the published `.sha256`.
- The report shows 58 Eclipse-signed jars and names all four m2e jars as trusted through the tarball only. If the counts differ from design §3, stop and report.
- The report lists which jars match Maven Central.
- Running `tools/pin.py 1.63.0` again produces a byte-identical `pin.json`.
- `mise run validate` passes.

## Out of scope

- Comparing against the Red Hat extension (design §3). It's optional, and no extension version is known to bundle 1.63.0.
