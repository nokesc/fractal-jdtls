# T002.03 — The bundle and HTTP mode

Step 3 of [T002](T002.md).

## Why now

Every operation runs inside this bundle, behind this launch path and token check.

## Depends on

T002.02, approved by Chris.

## Design

- [design.md](../design.md) §11: "Inside JDT LS", "Launching", "Security", "Errors", "Status and shutdown"; §2, §4 and §5 for the zip, `release-files.json` and the launcher.
- [HTTP-FINDINGS](../research/jdtls-http-spike.md), questions 1 to 3.

## Changes

- **The `endpoint/` Maven module** in the root POM, producing `endpoint/target/fractal-jdtls-endpoint.jar`, an OSGi bundle with a hand-written or generated manifest.
  - It compiles against the pinned tarball's jars, downloaded into a build cache and verified against `pin.json`, never `~/.m2` for Eclipse's files, and never committed. A unit test fails if the bundle imports a package that the pinned JDT LS doesn't export.
  - The module uses Java `--release 21`, like the agent.
- **The release zip and the installer:** `lib/fractal-jdtls-endpoint.jar` is added to the zip and to `release-files.json`. `--verify` and the launch check cover it.
- **The launcher's HTTP mode,** as in §5 and §11:
  - the `--http-port-file` and `--http-settings` options;
  - `FRACTAL_JDTLS_HTTP_TOKEN` is required in HTTP mode, with its minimum length, and kept out of JDT LS's environment once read;
  - the bundle is loaded the way the spike chose;
  - `--help` documents all of it.

  Without HTTP mode, the command line is unchanged, which T001's unit tests keep checking.
- **The bundle:**
  - the in-JVM client and its answers to JDT LS's requests back to the client;
  - the HTTP server on `127.0.0.1`, port 0;
  - the port file, written atomically with mode 0600;
  - the token, `Host` and `Origin` checks;
  - the problem framework and the `internal` error;
  - `GET /v1/status` (with `wait=ready`), `GET /v1/openapi.json`, `POST /v1/shutdown`.
- **Tests:**
  - JUnit: the checks, the problem framework, and that every route the server registers is in the description;
  - pytest unit tests for the launcher's HTTP options;
  - a new integration test (`tests/integration/test_http.py`) that starts the installed release in HTTP mode.

## Acceptance

Record real output for each item.

- **Start and readiness:** `bin/jdtls --http-port-file <f>` with a token and a settings file starts. The port file appears with mode 0600, and `GET /v1/status?wait=ready` reports ready and the release.
- **The checks:** each request below is refused, with the problem's body shown, and the token never appears in any output or log.
  - no token, or the wrong token: `401`;
  - a wrong `Host`: refused;
  - an `Origin` header: refused;
  - in HTTP mode, a missing or short token: the launcher refuses to start.
- **Only localhost:** `ss -ltnp` shows only `127.0.0.1:<port>` for the JVM, and no other socket.
- **Shutdown:** `POST /v1/shutdown` answers, JDT LS saves its workspace, and the process exits 0.
- **The install stays unchanged:** `--verify` passes afterwards, including the endpoint jar, and nothing was written inside the install.
- **Plain mode is unchanged:** the T001 integration suite passes.
- `mise run validate` passes.
