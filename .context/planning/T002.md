# T002 — The HTTP endpoint: one JDT LS shared by many sessions

Builds [design.md](../design.md) §11 and the §1, §5 and §10 changes that go with it. Starts from a spike, as T001 did, because the riskiest mechanisms are unproven:

- how our bundle loads and becomes JDT LS's only client inside the JVM;
- adding and removing worktrees at runtime (design §10);
- keeping JDT LS in step with the disk without a file watcher or timing heuristics.

Chris decided the shape on 2026-11-07:

- in-process, with no extra processes;
- HTTP only, with no stdio client;
- every request names its worktree and Maven module, in the body;
- the disk is reconciled at fixed points, stability first;
- the endpoint applies refactoring edits itself;
- code is addressed by Java name, with structured errors written for an LLM;
- a generic LSP passthrough;
- simple refactorings now, advanced ones in later series;
- worktrees are added and removed at runtime;
- running tests and debugging are out.

## How the series works

- **As in [T001](T001.md):**
  - tasks are ephemeral, and the design and the code are authoritative;
  - each task records the real output of every acceptance item in `.context/planning/evidence/T002.NN.md`, committed with the work in one commit whose subject starts `T002.NN: `;
  - nothing is tagged, pushed or published by an agent.
- **The spike is a seed, not the product.** T002.01 writes its code to `.context/spike/http/` and its findings to `.context/research/jdtls-http-spike.md` (HTTP-FINDINGS). Later tasks port what they need. T002.05 deletes the seed and keeps the findings.
- **Chris's stop points:**
  - **After T002.02:** Chris reviews the API contract and the design changes that the spike made. Every `[REVIEW HERE]` in design §11 must be settled before T002.03 starts. When Chris has delegated decisions for a run, the governor settles them, marks each in the design "Decided by the governor on <date> during <task>; to review", and lists it in the run's report.
  - **Within T002.01:** if any of its blocking questions fails, the task stops with `T002.01-BLOCKED.md`. The design depends on the answers.
- **Stability over speed.** Where a task has to choose, it takes the mechanism that gives the same result every time, measures what that costs, and reports the numbers. It never silently switches to a faster heuristic.
- **Every task keeps `AGENTS.md` and `mise tasks ls` current** for what it adds.

## Overall acceptance

- Every child task's acceptance is recorded in its evidence file.
- Design §11 has no `[REVIEW HERE]` left, and every decision made along the way is in the design.
- **One full loop, through HTTP only,** recorded in T002.12's evidence, against the installed release:
  1. start in HTTP mode;
  2. add two worktrees;
  3. edit a file on disk, then `build`, and see the expected problems;
  4. rename a method by name, and see the edit and a clean build;
  5. remove a worktree;
  6. shut down.

  Nothing is written inside the install, and `--verify` passes afterwards.
- Without HTTP mode, the launcher and the T001 integration suite behave as before.
- `mise run validate` passes.
