# T002.10 — A folder per operation

Step 10 of [T002](T002.md). Inserted by the governor on 2026-11-08, at Chris's request.

## Why now

Nothing records a refactoring where Fractal Harness, a replacement agent or Chris can inspect it after a crash or disconnect, and nothing ties an apply to the dry run that was reviewed. Chris's design (§11, "Operation folders") is deliberately minimal: blocking calls, inspectable records, an optional dry-run check, and recovery by Git and the agents. This comes before T002.11, so the soak covers it.

## Depends on

T002.07 (refactorings and the apply), T002.08 (the scratch folder).

## Design

[design.md](../design.md) §11, "Operation folders" and "Refactorings and edits"; §10, "Refactoring policy and recovery are the client's".

## Changes

The smallest changes to the existing implementation. **Don't add** a transaction journal, file backups, saved plans, automatic rollback, writer coordination, a lookup operation or any crash-recovery protocol (Chris, 2026-11-08); the larger variants in `.context/future/operation-folders/` are parked, not planned.

- **The operation folder** (a small new class, called from `CodeRequest`): once the request is parsed and its worktree known, `<worktree>/temp/fractal-jdtls/<id>/` with an ID the endpoint generates, `<UTC time to the millisecond>-<8 random hex digits>`; created exclusively; its real path inside the worktree's real root through the existing `Edits.inside` (`edit-outside-worktree` otherwise).
- **Its three files, in order:** `request.json` (time received, operation, request body, never the token); `diff.patch` once the edit is computed, before any source write; `response.json` last, success or problem, by temporary name and rename.
- **The answer** to a successful request gains `operation` and `operationFolder`.
- **`/v1/status`** shows each in-flight refactoring's `operation`: stored on its existing `InFlight` entry, set before the folder is created, and the entry closed only after `response.json` is written.
- **`writeSetDigest`** in every refactoring's answer, computed in `Edits` from the prepared write set as §11 defines it; an optional `expectWriteSetDigest` on an apply, compared before anything is written, also when the recomputed edit changes nothing (today `CodeRequest` returns early there); `edit-changed` (409) when it differs, with the new diff.
- **`FileRecords.skipped`** also skips `temp/fractal-jdtls/`.
- **The `EditWriter.create` fix** (found in review): register the create's undo before writing the file, so a create that fails partway is undone by the existing live undo. A regression test that fails on the current code.
- **The contract:** `operation`, `operationFolder`, `writeSetDigest`, `expectWriteSetDigest`, the code `edit-changed` with its example and `hint`, and the operation folder described. Replace the refactoring examples with the real ones.
- **The fixture's `.gitignore`** ignores `temp/`. **AGENTS.md** mentions the folders.

## Acceptance

Record real output for each item.

- **A dry run, then its apply with `expectWriteSetDigest`:** each folder's files listed and shown, and the answer's `operation` and `operationFolder`.
- **`edit-changed`:** a file in the edit changed between the dry run and the apply; and once more with the change only outside the diff's hunks (the diff is the same, the digest isn't); nothing written either time.
- **Still running:** a refactoring held at a `TestPauses` point; `/v1/status` lists its `operation` while its folder has no `response.json`; after it's released, the ID is gone and `response.json` is there.
- **A refused refactoring** (`refactoring-refused`) still leaves `request.json` and its `response.json`.
- **A `temp` that links outside the worktree:** refused, nothing written outside.
- **The outcome unknown:** JDT LS killed (`kill -9`) at a `TestPauses` point after the first source write; its folder has `request.json` and `diff.patch` and no `response.json`; `git checkout` of the files `diff.patch` names restores the worktree (shown with hashes). The endpoint does nothing about it at its next start, and its `/v1/status` doesn't list that ID.
- **The records' cost on the next fixed point:** the first fixed point after a refactoring measured (it's a full one, because Eclipse's sync check sees the new files; accepted, §11), and the ones after it on the fast path. (Corrected by the governor after the first commit: the earlier wording demanded the fast path at once, which only an Eclipse filter, deferred by the design, could give.)
- **The create fix:** the regression test failing on the current code, then passing.
- `mise run validate` passes.
