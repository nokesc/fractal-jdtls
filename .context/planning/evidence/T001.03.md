# T001.03 evidence: the installer

Recorded 2026-11-01 on branch `t001-first-release` (after T001.02), Linux (WSL2). The real install ran with the system Python, `/usr/bin/python3` (3.14.4), outside any virtual environment, the way a user would run it. The unit tests ran under the mise Python, 3.12.14. Maven used the scratch repository `/tmp/fractal-jdtls-t001/m2/repository` through `MAVEN_ARGS`.

## What was built

- **`bin/install.py`** (design §4). Standard library only, written for Python 3.10 or newer.
  - Installs the release it ships in into `<root>/<release>/`, with `<release>` from `pin.json`.
  - The root comes from `--root`, else `FRACTAL_JDTLS_ROOT`, else the root an installed copy lives in, else `${XDG_DATA_HOME:-~/.local/share}/fractal-jdtls`.
  - It assembles the install in `<root>/.<release>.*.partial` beside the target: it downloads the tarball and checks its SHA-256 before unpacking, then unpacks only regular files and folders, refusing links, `..` and absolute paths.
  - It then downloads Byte Buddy into `lib/` and checks it, and copies the release's own seven files.
  - Before renaming the folder into place, it verifies the whole tree: missing, extra or changed files against `pin.json`, and the release's own files against the release folder.
  - It holds a lock file, `<root>/.<release>.lock`, while it works, so it can safely remove a partial folder left by a killed install.
  - SIGINT and SIGTERM unwind and remove the partial folder. It retries HTTP 429/5xx and broken connections, including a body shorter than `Content-Length`.
  - `--verify` reports every missing, extra or changed file, and exits 1 if there are any.
- **`bin/jdtls`**: a placeholder that exits with "the launcher isn't implemented yet (T001.05)". It's there so the zip and the install have the full §2 layout. T001.05 replaces it.
- **`tools/release_zip.py`** and **`mise run release:zip`** (which depends on `build`). The tool writes `build/fractal-jdtls-<release>.zip`, with the §2 layout under `fractal-jdtls-<release>/`.
  - The zip is reproducible: entries are sorted, timestamps come from the POM's `project.build.outputTimestamp`, and modes are fixed (755 for `bin/`).
  - It takes the file list from `install.py`'s `RELEASE_FILES`, so the two can't drift.
  - It refuses to build if the agent jar's `Class-Path` doesn't name `pin.json`'s Byte Buddy jar.
- **`mise run validate`** is now test, then `release:zip`, which builds the jars first.
- **`tests/unit/test_install.py`** (33 tests) and **`tests/unit/conftest.py`**. The conftest gives every unit test a scratch `HOME` and XDG folders, for the reason under item 3.
- **AGENTS.md** lists `release:zip`. **Design §4** has a `[REVIEW HERE]` proposal (see "For Chris").

## 2. After a tampering edit, `--verify` names that file and exits non-zero

This is in the log above, under "tampering edit". I appended one byte to `eclipse/plugins/org.eclipse.m2e.core_2.8.0.20260815-0704.jar`, which changed its SHA-256 from `34872f77…` to `f9128a80…`. ## Failures along the way (retained)

- **A short download wasn't retried.** The retry test first failed with:

  ```
  HTTP 503; retrying in 0 s
  install.py: error: Byte Buddy 1.2.3 from http://127.0.0.1:37803/maven2/.../byte-buddy-1.2.3.jar has SHA-256 cb61609f…, but pin.json expects 060b8bd4…
  ```

  urllib doesn't raise when a connection closes before `Content-Length`. The hash check refused the file, but it wasn't retried. `download()` now compares the bytes received with `Content-Length` and retries.
- **The unit-test leak into `~/.local/share`,** under item 3.
- **`--verify` from a stale installed copy.** My first real run used a zip built before I added root inference, so the installed `--verify` looked in the default root (`isn't installed in /home/nokes/.local/share/fractal-jdtls/1.63.0-1`, exit 1; read-only, inside the sandbox). I rebuilt the zip, and the whole acceptance run above uses the final code.
- Three test-authoring mistakes, fixed in the tests:
  - a `KeyError` from deleting an unpinned file from the pin when it wasn't there to begin with;
  - a sleep stub that cleared the truncation too early;
  - "(1 problems)", which now reads "(1 problem)".

## For Chris

- **`[REVIEW HERE]` in design §4.**
  - `pin.json` has no hashes for this release's own seven files. So `--verify` checks their contents only when run from the unzipped release; run from inside the install, it checks them for presence only, and says so.
  - The proposal: if the launch check (§5) should cover the agent jar, `release:zip` could add a hash list of these files to the zip.
  - The same note records three behaviors the design doesn't spell out. An installed `install.py` defaults to its own root. The lock file stays in the root. A target that exists but fails verification is left alone, with an instruction to delete it and run again.
- **`bin/jdtls` is a placeholder** until T001.05.
- **The lock file** `<root>/.<release>.lock` stays in the root after an install. "To uninstall, delete the folder" still works; the empty lock file is left behind.

## Review

Response to the cross-agent review, 2026-11-02. The governor resolved the `[REVIEW HERE]` proposal in design §4 in commit `c53635b`, and said to implement that decision as R1's fix.

- **R1: fixed.** The finding was valid. Run from inside the install, `--verify` checked the release's own files only for presence, so a changed agent jar passed. It now works as design §2 and §4 describe:
  - `release:zip` writes `release-files.json` into the zip. It holds the release ID and the SHA-256 of every other file in the zip: `bin/install.py`, `bin/jdtls`, the agent and boot jars, `pin.json`, `LICENSE` and `NOTICE`.
  - Before installing, or before `--verify` runs from an unzipped release, the installer checks the release folder against that file. Any change, missing file, missing or extra entry, invalid hash, or release ID different from `pin.json`'s stops it, before any download.
  - The installer copies `release-files.json` into the install. `--verify` checks the seven files against it wherever it runs from. From an unzipped release, it also requires the installed `release-files.json` to equal the release's copy, so an install whose `release-files.json` was rewritten to match a change is still caught.
  - The "checked for presence only" output, and comparing against the release folder's copies, are gone. `install.py` keeps a single list of the hashed files (`HASHED_FILES`), and `tools/release_zip.py` uses it.

  The section numbers below continue those above.
