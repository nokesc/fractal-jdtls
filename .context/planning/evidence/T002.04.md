## What changed

- **The agent fix** (`agent/boot`, as the governor kept it minimal). `Hooks.mavenProjectRead()` is set by the first naming or requester hook call (`Boot.projectName`, `populateClasspathEnter`, the Maven requester hooks). The shutdown check now reports the hooks whose class never loaded only if `populateClasspath` was never advised and a Maven project was read. Before, it reported if any hook was in place. Two `HooksTest` cases are new, and three set the flag. Design §6: a proposal.
- **The endpoint's worktree operations** (`endpoint/`):
  - **`WorktreeOps`:**
    - routes `POST /v1/worktrees/add`, `/remove` and `/list`, and the new `POST /v1/modules/check`;
    - the worktree thread, on which changes run one at a time;
    - the folder change: `workspace/didChangeWorkspaceFolders`, the `fractal/barrier` request, which must fail with `-32601`, then the join;
    - the health check and its one repair;
    - the restart's check, and the status pieces.
  - **`Alone`:** imports run alone. A change is announced when it's accepted. It begins once the requests that reach JDT LS have finished, and new ones wait for it, or get `not-ready` with `reason: importing`.
  - **`Registry`:** the registered worktrees, their modules and repair, and the saved state, `<data>/.fractal-jdtls/worktrees.json`, written atomically. **`Mapping`:** the `ModulePath` syntax, the add-time worktree root check, and every per-request check of §11 "The contract", each a catalogued problem with a `hint`. **`Workspace`:** everything read from Eclipse, m2e and JDT LS's importer classes. **`Jobs`:** "Joining the work", ported from the spike, then changed (see "Found and fixed"). **`Fields`:** strict body fields. **`InFlight`:** the status's `inFlight`.
  - `Endpoint` loads the saved worktrees before JDT LS starts. It drops any whose folder is gone or that's no longer a worktree root, and passes the rest in `initialize`, both as `workspaceFolders` and as `initializationOptions.workspaceFolders`, which is what JDT LS reads (`BaseInitHandler`). `LspClient` answers JDT LS's `workspace/workspaceFolders` from the registry. `HttpApi.Request` carries its arrival time, so waits count the time spent queued for a worker.
  - 8 new codes in `Code`, all already in the catalogue. New imports in the manifest: `org.eclipse.core.resources`, `org.eclipse.core.runtime` `[3.8,4)`, `org.eclipse.core.runtime.jobs`, `org.eclipse.jdt.ls.core.internal.managers`, `org.eclipse.m2e.core`, `.embedder` and `.project`. New system-scoped jars in `endpoint/pom.xml`: equinox.common, core.jobs, core.resources and m2e.core, plus `org.osgi.service.prefs` for `JobsTest` only (not imported).
  - No Eclipse class loads before JDT LS has started: everything that touches Eclipse types is in `Workspace` and `Jobs`, and `Jobs` is created in the check after `initialize`.
- **The contract** (`openapi.json`, 24 operations):
  - the new `POST /v1/modules/check` (`CheckModuleRequest`, `CheckModuleResponse`);
  - `timeoutMs` on `worktrees/add` and `/remove` bounds only the wait, so those two no longer list `504 timeout`;
  - the `not-ready` `reason` description now covers removals and the restart's check.
- **The launcher** passes `-Dfractal.jdtls.http.state=<data>/.fractal-jdtls/worktrees.json` (`--help` and the module docstring say so). The `-Dfractal.jdtls.http.*` refusal already covers it. `tests/unit/test_launcher.py`'s expected options include it.
- **Tests:**
  - JUnit in `endpoint/`, from 40 to 53:
    - `WorktreesTest` (10): the gate's ordering and `not-ready`, the state file, dropped worktrees, `Fields`, the `ModulePath` syntax, the root check with a symbolic link, and the `worktree-not-registered` candidates;
    - `JobsTest` (3), with Eclipse's real job manager;
    - `DescriptionTest` registers the worktree routes, and `LspClientTest` covers `workspace/workspaceFolders`.
  - Integration, all through HTTP:
    - `test_http_worktrees.py` (20): the story below;
    - `test_import_repair.py` (2);
    - `test_imports.py`: one large import in the gate, and the 20 imports, marked `imports`;
    - `large_tree.py`: the spike's generator, ported;
    - `test_http.py` gains a check that a start and shutdown with no worktrees reports no agent error.
  - `endpoint_client.py` gains `Client`, which checks every answer against the served description, and the shared `http_command` and `write_settings`.
- **Tasks and docs:**
  - `mise run test:integration` runs `-m 'not imports'`;
  - the new `mise run test:imports` runs the 20 imports (`FRACTAL_JDTLS_IMPORTS` sets the count), and the marker is registered in `pyproject.toml`;
  - AGENTS.md describes the endpoint's state file, the classes, the new tests and `test:imports`.
- **Design:** seven `[REVIEW HERE]` proposals (§6 once, §11 six times), listed under "Decisions for review".

## Found and fixed: a join that waited for a job's next run

Seen in a rerun of the story: two removals took 301,328 and 300,563 ms, against 0.6–1.9 s everywhere else. JDT LS logged nothing in that time. I made the endpoint log, every 10 s, any join still waiting, naming the job, then reproduced it with the story's steps (`$S/driver/repro.py`). It happened in 1 run of 3:

```
remove wt-stray: 200 in 301277 ms
still joining JDT LS's job 'Periodic workspace save.' (org.eclipse.core.internal.resources.DelayedSnapshotJob, sleeping) after 10000 ms; other jobs: Compacting resource model (org.eclipse.core.internal.utils.StringPoolJob, sleeping)
…
still joining JDT LS's job 'Periodic workspace save.' (org.eclipse.core.internal.resources.DelayedSnapshotJob, sleeping) after 290016 ms; …
removed wt-stray: 3 projects deleted, files kept; joined 5 jobs in 2 rounds, 301263 ms: [Updating workspace folders (69 ms), Register Watchers (1118 ms), Periodic workspace save. (299968 ms), Sending build events with disabled autobuild (102 ms), Updating Maven Dependencies (0 ms)]
```

- **The cause.** Eclipse's workspace save ran during the removal, so the round found it running. By the time its turn came, after JDT LS's "Register Watchers" (about 1 s), it had finished and rescheduled itself for its 300 s interval. `Job.join` on a sleeping job waits for its next run. The spike's join, which the design adopted, has the same race.
- **The fix** (`Jobs.await`):
  - the join waits for the job's own `done` event, with the listener added before the state is read;
  - a job that has ended, or gone back to sleep, counts as joined, unless it's a kind joined while it sleeps (`AutoBuildJob`, m2e's background queue);
  - still no timing.
- **A deterministic test.** `JobsTest.aJobFoundRunningThatHasGoneBackToSleepIsJoinedAtOnce` puts a real Eclipse job in that state. With the old `Job.join` put back (and a 5 s guard instead of 600 s), it fails:

  ```
  [ERROR] org.fractal.jdtls.endpoint.JobsTest.aJobFoundRunningThatHasGoneBackToSleepIsJoinedAtOnce -- Time elapsed: 5.026 s <<< FAILURE!
  org.opentest4j.AssertionFailedError: expected: <true> but was: <false>
  ```

  With the fix, all 3 `JobsTest` cases pass.
- **After the fix, 5 runs of the same steps:** every removal took 609–1,117 ms, and in 4 of them the save job was joined at the same point:

  ```
  fixed2 removed wt-stray: … joined 5 jobs in 2 rounds, 1072 ms: [Updating workspace folders (134 ms), Register Watchers (833 ms), Periodic workspace save. (0 ms), Sending build events with disabled autobuild (101 ms), Updating Maven Dependencies (0 ms)]
  ```

## Decisions for review

The first seven are `[REVIEW HERE]` proposals in the design.

1. **§6 "When a hook that never loaded is reported":** "provided at least one other hook was [in place]" becomes "provided a Maven project was read (a naming or requester hook ran)".
2. **§11 "The contract":** the checks in detail, and `POST /v1/modules/check`, an operation that runs only them, returning the module and `waitedMs`. The task allowed such an operation if the description lists it; it's public, because the harness can use it to ask why a module can't be addressed. A project whose name doesn't start with the worktree's folder name also counts as `module-in-other-worktree`.
3. **§11 "Restart":**
   - the state file is `<data>/.fractal-jdtls/worktrees.json`, not per release, passed by the launcher as `-Dfractal.jdtls.http.state`;
   - `initialize` carries `initializationOptions.workspaceFolders`, which is what JDT LS reads;
   - a saved worktree is dropped when it's gone, not a root, or its name is taken, and a damaged file stops startup;
   - the restart's check joins every job left after `ServiceReady`, then checks health with the same one repair.
4. **§11 "Imports run alone":**
   - removals and the restart's check run alone too;
   - `reason: importing` covers all three;
   - a started change is never cancelled, so `timeoutMs` on `add` and `remove` bounds only the wait (then `not-ready`), and those two no longer list `timeout`;
   - `list` and `status` never wait.
5. **§11 "Import health":** the modules are found as JDT LS's Maven importer finds them (`BasicFileDetector`, then m2e's `LocalProjectScanner`); a `pom`-packaged module needs no Java nature; the repair is two folder changes.
6. **§11 "Import health":** a POM that m2e can't read fails the check too. The repair can't help, so it's `import-failed`, but the failure quotes m2e's markers and the hint says to fix the POM. Telling this apart before the repair (saving 1.3 s) isn't done.
7. **§11 "Joining the work":** a join waits for the end of the run it found, never the job's next run (above).
8. **The contract changes** (the description is edited directly, as AGENTS.md says):
   - `modules/check` and its two schemas;
   - the `timeoutMs` wording of `add` and `remove`, and the 504s they no longer list;
   - the `not-ready` `reason` description;
   - `remove`'s note that it runs alone;
   - `add`'s `not-ready` line now covers `timeoutMs`.
9. **Not done here: the `.git` resource filter on each worktree's projects** (§11 "Keeping in step with the disk" says it goes on "when the worktree is added"). It serves the refresh at each fixed point, which is T002.05's, so it's left for T002.05, which must also put it on worktrees restored at a restart.

## Review

The cross-agent review (`.context/planning/T002.04_agent_review.md`) had three findings. All three are valid and fixed, as the governor's notes in `8b6e617` settled them.

- **R1, malformed POMs passed the health check: fixed.**
  - **Confirmed in the code.** `Workspace.modules` took the modules only from m2e's `LocalProjectScanner`, and only logged its errors. So a POM m2e couldn't parse was never a module. A malformed standalone root POM gave no modules at all, which reported `imported`.

One whose POM can't be read keeps the parser's reason, fails the check, and its failure quotes that reason under the POM-errors hint.
  - **Tests.**
