## What was done

- **`POST /v1/lsp`** (`LspPassthrough`):
  - It reads `worktree`, `module`, `method`, `params`, `changedPaths`, `timeoutMs` (default 120,000 ms, the reads' default) and `wait`. Then it refuses what isn't allowed, before any wait.
  - Otherwise it runs through `CodeRequest.run`, like every read: the readiness and worktree-change waits, the mapping with every check, the fixed point with its fast path, and then the answer under the worktree's read lock.
  - The answer checks the URIs in `params`, then sends the request with `LspClient.call`. Its deadline sends `$/cancelRequest` and gives `timeout` with phase `running`, and JDT LS's error gives `lsp-error`, with `lsp` exactly as JDT LS sent it.
  - The response is `{sync, result, applyEditsRefused}`.
- **The classification:**
  - The allowed requests and commands, and the refused methods and commands each with a reason and what to use instead, are in `LspPassthrough`'s four tables (below).
  - After `initialize`, `ServedMethods` reads what JDT LS really has: every method of `JDTLanguageServer`, through lsp4j's `ServiceEndpoints.getSupportedMethods`, and the `executeCommandProvider` commands of the `initialize` result, which `LspClient` now keeps.
  - The endpoint logs the comparison, naming anything unclassified. It's an allow-list: anything not allowed is refused.
- **URIs:**
  - Every `file:` URI anywhere in `params` must lie in the named worktree, after normalizing, and every `jdt:` URI that names a project must name a project located in it (after the review, R1: by the project's location in Eclipse's workspace, not its name). Otherwise the answer is the new code `uri-outside-worktree` (422), whose candidate names the worktree and module that hold the file.
  - A malformed `file:` URI is `invalid-request`.
- **`workspace/applyEdit` during a passthrough:**
  - `LspClient.watchApplyEdits()` collects every `workspace/applyEdit` that JDT LS sends while the request is in flight.
  - Each is answered `applied: false`, with the reason "the Fractal JDT LS endpoint applies no edit JDT LS sends: the LSP passthrough returns it to its caller, unapplied", and listed in `applyEditsRefused`.
  - Any other request from JDT LS is answered as before.
- **Cancel logging:** `LspClient` logs each `$/cancelRequest` it sends. It also logs JDT LS's late answer to a request it no longer waits for, with that answer's error code. That is what shows the cancel reaching JDT LS.
- **The test-only hold `TestJobs`:**
  - It uses the existing test pauses folder, at the point `lsp-hold`. When armed, it schedules an Eclipse job of JDT LS's `DocumentLifeCycleJobs` family, which runs until the test deletes the marker. `textDocument/documentSymbol` joins that family with the request's own monitor before it answers.
  - This holds a request inside JDT LS with no dependence on timing. The launcher never passes the property.
- **The contract:**
  - The `/v1/lsp` description now lists every method and command it sends, every one it refuses, the URI rule, `applyEditsRefused`, and that documents are never opened.
  - Its examples now show the gate's real `documentSymbol`, `getClasspaths` and `lsp-error` answers, with the paths shortened.
  - `LspResponse` gains `applyEditsRefused`, the catalogue gains `uri-outside-worktree` with an example, and `Code` gains `LSP_ERROR`, `LSP_METHOD_REFUSED` and `URI_OUTSIDE_WORKTREE`.
- **The build:**
  - `endpoint/pom.xml` now sets `forceCreation` on the jar plugin. Without it, a manifest-only change left the old jar in place (see "Failures corrected").
  - `tests/unit/test_endpoint_bundle.py` gains two checks: the built jar's manifest equals the source manifest, and every package the bundle's classes use (`jdeps -verbose:package`) is imported.
  - The manifest imports `org.eclipse.lsp4j.jsonrpc.json` and `org.eclipse.lsp4j.jsonrpc.services`.
- **Tests:**
  - JUnit: `LspPassthroughTest` (9 tests: the tables, refusals, coverage and URIs), two new `LspClientTest` cases (an `applyEdit` during a watch is refused and kept; a request past its deadline is cancelled, and JDT LS's error is kept whole), and `DescriptionTest` for the new route and code.
  - Integration: `tests/integration/test_lsp.py` (58 tests on one story).

## How the methods and commands were classified

Before writing the tables, I read the pinned jars:
- **Methods:** a probe (`temp/t002.09/Methods.java`, run with every plugin jar of the build cache on the class path) listed `ServiceEndpoints.getSupportedMethods(JDTLanguageServer.class)`: 102 methods.
- **Commands:** `org.eclipse.jdt.ls.core`'s `plugin.xml` registers 33 commands on `org.eclipse.jdt.ls.core.delegateCommandHandler`, all with one class, `JDTDelegateCommandHandler`; no other bundle contributes any (`temp/t002.09/plugin_commands.py`). `javap` of `JDTDelegateCommandHandler.executeCommand` maps each command to the method it calls, and that's how each one's effect was read.
- **Edits JDT LS might push:** every caller of `JavaClientConnection.applyWorkspaceEdit` in `org.eclipse.jdt.ls.core` was found:
  - `java.edit.organizeImports`, only when `ClientPreferences.isWorkspaceApplyEditSupported()`, which is false because the endpoint claims `workspace.applyEdit: false`, so it returns its `WorkspaceEdit` instead;
  - `BaseDocumentLifeCycleHandler.handleFileRenameForTypeDeclaration`, reached from `workspace/didRenameFiles`, a notification the passthrough refuses.

  So with JDT LS 1.63.0, no allowed request makes JDT LS send `workspace/applyEdit`. `applyEditsRefused` is tested in JUnit against a fake server, and the integration story shows it empty, with the files unchanged, after `textDocument/rename` and `java.edit.organizeImports`.
- **Files and workspace changes:** no request handler performs a `Change`, commits a working copy or writes a file. The writers (`setRawClasspath`, `IFile.create*`, `IResource.delete`) are reached only from the refused commands, from imports, or from `DocumentLifeCycleHandler.resolveCompilationUnit`, whose fake compilation units for files outside every project come only from `didOpen`, which is refused.

## Decisions for review

All are in design §11's `[REVIEW HERE]` "T002.09's details":

1. **An allow-list for methods and commands, checked against the real server at startup.**
   - What's not allowed is refused before any wait, including methods JDT LS doesn't serve and ones a later JDT LS adds. The endpoint answers those itself (`lsp-method-refused`, with the reason) rather than passing them on for JDT LS's -32601.
   - The startup log names anything unclassified, and the integration suite fails unless that's none.
2. **The classification itself** (the tables below). Beyond §11's lists, it refuses:
   - the builds (`java/buildWorkspace`, `java/buildProjects`) and project updates (`java/projectConfigurationUpdate`, `java/projectConfigurationsUpdate`);
   - the editor file-operation requests `workspace/willCreateFiles`, `willRenameFiles` and `willDeleteFiles`, which only compute edits, but belong to the file-synchronization protocol the endpoint doesn't take part in;
   - the ten more commands listed there.
3. **`uri-outside-worktree`, a new code** (422, with candidates).
   - `jdt:` URIs are checked by the project their handle names, placed by its location (after review R1); I extended "file: URIs" to them for the same reason, since a class file read through another worktree's project uses that worktree's classpath, which this request didn't reconcile.
   - The `file:` check is lexical, after normalizing. A URI that reaches the worktree only through a symbolic link is refused, and the detail says to spell it with the worktree's real path.
   - The check runs after the fixed point, under the read lock, because it needs the mapped worktree.
4. **`applyEditsRefused` is always present.** An edit is listed in every passthrough in flight when it arrives, since JDT LS doesn't say which request it belongs to.
5. **No cancel on disconnect.** The governor's prompt asks for `$/cancelRequest` on timeout or disconnect, but design §11 already records that the JDK's HTTP server gives no sign of a disconnect. The passthrough behaves like every read: only the deadline cancels. This can be revisited with the reads in T002.11 (concurrency), which the design says may revisit it.
6. **The test-only hold `TestJobs`**, which relies on JDT LS 1.63.0's `DocumentLifeCycleJobs` family name. The launcher never passes the property, and a re-pin that renames the family fails the cancel test loudly.
7. **`forceCreation` on the endpoint's jar, and the two bundle checks** (outside the passthrough, but found by it).
