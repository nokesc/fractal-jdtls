## Decisions for review

All of them are in design §11 "Threading and queuing", `[REVIEW HERE]` "T002.11's details":

1. **The pool: 16 workers and a queue of 64, then `busy` with `retryAfter: 2`.** The measurements are above. 16 is where the rate levels off, and the conservative choice for stability: more threads only add latency and heap. The queue bounds memory and wait time, well under the 256 connections.
2. **A disconnect isn't noticed; the deadline is the cancel.** As decided in advance: there's no supported API for it, and nothing reaches into the server's internals. The description now tells callers to send a `timeoutMs` no longer than they'll wait.
3. **`Deadline` is a plain `IProgressMonitor`.** A bug fix, but it records why it must never be a `NullProgressMonitor`.
4. **JDT LS's limitation is accepted and pinned:** a handler waiting for its document life-cycle jobs isn't stopped by `$/cancelRequest`. The endpoint still answers `timeout` and frees its worker. Fixing it would mean changing JDT LS, which is out of the endpoint's scope.
5. **The soak runs outside the gate,** as decided in advance: `mise run test:soak` for 10 minutes, with the gate running the same scenario for about a minute. Chris decides whether the long one joins the gate.

## For Chris's review

- **JDT LS's cancel limitation** (above): `textDocument/definition`, `documentSymbol` and other handlers that call `waitForLifecycleJobs` keep a JDT LS thread (from the common `ForkJoinPool`) until the life-cycle jobs end, even after `$/cancelRequest`. With a long-running document job, those requests pile up in JDT LS, in every worktree. It's worth reporting upstream: `CancellableProgressMonitor extends NullProgressMonitor`, and `ProgressReporterManager.monitorFor` replaces that.

## Review

The cross-agent review (`.context/planning/T002.11_agent_review.md`) had three findings. The governor settled them in `8438dcd`: design §11's "T002.11's details" is approved, with the review's three changes, and T002.11.md's items are amended.

- **R1: fixed.** A request waiting in the queue was answered only when a worker reached it. If every worker stayed busy, a queued request with `timeoutMs: 1000` waited as long as they did.
  - Now `HttpApi` knows each route's default (`route(method, path, timeoutDefaultMs, handler)`, registered by every operation that takes `timeoutMs`). It reads a request's own `timeoutMs` from its body, else uses that default. When a request is queued, one timer thread (`fractal-endpoint-queue-deadline-1`, a `ScheduledThreadPoolExecutor` that only completes futures) is set for its deadline.
  - Whichever comes first, a worker or the deadline, claims the request (an `AtomicBoolean`). At the deadline the request is taken out of the queue (`ThreadPoolExecutor.remove`) and answered with the existing `busy` problem, "The request waited N ms for a worker thread, past its timeoutMs of M, so it wasn't run.", with `retryAfter: 1`. That problem is now `HttpApi.waitedForAWorker`, shared with `WorktreeOps.refuseIfExpired`. A worker that reaches a request already answered does nothing.
  - `worktrees/list` takes no `timeoutMs`, so it gets no queue deadline, as before. The lifecycle routes never queue.
  - The test, `HttpApiTest.aQueuedRequestIsAnsweredAtItsDeadlineAndNeverRun`: every worker is held, then two requests are queued, one with `timeoutMs: 500` and one with none, on a route whose default is 800. Each must be answered `busy` at about its deadline, with `retryAfter: 1`, and its handler must never run, even once the workers are free. It failed first, on the code before the fix, with the new route overload in place but doing nothing more (`temp/t002.11/review-r1-before.log`):

  - The description's `busy` now says a request still queued when its `timeoutMs` passes is answered then, and won't be run.
- **R2: fixed in the design and the evidence, no code (the limitation is accepted, as the governor decided).** The review is right that a handler waiting in `waitForLifecycleJobs` is abandoned, not stopped, and that abandoned handlers could outlast the pool's bound. What bounds it, from JDT LS 1.63.0's bytecode (the classes extracted to `temp/t002.11/jdtls-classes/`), and a check, is now in design §11's limitation bullet:
  - **One job.** The family has a single job, "Validate documents" (`BaseDocumentLifeCycleHandler$1`, its `validationTimer`). The other six classes that name the family only join it.
  - **Only for open documents.** It's scheduled by `triggerValidation`, which `didOpen` and `didChange` call, and which `ClasspathUpdateHandler` and `WorkspaceDiagnosticsHandler` call only for primary working copies.
  - **None in HTTP mode.** The endpoint never sends document notifications. The passthrough refuses them all, `java/validateDocument` and `java.project.refreshDiagnostics`. The endpoint makes no working copy. JDT LS's other four primary working copies are made and discarded within one call.
  - **Checked:** no fixed point in the gate's suite (373 that joined jobs) or the soak (1,731) joined "Validate documents", and no log names it. In the soak, the 1,378 `definition` and `outline` requests, which join the family, never timed out.
  - So abandoned handlers don't pile up outside the test hold, and there was nothing to stop for.
- **R3: rejected, by the governor's decision.** `timeout` has no `retryAfter`: the endpoint has no basis for an estimate, and the problem's hint already says to send it again with a larger `timeoutMs`, or narrower.
