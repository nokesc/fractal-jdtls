## What was built

- **The eight navigation operations** of the description, `definition`, `references`, `implementations`, `type-hierarchy`, `call-hierarchy`, `outline`, `symbols` and `describe` (`NavOps` for the routes, `Navigation` for the answers). Each runs as `problems` does, through the new `CodeRequest`, which `ProblemOps` now uses too: it waits for a worker, JDT LS's start and a worktree change, never past its deadline; maps the module with every check; runs the fixed point for the worktree, with its fast path; reads the answer under the worktree's read lock; and reports `sync`.
- **Resolving names and text anchors** (`Targets`, with `NameSyntax` for the `JavaName` syntax and `TextAnchors` for matching text), with every addressing error of the catalogue: `invalid-name`, `type-not-found`, `member-not-found`, `package-not-found`, `ambiguous-member`, `ambiguous-type`, `text-not-found`, `text-not-unique`, `file-not-found`, `file-in-other-module`, `not-java-source` and `not-applicable`. Library and JDK names resolve on the requesting module's classpath for these read-only operations.
- **Answers in the caller's terms** (`Locations`): Java names, the module, the file relative to it, 1-based lines and columns, the source line (cut at 500 characters), or `library` (the jar, or `jrt:/<module>`).
- **Engines.** JDT LS's LSP handlers through the in-JVM client for definition (text anchors), references, implementations, subtypes and the outline; JDT directly where a handler can't express the contract, each reason in the design's new proposal and summarized under "Decisions for review". `LspClient.call` cancels a request with `$/cancelRequest` at the request's deadline. `initialize` now asks for hierarchical document symbols.
- **The fixture** grew `Names` (four `describe` overloads, a constructor, a field, `normalize`, the nested `Names.Inner`), the interface `Step` with `EchoStep` (harness-contract) and `PrintStep` (harness-app), and `Greeter` (harness-app), so calls cross modules: `PrintStep#run` calls `Greeter#greet` and `Names#describe(ExecutionId)`, and `Greeter` calls `Names#normalize`. Its POMs stay `pom.xml.fixture`, unchanged.
- **Tests:**
  - JUnit: `NameSyntaxTest` (the syntax, and where invalid names break) and `TextAnchorsTest` (exact text, CRLF, other whitespace, closest lines, `select`); `DescriptionTest` lists the new routes. 75 endpoint tests in all.
  - Integration: `test_navigation.py`, through HTTP only (29 tests): every operation, JDK and Maven names, every addressing error with its corrected request, and the same requests in main, wt-a and wt-b.
- **The contract** (`openapi.json`): the scope of references, implementations, subtypes and callers from a `pom` module; outline lines; what `javadoc` and `members` hold; when `ambiguous-type` arises; the closest lines `text-not-found` quotes; the `ExecutionId` example's members made the real answer.
- **A log line** in `DiskSync`'s listener: when a change seen inside Eclipse, outside a fixed point, clears a worktree's mark, the endpoint log names the change and the thread. It found the observation under "For Chris's review".

## Decisions for review

Three `[REVIEW HERE]` proposals in design §11 "Navigation and search":

1. **Which engine answers each operation.** JDT LS's handlers through the in-JVM client wherever the target has a position in the worktree's sources: definition from a text anchor, references, implementations, subtypes (with an item made from the type's JDT handle) and the outline. JDT directly, each because the handler can't express the contract:
   - a name's definition is the declaration it resolved to;
   - library and JDK targets (references by JDT search, implementations by a JDT type hierarchy), which may have no source and so no position for a handler; library signatures always from JDT's model, so a JDK with or without `src.zip` answers the same;
   - supertypes, by `IType.newSupertypeHierarchy`: `typeHierarchy/supertypes` left out `java.lang.Object` and `java.lang.Record` in the first run, because JDT LS gives a library type a location only for a client that opens `jdt://` class files;
   - the call hierarchy, by `CallHierarchyCore`, the handler's own engine: the handler finds each item's element again from its URI and position, so a library callee without source would lose its Java name;
   - `symbols`, by a JDT declaration search of the worktree: `workspace/symbol` finds only types (methods only with a client setting), never fields, and searches every worktree;
   - `describe`'s Javadoc from `JavadocContentAccess2.getMarkdownContent`, which the hover uses: the hover itself, in the first run, ended with `Source: *[wt-a.harness-contract](file:///…/Names.java#5)*`, an Eclipse project name and a file URI, which the contract never shows.
   - `initialize` asks for hierarchical document symbols, so the outline nests.
2. **The search scope and type ambiguity.** "The module and the modules that depend on it" is the requesting module's project and every Java project of the worktree whose resolved classpath requires it; a `pom` module such as `.` covers every module in its folder. A type two modules declare is the requesting module's, else the one on its classpath, else `ambiguous-type`. A name without `#` is a type first, then a package.
3. **Text anchors, exactly:** matching in JDT's buffer, line breaks, `select`, `codeSelect`, the whitespace candidates and the closest lines.

Documentation gaps found:

- The task says names resolve "scoped to the requesting module and the worktree modules that depend on it"; design §11 says types come from the worktree's sources, and the contract that references cover the module and its dependents. I followed the design: names resolve in the whole worktree (so a harness-app request can name a harness-contract type), and searches are scoped to the module and its dependents. Proposal 2 writes this down.
- Neither the design nor the contract said what a `pom` module such as `.` covers, or how a library element's signature is written; proposals 1 and 2 do.
- A record's implicit members (its canonical constructor and accessors) aren't in JDT's model, so `describe` doesn't list them, and they can't be named. The contract's example listed them; it now shows the real answer, and `members` says so.

## Review

The cross-agent review (`.context/planning/T002.06_agent_review.md`) found six bugs. All six were valid and are fixed; the governor settled the rules for R2 and R3 in design §11 (commit 0005377) before the fixes. Each fix has a test that failed on the reviewed code, shown below, and passes now.

- **R1: fixed.** A library method's implementations were matched with `IType.findMethods`, which compares parameter types as declared, so `ByLength#compare(String,String)` in a class implementing `Comparator<String>` wasn't an implementation of `java.util.Comparator#compare`. Now each same-named method of a subtype is checked with JDT's bindings, made in one batch in the subtype's project (`ASTParser.createBindings`), and `IMethodBinding.overrides`, which applies the type arguments. Public JDT API; JDT's internal `MethodOverrideTester` is in a split package with a mandatory attribute, so it wasn't used. Test: `test_review_r1_a_library_method_implemented_with_type_arguments`.
- **R2: fixed.** A qualified parameter type matched any type whose name ended the same way (`a.Date` matched `b.a.Date`). Now a qualified parameter type matches only that type, as the §11 rule now says, and a simple one the last segment. A partly qualified name such as `Map.Entry` is qualified, so it no longer matches `java.util.Map.Entry`. The comparison moved, unchanged at first, into `NameSyntax.Param.matches`, so it's unit-tested. Test: `NameSyntaxTest.aQualifiedParameterTypeMatchesOnlyThatType`.
- **R3: fixed, by the §11 rule the governor changed.** A name without parentheses is the field if the type declares one; a method that shares a field's name is written with its parentheses. So `Sizes#size` is the field and `Sizes#size()` the method, and every candidate resolves. The description says so in `JavaName` (all 10 copies of its text), in `ambiguous-member`'s catalogue entry, and in that entry's example's description. The example itself, the four `Names#describe` overloads, is still right: `Names` has no field of that name. Test: `test_review_r3_a_field_wins_a_name_without_parentheses`, both directions.
- **R4: fixed.** `text-not-unique`'s `within` candidates counted occurrences by their nearest declaration, so for `public class Twice { public Twice() { } }` and text `Twice` it offered `Twice`, whose range holds both occurrences. Now each candidate declaration's name is first resolved back to it in that file, then offered only if the text occurs exactly once in its whole source range (`TextAnchors.onceWithin`). Tests: `test_review_r4_every_within_candidate_resolves`, which applies every candidate offered and expects a definition, and `TextAnchorsTest.aWithinIsOfferedOnlyIfTheTextOccursOnceInItsWholeRange`.
- **R5: fixed.** The signature scanner ended a field at a comma inside type arguments (`public Map<String, Integer> entries` became `public Map<String`). Now `<` and `>` outside parentheses count as type arguments: in a declaration, before any initializer, they can be nothing else. Inside parentheses, such as an annotation's arguments, they're left alone. Tests: `LocationsTest` (fields, nested type arguments, generic methods, a multi-field declaration, an annotation with `<`) and `test_review_r5_a_generic_fields_signature_keeps_its_type_arguments` (`describe` and the outline).
- **R6: fixed.** After a match, the text search skipped the match's length, so overlapping occurrences were missed: `a.a` occurs twice in `a.a.a`, and the anchor was accepted as unique. Now every start position is tried, and the search for occurrences with other whitespace does the same. Test: `TextAnchorsTest.overlappingOccurrencesAllCount`.

The integration checks for R1, R3, R4 and R5 use three files the story writes into wt-a only: `ByLength` (harness-app), `Sizes` and `Twice` (harness-contract). The committed fixture is unchanged.
