## What was built

- **`.github/workflows/release.yml`** (design §9) runs on a pushed `v*` tag. It is one job on `ubuntu-24.04`, with `contents: write` and a 45-minute timeout. Its steps are in the design's order:
  1. Check out the tagged commit (`actions/checkout` v7.0.1, pinned by SHA, without keeping credentials).
  2. Install the repository's own toolchain from `mise.toml`: `jdx/mise-action` v5.2.5, pinned by SHA. It is pinned to mise `2026.9.5`, the version used locally, and caches nothing. `MISE_TRUSTED_CONFIG_PATHS` trusts the checkout's `mise.toml`.
  3. `mise run setup`.
  4. **Check the tag:** `mise run release:check-tag -- "$TAG"`. It fails unless the tag is `v` plus `pin.json`'s `release` and the release notes exist. It writes `release`, `zip` and `notes` to `$GITHUB_OUTPUT`.
  5. **Build:** `mise run release:zip`.
  6. **Run the gate:** `mise run validate`, the same gate as locally. In CI it starts with no Maven cache and no stray `/tmp/.git`.
  7. Show the zip's SHA-256 and file list.
  8. **Create a draft release:** `gh release create "$TAG" --draft --verify-tag --title "fractal-jdtls <release>" --notes-file .github/release-notes/<tag>.md`.
  9. **Attach the zip:** `gh release upload`.
  10. **Publish:** `gh release edit --draft=false`.

  With immutable releases on, publishing locks the release and its asset, which is why the zip is attached to the draft first. The tag reaches the shell scripts only through `env`, never by `${{ }}` inside a `run:` script.
- **`tools/release_tag.py`** is the tag check, run as the new mise task `release:check-tag`. `tests/unit/test_release_tag.py` has 10 tests:
  - a matching tag;
  - six mismatched tags (`v9.9.9-1`, `9.9.9-2`, `v9.9.9`, `v9.9.9-2-rc1`, `V9.9.9-2` and an empty one);
  - missing notes;
  - this repository's own release having notes;
  - the `$GITHUB_OUTPUT` lines.
- **Release notes: [`.github/release-notes/v1.63.0-1.md`](../../../.github/release-notes/v1.63.0-1.md).** This is the file the workflow passes as the release's body (`--notes-file`); a missing file fails the tag check. It covers:
  - what's pinned: JDT LS 1.63.0 and its tarball SHA-256, m2e core, m2e jdt and embedded Maven versions, Byte Buddy 1.18.14 and its SHA-256, and Java 21 or newer;
  - what the zip holds and what is downloaded;
  - what was tested together;
  - how each file is trusted, from the pin report. 58 of 110 `plugins/` jars and the `features/` jar are Eclipse-signed, and 41 jars are byte-identical to Maven Central. **29 jars, including all of m2e, and 13 other files are trusted only through Eclipse's SHA-256**, and Eclipse publishes no PGP signature. **Byte Buddy's PGP signature wasn't checked**, because the key `7999BEFBA1039E8B` wasn't in the keyring.
  - the known gaps: runtime workspace-folder changes, the agent needed on every start, unique worktree folder names, version-pinned hooks, and Linux only;
  - where to report a problem.
- **README:**
  - **Install:** prerequisites (Linux, Python 3.10 or newer, Java 21 or newer, network while installing); download, unzip and `install.py`; the root and `--root` / `FRACTAL_JDTLS_ROOT`; `--verify`; uninstalling.
  - **Use:** a symlink onto `PATH` or a client command; the drop-in options; how Java is chosen; the default `-data`; the check at launch; what the agent does; the "fresh `-data`" rule; unique folder names; what belongs to the client.
  - **Known gaps** (extended), **Report a problem** (GitHub issues, and what to include), and **Development**.
- **AGENTS.md** describes `.github/`, `tools/release_tag.py`, `mise run release:check-tag`, the release flow and the actionlint command.

## 4. For Chris: tagging, and immutable releases

The agent didn't tag, push or publish anything. The tagged commit must contain this branch's work, including the workflow and `.github/release-notes/v1.63.0-1.md`, so merge the branch into `main` first, however you prefer.

**First, turn on immutable releases**, before the tag, so v1.63.0-1 is the first immutable release:

1. Open <https://github.com/nokesc/fractal-jdtls/settings> (the repository's **Settings → General**).
2. In the **Releases** section, tick **Enable release immutability**. It applies to releases published after it's turned on; drafts stay editable until they're published.

Also check **Settings → Actions → General**: Actions must be allowed to run. The workflow asks for `contents: write` itself, so the default read-only "Workflow permissions" is enough, unless an organization policy forbids raising it.

**Then tag and push.** Run these from a clone of `main` after the merge:

```bash
git switch main
git pull --ff-only origin main
mise run release:check-tag -- v1.63.0-1        # the workflow's first check, locally
git tag -a v1.63.0-1 -m "fractal-jdtls 1.63.0-1 (JDT LS 1.63.0)"
git push origin v1.63.0-1
```

Use `git tag -s` instead of `-a` if you sign tags.

Pushing the tag starts **Release v1.63.0-1** under the repository's Actions tab. The release appears published only after the gate passes; if any step fails, nothing is published. A draft release left by a failure in the attach or publish step can be deleted, and the workflow re-run.
