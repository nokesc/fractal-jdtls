## What was done

- **`OperationFolder`** (new, plain Java):
  - The ID is `<UTC time to the millisecond>-<8 random hex digits>` (`SecureRandom`), for example `20261109T103728.039Z-71b69ffb`. The time is the request's arrival.
  - `create` tells the in-flight entry the ID first. It checks with `Edits.inside` that the folder's real path is in the worktree's real root, before and after making `temp/fractal-jdtls/` (`edit-outside-worktree` otherwise, nothing made outside). Then it makes `<id>/` exclusively, with a new random part on a clash.
  - It writes `request.json` (`id`, `received`, `operation`, `request`, the body as received; the token is a header and never in it), then `diff.patch`. Each is created once (`CREATE_NEW`). Last comes `response.json`, written as `.response.json.tmp` and moved into place with `ATOMIC_MOVE`.
- **`CodeRequest.edit`:**
  - Once the mapping has found the worktree and module, it sets the ID on the `InFlight` entry and makes the folder with its `request.json`.
  - Then the first fixed point and the edit; `diff.patch` is written right after, before any source write.
  - Then `expectWriteSetDigest`'s comparison, made also when the edit changes nothing (`edit-changed`, nothing written), then the dry run, or the apply as before.
  - Every outcome is written to `response.json` as the caller gets it: the answer, a problem, or the `internal` problem, through the new `HttpApi.problemJson`. Only then does the `InFlight` entry close.
  - A successful answer gains `operation` and `operationFolder`.
- **`writeSetDigest`** (`Edits.writeSetDigest`, in every refactoring's answer): a SHA-256 over the prepared writes `Edits` hands to `EditWriter`.
  - First comes the number of entries; then for each file operation, in plan order, its kind, its path relative to the worktree, `from` for a rename, and its new bytes, except for a delete.
  - Every field is framed by its length as 8 bytes, big-endian.
- **`EditOps`** reads `expectWriteSetDigest`: optional, 64 lowercase hex digits, else `invalid-request`.
- **`InFlight`:** each entry has `path`, the route's path, which was named `operation` before; a refactoring also has `operation`, its ID.
- **`FileRecords.skipped`** also skips a folder `fractal-jdtls` whose parent is `temp`.
- **`DiskSync.filterOperations`** (new, see "Failures corrected"; **removed in the review's follow-up**, see "Review"): a resource filter on the worktree root project's `temp` folder that excludes `fractal-jdtls`, so Eclipse's view skips the folders too.
- **`EditWriter`:**
  - The create fix: the file is created (`CREATE_NEW`), its undo is journaled, and only then are its bytes written.
  - The bytes now go through an `Output`, which a test can make fail partway.
  - A hook runs once after the first file's step: the new test pause `after-first-write`.
- **The contract:**
  - `EditResult` gains `operation`, `operationFolder` and `writeSetDigest`, all required; each refactoring request gains `expectWriteSetDigest`.
  - Each refactoring's description has the operation folder and the dry-run check, and its errors list `edit-changed`.
  - The catalogue gains `edit-changed` (409) with its example and hint. `Error` gains `diff` and `writeSetDigest`, and `edit-outside-worktree`'s description names the operation folder.
  - `InFlight` gains `path` and the ID.
  - Every refactoring example was replaced with a real answer, from a `test_refactoring.py` run of this code (paths shortened to `/work`). `edit-changed` and the in-flight refactoring are also real: the latter is a new `/v1/status` example, "refactoring". A new rename request example, "checked", sends a dry run's real digest.
- **Tests:**
  - JUnit: `OperationFolderTest` (6 tests: the ID, the files and their order, a linked `temp`, the record's skip, the digest's framing with an independently computed vector, and the in-flight entry), `EditWriterTest.aCreateWhoseWriteFailsPartwayIsUndone`, and `DescriptionTest` (43 codes).
  - Integration: `tests/integration/test_operation_folders.py` (11 tests on one story, then a second JDT LS on the same `-data`).
  - `test_refactoring.py`'s file hashes leave out the worktree's `temp/`, and `test_imports.py` reads `inFlight[].path`.
- **The fixture's `.gitignore`** ignores `temp/`.
- **Docs:** AGENTS.md mentions the folders, `OperationFolder`, the filter, the new pause and `test_operation_folders.py`. Design §11 has one `[REVIEW HERE]`, "T002.10's details".

## Decisions for review

The governor approved these in `2f0978f`, except item 1, the Eclipse filter, which is removed ("Review").

All of these are in design §11's `[REVIEW HERE]` "T002.10's details":

1. **Eclipse's view skips the folders too:**
   - A resource filter on the worktree root project's `temp` folder excludes its child folder `fractal-jdtls` (folders only, not inherited).
   - It's made at the first full fixed point that finds `temp/` a real folder, before that fixed point's refresh. The files are recorded again after it, because it changes the root project's `.project`.
   - Its cost: one full fixed point per worktree, at its first refactoring, 112.8 ms in the gate.
   - Without it, every fixed point after a refactoring was a full one.
2. **`/v1/status`'s `inFlight[].operation` is renamed `path`,** and `operation` is now a refactoring's ID, the name its answer uses for it. It's a change to the 1.0.0 description, which hasn't been released.
3. **When the folder is made:** after the waits and the mapping. A request refused before them, or by them, has no folder.
4. **What the files hold:**
   - `request.json`'s fields, and `diff.patch` equal to the answer's `diff`.
   - `response.json` is the body sent, the `internal` problem included.
   - A `diff.patch` that can't be written fails the request before any source write. A `response.json` that can't be written is logged, and the caller still gets the answer.
5. **The digest's framing** is as described under "What was done". `expectWriteSetDigest` must be lowercase hex, and it's compared on a dry run too.
6. **`edit-changed` carries `diff` and `writeSetDigest`.**
7. **The test pause `after-first-write`**, in `EditWriter`.

## For Chris's review

The first two points were about the filter, which is removed; the point that replaces them is under "Review".

- **A worktree's first refactoring pays one full fixed point,** to make the filter on `temp` (112.8 ms on the fixture). If the worktree's `temp/` already exists when it's added, the filter could be made then, and the cost would go. I didn't build that: it's one more step in the add path, and the task asked for the minimum.
- **The filter lives in the root project's `.project`,** like the `.git` filter. `.project` is git-ignored in the fixture; a real project that commits `.project` would see the new filter in `git status`. The `.git` filter already does this.
- Nothing else seemed to need more than the design gives.

## Follow-up

The governor's follow-up (`temp/governor/T002/T002.10-followup2.md`, design commit `a28e63f`): the operation folder, with its `request.json`, is now made right after the request's first fixed point, not before it. That fixed point stays on its fast path. The ID still goes on the in-flight entry before the folder exists (`OperationFolder.create` tells it first).

- **The change, in `CodeRequest`:**
  - `edit` no longer makes the folder before the fixed point.
  - `refactor` runs the first fixed point, with the edit computed in it as before, then makes the folder and writes `request.json`, then `diff.patch`, and the rest as before.
  - The description's six refactoring texts now say the folder is made once the request's first fixed point is done.
- **A refusal still leaves its folder.** The edit is computed inside that fixed point, under its read lock, but T002.10's acceptance item still requires a `refactoring-refused` request to leave `request.json` and `response.json`. Design §11's list of requests without a folder doesn't include JDT's refusals either.
  - So a `Problem` that the computation answers (a JDT refusal, an addressing error) is held until the fixed point is done. The folder is then made with `request.json`, and that problem is the answer, recorded in `response.json`.
