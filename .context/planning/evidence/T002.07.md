## What was built

- **The six refactorings** of the description (`EditOps` for the routes, `Refactorings` for the edits): `refactor/rename` (a type with its file, a method, a field, a local variable or parameter, a type parameter, a package with its folder), `refactor/organize-imports`, `refactor/extract-variable`, `refactor/extract-constant`, `refactor/extract-method` and `refactor/inline-variable`. Every choice JDT LS would ask for is a request field: `newName`, `name`, `replaceAll`, and organize imports' `choices`.
- **Engines** (design proposal "Which engine computes each refactoring"): JDT LS's `RenameSupport` with its handler's flags and `ChangeUtil`'s conversion to a `WorkspaceEdit`; JDT LS's `OrganizeImportsHandler` with a chooser that answers from `choices`; JDT's LTK refactorings (`ExtractTempRefactoring`, `ExtractConstantRefactoring`, `ExtractMethodRefactoring`, `InlineTempRefactoring`) with the requested name set before the change is made. Extract method's name arrives in the one edit, against one baseline (D6): the governor's preferred option.
- **Applying edits, as the client** (`CodeRequest.edit`, `Edits`, `EditPlan`, `EditWriter`, `UnifiedDiff`, `DiskSync.apply`):
  1. the fixed point, with its fast path;
  2. under the worktree's read lock, the edit computed; every file it names checked to be in the worktree (`edit-outside-worktree`); each file it changes read once, in its charset with its BOM kept aside, and required to be exactly what JDT computed from (else `files-changed`); the `documentChanges` worked out in memory, in order, text edits, creates, renames and deletes, into each file's new bytes and the unified diff;
  3. with `dryRun`, the diff; otherwise the apply, one more fixed point: under the worktree's write lock and the workspace root rule, each file the edit reads checked against its baseline (the record of the first fixed point, the bytes, `isSynchronized`) and each file it creates checked to be still absent (else `files-changed`, nothing written); every file written, all or none (a failure puts every written file back: `write-failed`); then the refresh, the build and the join; then the worktree's problems read under the read lock. `sync` is the first fixed point and `syncAfter` the apply's (`notSkippedBecause: edit-applied`).
- **Errors:** `files-changed`, `refactoring-refused` and `not-applicable` (JDT's own reason quoted), `declared-in-other-module` (its candidate sets `module`, and `target` too when the target was an anchor in the other module's file), `ambiguous-import`, `edit-outside-worktree`, and the new `write-failed`. `Targets.range` resolves a text anchor to a range without `codeSelect`, for the extracts.
- **The contract** (`openapi.json`): `write-failed` in the catalogue, with its example, in every refactoring's 409; `EditResult.warnings` (JDT's warnings); `applied: false` for an edit that changes nothing; the apply described as one fixed point, all or nothing, files keeping their charset, BOM and line separators; `phase: applying`; a renamed field's getter and setter, and a renamed package's folder; organize imports' error list made a list; every refactoring's request and response examples replaced by the real ones of the integration run (the old ones described a `Greeter` the fixture doesn't have).
- **A test-only mechanism**, `TestPauses` (`-Dfractal.jdtls.endpoint.testPauses=<folder>`, which the launcher never passes): a test arms a point, and the next refactoring waits there until the test lets it go, so the integration suite can change a file between the computation and the apply, or make one unwritable between the apply's check and its writes. Documented in AGENTS.md beside the other test-only mechanisms.
- **Tests:**
  - JUnit: `EditPlanTest` (LSP edits applied in order, CRLF and lone CR, UTF-16 units, strictness, a type rename, JDT LS's package rename through its `.temp` file), `UnifiedDiffTest` (hunks, context, created/deleted/renamed files, missing newlines, CRLF, the edit script on 200 random pairs), `EditWriterTest` (all written and the emptied folder removed; a read-only file making the last write fail, and every file put back to its exact bytes and inode, the moved file to its old path, the deleted one restored, the made folder removed; never replacing a file that appeared), `EditsTest` (reading a `WorkspaceEdit`, and files outside the worktree or not on disk); `DescriptionTest` lists the new routes and code. 98 endpoint tests in all.
- **AGENTS.md:** the class map, the story and the test pauses.
- **Integration story** (`tests/integration/test_refactoring.py`, 8 tests, HTTP only). One JDT LS on the fixture's main checkout and two linked worktrees. `Lists.java` (it uses `List`, imports an unused `Map`) is written to wt-a and wt-b before the start. Every refactoring then runs in wt-a, while wt-b holds the same code: as a dry run (wt-a's hashes checked unchanged), applied, and followed by a `build`. Next come JDT's refusals (wt-a unchanged after each), the two races and a clean build. main, wt-a and wt-b are hashed before and after the story.

## Decisions for review

Each is in design §11 "Refactorings and edits" behind `[REVIEW HERE]` (4 markers), or in the contract, whose change is part of this commit.

1. **Engines: JDT LS's and JDT's own engines, called directly, not their LSP handlers** (design marker 1). Rename is `RenameSupport` with the `textDocument/rename` handler's flags (49: references, and a renamed field's getter and setter) and `ChangeUtil`'s conversion. Organize imports is `OrganizeImportsHandler.organizeImports` with a chooser that answers from `choices`. The four extract and inline refactorings are LTK's `ExtractTempRefactoring`, `ExtractConstantRefactoring`, `ExtractMethodRefactoring` and `InlineTempRefactoring`, with the requested name set before the change is created. This is the governor's preferred option for D6: the name arrives in the one edit, checked against one baseline, with no second rename. Why: each handler drops something the contract needs. `java/getRefactorEdit` always names the result `extracted`, checks only the initial conditions, and returns nothing when they fail, with no reason. The rename handler accepts any rename JDT rates below FATAL. Organize imports' LSP command asks the client to choose an ambiguous import, which an HTTP request can't answer mid-call.
2. **A rename is refused on any ERROR, not only FATAL** (design marker 1). JDT LS's handler refuses only a fatal status, so a method clash (`pad`→`describe`, an ERROR) would be written. The endpoint refuses every error as `refactoring-refused`, quoting JDT, and returns JDT's warnings in a new `EditResult.warnings` field. `RenameSupport.preCheck()` isn't called: for an element-created support it throws a NullPointerException (its pre-check status is null), so the full condition check is used instead.
3. **`not-applicable` versus `refactoring-refused`** (design marker 1). An error in the initial conditions, which concern the selection, is `not-applicable`; an error in the name's check or in the final conditions is `refactoring-refused`. Both quote JDT's sentences, with `/<project>/` turned into `<module>/` so the message is in the caller's terms.
4. **The baseline is the fixed point's record plus each affected file's bytes, which must equal JDT's buffer** (design marker 2), rather than the spike's hash of every file. Its cost is measured below. The file record costs nothing more than the fixed point already does (105–293 ms on the large tree), hashing every file would add 134–467 ms per refactoring, and the check at apply time took 0.12–0.43 ms on the fixture.
5. **The apply is one more fixed point, `DiskSync.apply`** (design marker 2). It holds the worktree's write lock and the workspace root rule from the baseline check through the writes, the refresh, the build and the join, and the problems are then read under the read lock. `syncAfter.notSkippedBecause` is `edit-applied`. The deadline is checked once, just before the writes (`timeout`, `phase: applying`, nothing written). After the writes the apply isn't cancelled, so the answer always reports what was written.
6. **All or nothing, and the new code `write-failed`** (design marker 3; contract: catalogue entry, example and each refactoring's 409). In-place writes keep the inode, owner and permissions. A rename moves the file first and never over an existing file. Creates use `CREATE_NEW`, deletes keep the bytes and permissions to restore, and a package folder the edit empties is removed, never a module's or source folder. Every step is journaled and undone newest first on failure. A file whose bytes aren't valid in its charset is `refactoring-refused`, not written with replacement characters.
7. **An edit outside the worktree is `edit-outside-worktree`, not `internal`** (design marker 4). The contract, written after the task file, already gives it this code (422, with `files`). The task said `internal`.
8. **An edit that changes nothing isn't applied** (contract: `EditResult.applied`). This is `applied: false` with no `syncAfter`, as shown by the second organize imports.
9. **A test-only mechanism, `TestPauses`** (`-Dfractal.jdtls.endpoint.testPauses=<folder>`, documented in AGENTS.md, never passed by the launcher). It lets the integration suite place a change exactly between the computation and the apply (`before-apply`), or between the apply's check and its writes (`before-write`), deterministically, with no timing. Without the property it is one `System.getProperty` per refactoring.
10. **The licensing unit test skips `temp/`.** The first gate failed because `test_licensing.py` walked the governor's git-ignored `temp/governor/` scripts. `temp/` now joins its skipped folders, with a comment. The governor's files weren't touched.
