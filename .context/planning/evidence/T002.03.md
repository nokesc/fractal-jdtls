## What changed

- **`endpoint/`, the bundle's Maven module** in the root POM, producing `endpoint/target/fractal-jdtls-endpoint.jar`, package `org.fractal.jdtls.endpoint`, `--release 21` from the root POM. The manifest is hand-written (`src/main/manifest/MANIFEST.MF`): `Bundle-Activator`, `Require-Capability` Java 21, and `Import-Package` only: `com.google.gson` and `com.google.gson.stream` `[2.11,3)`, `com.sun.net.httpserver`, `org.eclipse.jdt.ls.core.internal` and `org.osgi.framework` `[1.10,2)`. The jar holds the endpoint's classes and `openapi.json`, nothing else.
  - **Ported from the spike, as the governor asked:** `HeapPipe` unchanged but for its timing fields; `LspClient`'s framing over Gson and its answers to JDT LS (decision D8, below); the activator's stream swap and `initialize`; the HTTP server on `127.0.0.1`, port 0, and the atomic port file.
  - **New:** `Config` (the launcher's `-Dfractal.jdtls.http.*`), `Token` (the pipe), `Settings` (the fixed settings, in nested and dotted forms), `Description` (the served contract, which is also the error catalogue at runtime), `Code` and `Problem` (RFC 9457), `Gate` (token, `Host`, `Origin`), `HttpApi` (routing, body limit, problems, `internal`), `StreamCheck` (the identity check, the one class that touches JDT LS internals), `Fatal` (stderr and `halt(1)`), `Endpoint` (startup, status, shutdown), `PortFile` and `Log`.
  - **Routes:** `GET /v1/status` (with `wait=ready&timeoutMs=`, answered without holding a worker thread while it waits), `GET /v1/openapi.json` (the bundled bytes as they are) and `POST /v1/shutdown` (202, then LSP `shutdown` and `exit`, started only after the response is sent). Every other path is `route-not-found`, as the governor decided; a known path with another method is `method-not-allowed` with `Allow`.
- **The build cache, `tools/jdtls_cache.py`.** It downloads the pinned tarball once into `.cache/jdtls/<SHA-256>/` (git ignores `.cache/`), checking the tarball's SHA-256 before unpacking and every file after, then renames it into place; every build verifies the folder against `pin.json` again (every file, nothing missing or extra) before Maven runs, in 0.24–0.25 s. It reuses `bin/install.py`'s pin, download, unpack and scan, so the two can't drift. `mise run build` runs it before Maven. The endpoint's POM names the jars it compiles against as system-scoped dependencies under that folder, so Maven reads them in place and never copies them into `~/.m2`.
  - **Not shared with the integration suite's tarball:** the suite installs with the shipped `install.py`, which downloads for itself and has no option to use a local tarball. Adding one to the shipped installer is beyond this task, so the suite still downloads the tarball once per session.
- **The release zip and the installer:** `lib/fractal-jdtls-endpoint.jar` is in `install.py`'s `HASHED_FILES` and `release_zip.py`'s `SOURCES`, so `release-files.json`, `--verify` and the launch check cover it ("this release's own 8").
- **The launcher's HTTP mode (`bin/jdtls`),** only with `--http-port-file`:
  - `--http-port-file` and `--http-settings`, made absolute against the working directory; the port file's folder must exist, the port file can't be in the install, and one left from an earlier run is removed; the settings file must be readable. `--http-settings` without `--http-port-file` is a usage error.
  - `FRACTAL_JDTLS_HTTP_TOKEN`: required, 32 to 4,096 visible ASCII characters, never printed. The launcher writes it into a pipe, closes the write end, marks the read end inheritable, and `exec`s Java with `os.execve` and an environment without the variable. The descriptor's number is `-Dfractal.jdtls.http.tokenFd`.
  - The JVM options, after the client's: `-Dosgi.bundles=<the install's eclipse/config_linux/config.ini start list, read with Java-properties rules>,reference:file:<release>/lib/fractal-jdtls-endpoint.jar@4:start`, `-DwatchParentProcess=false`, `-Djava.import.generatesMetadataFilesAtProjectRoot=false`, and `-Dfractal.jdtls.http.` `portFile`, `settings`, `log` (`<data>/.fractal-jdtls/<release>/endpoint.log`), `release` and `tokenFd`.
  - Refused `--jvm-arg`s: `-Dosgi.bundles`, any `-Dfractal.jdtls.http.*`, and `-DwatchParentProcess` or `-Djava.import.generatesMetadataFilesAtProjectRoot` with any other value than `false` (the same value is accepted).
  - It checks the Java has the `jdk.httpserver` module (`java --list-modules`), and that the install's path holds no character Equinox's start list can't (`, @ % # ?` or white space).
  - Its checks come before it writes anything, so a refused start creates no `-data`.
  - `--help` documents all of it. Without `--http-port-file` the command line is exactly the plain one, even with the token set.
- **Tests:**
  - JUnit, 36 in `endpoint/`: `GateTest` (token, `Host`, `Origin`, the order, the empty 401), `DescriptionTest` (every registered route is an operation of the description; every `Code` is in the catalogue; problems carry the catalogue's status, title and `retryable`), `HttpApiTest` (a real server on `127.0.0.1` with raw requests: the checks, 404, 405 with `Allow`, status with and without `wait=ready`, `not-ready` with `Retry-After`, query validation, the served description, shutdown answering once and starting only after its response, 413, `internal` with no stack trace and the endpoint still serving), `SettingsTest`, `TokenTest`, `PortFileTest`, `HeapPipeTest` (bytes from threads that have ended, which `PipedInputStream` can't do), `LspClientTest` (`initialize`, a refused `initialize`, a failed check, every answer to JDT LS, framing).

  - Integration: `tests/integration/test_http.py` (16 tests) and its driver `endpoint_client.py`. `launch_without_agent.py` follows `prepare()`'s new return value.

## Decisions for review

In the design, behind `[REVIEW HERE]` in §11:

1. **The token pipe's descriptor stays open** ("Launching"). Java can't close a descriptor by number, so the endpoint reads `/proc/self/fd/<n>` to the end and closes what it opened; `<n>` stays open as an empty pipe whose writer is gone. No child inherits it (the JDK closes descriptors above 2 in children). The token is at most 4,096 characters (the pipe write never blocks) and visible ASCII (it goes into a header).
2. **The port file's lifetime, and the endpoint log's place** ("Listening"): the launcher removes a stale port file before starting; the endpoint removes its own on a clean shutdown; the log is `<data>/.fractal-jdtls/<release>/endpoint.log`; the launcher passes everything as `-Dfractal.jdtls.http.*` and refuses a client's own.
3. **How a startup failure ends the process** ("Listening"): stderr and the log, then `Runtime.halt(1)`; the activator never lets an exception reach Equinox; the launcher checks for `jdk.httpserver`.
4. **A bundle that doesn't resolve** ("Constraints and risks") would start JDT LS on the real stdin, without its client. The checks that make it unlikely, and why the agent doesn't guard it.

My own choices, which don't change §11's meaning:

5. **D8, the in-JVM client keeps the spike's own framing over the pinned Gson,** as the governor allowed: the passthrough (T002.08) forwards params unchanged, each answer to JDT LS is a few lines, and `$/cancelRequest` is one notification, so lsp4j's typed endpoint would add adapters to build and maintain for no gain (HTTP-FINDINGS "Framing"). It's about 300 lines with the answers, and `LspClientTest` covers it.
6. **Ready** means JDT LS answered `initialize`, the stream check passed, `initialized` was sent, and JDT LS reported `ServiceReady`. With worktrees (T002.04), imports will add to it.
7. **`Import-Package` only, no `Require-Bundle`.** Every package the bundle uses is named, which is what the unit test checks. Equinox resolves `org.eclipse.jdt.ls.core.internal`'s `x-friends` export, because JDT LS doesn't run Equinox's strict mode.
8. **Compiling through system-scoped dependencies** on the cache's versioned jar names. Maven reads them in place, and only the jars named are on the classpath. A JDT LS upgrade changes the names, and `test_endpoint_bundle.py` fails until the POM matches `pin.json`. Plain `mvn package` fails, naming the missing jar, until `mise run build` has filled the cache.
9. **The status wait doesn't hold a worker thread:** the response is sent when readiness completes or the timeout passes, so many callers waiting for ready can't use up the pool of 8 workers.
10. **Query parameters** are strict like bodies: unknown, repeated or invalid ones are `invalid-request`, and `errors[].field` names a parameter as a JSON Pointer, `/timeoutMs`. `timeoutMs` without `wait=ready` is invalid.
11. **A body over 1 MiB** is read and dropped up to 64 MiB before the 413, so the caller sees the answer rather than a reset connection.
12. **The 401 says no more than its code:** no `detail` and no `instance`.
13. **JDT LS's requests back to the client** are answered exactly as §11 lists; the spike also answered `workspace/workspaceFolders` and `client/unregisterCapability`, which now get `-32601`, as §11's "anything else" says. Neither was seen in the spike's runs.
14. **The settings file**: the fixed settings are looked for in nested and dotted forms (`{"java.autobuild.enabled": …}`) and refused in any; where the file has none, they're added in nested form; a setting that can't hold them (`"java": "x"`) is refused.
15. **The launcher's extra cost in HTTP mode** is `java --list-modules`, 76 ms (median of 7; `java -version`, which both modes run, is 39 ms).
16. **`X-Fractal-Session`** is logged with each request, cut to 200 printable ASCII characters; the token and `Authorization` header are never logged.
