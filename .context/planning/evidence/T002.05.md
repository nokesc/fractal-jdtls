## What was built

- **The fixed point** (`DiskSync`), for the requesting module's whole worktree, as design §11 "Keeping in step with the disk" says:
  - the fast path: the endpoint's own file record (`FileRecords`) unchanged, every project `isSynchronized`, and the worktree's "no change seen" mark set;
  - else, holding the workspace root rule: the `.git` filter where missing, the record, `refreshLocal` of each project, `IResource.touch` for the files the refresh missed (changes that kept their modification time, and `changedPaths`), changed POMs (by delta and by SHA-256) through m2e's multi-project update, `clean` when asked, and an incremental workspace build;
  - then the join of the jobs scheduled since the rule was taken, and the `sync` report.
- **`POST /v1/build` and `POST /v1/problems`** (`ProblemOps`), as in the description. They wait as `modules/check` does: never past their deadline, for a worker, for JDT LS's start, or for a worktree change. Problems come from markers after the join (`Markers`), with 1-based positions, the source line and the enclosing `JavaName` (`JavaNames`). A timeout cancels the fixed point's Eclipse operations through their progress monitor, and answers `timeout` with its `phase`.
- **Lightweight auto-refresh off:** the launcher passes `-Declipse.pluginCustomization=<release>/lib/http-mode-preferences.ini`, a new release file, and the endpoint refuses to start if the preference is on.
- **The `.git` filter** on each worktree's projects after an add and after a restart's check (deferred from T002.04), and at each fixed point.
- **Retiring the seed:** `.context/spike/http/` is deleted; HTTP-FINDINGS says where its code went and that it remains in Git history.
- **Tests:**
  - JUnit: `SyncPartsTest`, for the file record, positions, `changedPaths` and the new list fields; 66 endpoint tests in all.
  - pytest unit: the launcher's new option and refusals, and the new release file.
  - Integration: `test_http_sync.py` (the story), `test_run05_fresh.py` (2 fresh copies in the gate, 20 in `mise run test:run05`), the large tree's costs in `test_imports.py`'s gate import, and the restart's filter and first fixed point in `test_http_worktrees.py`.

### Changes that keep their modification time

Each started from a `build` that had seen `main/harness-app/.../Launcher.java` as it was. Then:

- **`cp -p`:** a broken copy given the file's own mtime (`touch -r`), then `cp -p` over the file;
- **`touch -r`:** the file kept aside with `cp -p`, edited, then its old mtime restored with `touch -r`;
- **two writes within one millisecond:** the second write's mtime set 1 ns after the first's, inside the same millisecond. That's what such a pair leaves on disk, since a fixed point can't be timed to land between two real writes.

The next `build` reported each, and the error. `before` and `after` are the file's bytes, size, inode, modification time and status-change time just before that `build` and just after it: identical, so the endpoint never touched the file. ## Decisions for review

All are in design §11 behind `[REVIEW HERE]`:

1. **Lightweight auto-refresh is turned off through `-Declipse.pluginCustomization`,** pointing at a new shipped file, `lib/http-mode-preferences.ini`. It's read once as a default and never written to `-data`. The launcher refuses a client's own, and the endpoint refuses to start if the preference is still on.
2. **The mark and the check, exactly.**
   - The fixed point holds the root rule itself from before its refresh until its build ends, so the changes delivered meanwhile are its own: its report, and they don't clear its mark.
   - A worktree with a fixed point still running never takes the fast path (`eclipse-changed`; the description says so).
   - The check reads the record first.
3. **The join waits for Eclipse's `AutoBuildOffJob`,** in the auto-build family, which is joined while it sleeps: up to 148 ms a fixed point. Kept.
4. **The `.git` filter:** an anchored regex with JDT LS's filter flags, but no update flags. It goes on after an add, after a restart's check, and at each fixed point.
5. **Changes that keep their modification time:** the record's scope and fields, taken before the refresh, and `IResource.touch` for every new or changed file the refresh didn't report. The file is never written.
6. **`filesChanged` leaves out JDT LS's own project files,** which it keeps under `-data`: 300 of 301 reported after the large import. They still clear the mark.
7. **The costs,** for review, with no change proposed: the large tree's fast-path check takes 442–623 ms, twice the spike's; refreshes stay under a second.
8. **Reading the markers:** the marker types behind each `kind`, how columns are counted, and what the element is for an import (the file's primary type).
9. **A fixed point's timeout:** its progress monitor is cancelled at the deadline, and the join stops but cancels no job. A caller that disconnects isn't detected, because the JDK's server gives no sign of it. Left for T002.09.
10. **Three more version-pinned internals,** added to "Constraints and risks".

The contract's text changed in two places: `eclipse-changed` covers a fixed point still running, and `filesChanged` says what it finds and what it leaves out.

## Review

The cross-agent review (`.context/planning/T002.05_agent_review.md`, not committed) had four findings. All four were valid, and all are fixed, as the governor's notes (`6d02c39`) settled them. After the fixes, the full gate passed, and so did `mise run test:run05`: 20 of 20 again equal to run 05, with 1 distinct outcome, exits `[0]`, 0 agent errors, and `build`'s sync totals for main 614–756 ms, wt-a 118–240 ms and wt-b 113–204 ms.

- **R1 (a first fixed point could miss a change that kept its mtime): fixed.**
  - **The record is saved:** `DiskSync` saves each worktree's record in `<data>/.fractal-jdtls/records/<hash>.json`, atomically, after each full fixed point (0.3–2 ms on the fixture, 25–48 ms on the large tree).
  - **A restart compares against it:** it loads the record, so its first fixed point finds what changed while JDT LS was stopped.
  - **A missing or unreadable record:** that first fixed point cleans the worktree's projects, reported as `sync.cleanBuild: no-saved-record`, a new property in the description; `clean: true` reports `requested`.
  - **An add needs no clean build:** it takes and saves the record just before its folder change, so a change during the import or before the first fixed point differs from it. Removing a worktree deletes its record.
  - **Tests:** `test_a_change_that_kept_its_mtime_while_jdtls_was_stopped_is_found_after_the_restart`, with and without a saved record. A `cp -p` change made while JDT LS was stopped:
    - with the record, the restart's first `problems` on main reported `first`, `filesChanged` `[Launcher.java changed]`, and the file's error, with no clean;
    - with main's record deleted, the same change gave `cleanBuild: no-saved-record`, and the error;
    - wt-a and wt-b, whose records were there, weren't cleaned;
    - the file's bytes and times were identical before and after;
    - `test_the_record_is_saved_for_each_worktree` checks there's one record per worktree.
- **R2 (a fixed point starting after the fast path's check could be missed): fixed.**
  - **The lock:** each worktree has a fair read-write lock. The fast path's check and the reading of its answer hold it to read. A fixed point holds it to write until its join ends, then downgrades to read for its own answer. A check can't miss a fixed point, and no answer is read while one changes the markers.
  - **`eclipse-changed`'s text** no longer says it covers a running fixed point: a request now waits for it, and then checks.
  - **Test:** `test_no_answer_is_read_while_a_clean_build_of_the_worktree_runs`. Five `build clean: true` of wt-a ran while four threads asked `problems`. All 20 answers were run 05's 3 errors; they waited 114–177 ms for the clean builds, then took the fast path. The test wasn't run against the old code, so it doesn't show that the old code failed it.
- **R3 (an unchanged worktree's answer could come after its deadline): fixed.** The deadline is checked after the fast path's check, and after any answer is read; past it, the answer is `timeout`. In the gate's large import, a `problems` with `timeoutMs: 100` on the unchanged tree got `504 timeout`, phase `syncing`, after 541 ms: the check isn't interrupted, but its result is refused.
- **R4 (cyclic type-variable bounds overflowed the stack): fixed.**
  - **The guard:** `JavaNames` tracks the type variables it has resolved, and a cycle erases to `java.lang.Object`, as javac does.
  - **The fallback:** `Markers.element()` catches any `Throwable` from naming, logs it, and leaves the problem without its element.
  - **Test:** `test_cyclic_type_variable_bounds_dont_stop_the_problems` builds a class with `<T extends T> void f(T value)` and `<A extends B, B extends A> void g(A a)`, each with a `Missing` local. The answer is 200, with JDT's two `Cycle detected` errors and the two `Missing cannot be resolved to a type`, named `org.fractal.harness.app.Cyclic#f(java.lang.Object)` and `#g(java.lang.Object)`.

Two new `[REVIEW HERE]` proposals in design §11 record how R1 and R2 were done: the record's file, format and timing, and the lock per worktree (with R3's checks).
