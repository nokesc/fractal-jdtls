Recorded 2026-11-02 on branch `t001-first-release` (after T001.04 and design commit 927c383), Linux (WSL2), i7-9750H (12 CPUs, no SHA extensions), OpenJDK 25.0.1 (mise), Python 3.12.14 (mise) and 3.14.4 (`/usr/bin/python3`).

- Maven used the scratch repository `/tmp/fractal-jdtls-t001/m2/repository`, through `MAVEN_ARGS`.
- JDT LS's own Maven import used the same scratch repository, through a scratch `settings.xml` passed as `java.configuration.maven.userSettings`.
- The install, every `-data`, the launcher's default cache (`XDG_CACHE_HOME`) and the fixture are under `/tmp/fractal-jdtls-t001/t005/`.

## What was built

**`bin/jdtls`** follows design §5. It is standard library only, Python 3.10 or newer.

- **Command line.** It accepts the stock options:
  - `--java-executable JAVA` or `--java-executable=JAVA`;
  - repeatable `--jvm-arg=OPTION` (a separate value is also accepted);
  - `-data DIR`;
  - `--validate-java-version` and `--no-validate-java-version`.
  
  Every other argument passes through to JDT LS in order. `-h` and `--help` print usage to stderr.
- **Verification at launch.**
  - It first hashes `bin/install.py` against the install's `release-files.json`, so a changed installer is never imported.
  - It then imports `install.py` with `sys.dont_write_bytecode` set, and runs exactly the check `install.py --verify` runs, against `pin.json` and `release-files.json`.
  - It refuses to start on any missing, extra or changed file, listing each one, and on a folder that isn't `<root>/<release>/`.
- **Java.**
  - It looks in `--java-executable`, then `$JAVA_HOME/bin/java`, then `java` on `PATH`. As in the stock launcher, a `JAVA_HOME` without `bin/java` falls back to `PATH`.
  - It runs `java -version` with the output captured. It reads `1.x` versions as `x`.
  - It refuses a Java below the pin's `java.minimum`, naming the minimum and where the Java came from.
- **`-data`.**
  - The client's value is made absolute. (Changed in review R2: it is now passed on unchanged, and may be a `file:` URL.)
  - The default is `${XDG_CACHE_HOME:-~/.cache}/fractal-jdtls/ws/<sha1 of realpath(cwd)>`. A relative `XDG_CACHE_HOME` is ignored, per the XDG spec, as `install.py` does for `XDG_DATA_HOME`.
  - A `-data` inside the install, or an Equinox `@` location, is refused.
- **`-configuration`.** It is `<data>/.fractal-jdtls/<release>/configuration`, created before launch, unless the client passes its own `-configuration`, which is then left alone. (Changed in review R1: a client's `-configuration` inside the install is now refused.)
  - This choice is within §5's "next to or inside `-data`": inside, because the client owns that folder.
  - It is per release because Equinox caches bundle state there, so switching releases on one `-data` starts clean.
- **The command.** It is the stock `jdtls.py` command, in the stock order:
  - the JAXP limits when Java is 24 or newer;
  - the stock `-D`, `-Xms1G`, `--add-modules` and `--add-opens` options, with `config_linux`;
  - `-javaagent:<release>/lib/fractal-jdtls-agent.jar` and one `-Dorg.osgi.framework.bootdelegation=…`;
  - the client's `--jvm-arg` values;
  - `-jar <the Equinox launcher pinned in pin.json> -data <data> -configuration <area>`;
  - the passed-through arguments.
  
  The Equinox launcher is chosen from `pin.json`'s file list. As in the stock launcher, the unversioned `org.eclipse.equinox.launcher.jar` is preferred, else `org.eclipse.equinox.launcher_*.jar`; exactly one must match.
- **The three 927c383 rules:**
  - **Boot delegation is merged.** The client's `-Dorg.osgi.framework.bootdelegation` is removed from its JVM arguments. Its packages, from the last one given (the one the JVM would have used), plus `org.fractal.jdtls.boot` unless already listed, become the one property.
  - **stdout belongs to LSP.** Every message goes to stderr. As a script, it also rebinds `sys.stdout` to stderr. `java -version` output is captured.
  - **Nothing is written into the install.**
    - The launcher never runs or imports the stock `eclipse/bin/jdtls`.
    - Bytecode is off while it imports `install.py`, and for the whole process when run as a script.
    - Its only write is the configuration area under `-data`.
- **Exec.** It replaces itself with `java` through `os.execv`, after flushing stderr.

**`tests/unit/test_launcher.py`** has 39 tests. Each builds a fake install (`<tmp>/root/9.9.9-1/`) holding the real `bin/jdtls` and `bin/install.py`, and uses a fake `java` that records its argv and pid and echoes stdin to stdout.

**AGENTS.md** now says how to start JDT LS from an install, and warns about the mise `python3` shim and `JAVA_HOME` (see "For Chris").

- `find -newer` against a marker touched before the launch;

- a search for `__pycache__`.
