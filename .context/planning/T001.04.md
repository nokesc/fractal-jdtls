# T001.04 — The agent

Step 4 of [T001](T001.md).

## Why now

The launcher always adds the agent, so the agent must exist first.

## Depends on

T001.01, and T001.02 for `pin.json`. A JDT LS install from T001.03, to check that the hooks are in place.

## Design

- [design.md](../design.md) §6.
- The spike's [FINDINGS](../research/jdtls-worktree-spike.md), "Result" and "Constraints and risks".
- The spike's sources, in the seed's `agent` folder (retired in T001.06; in Git history under `.context/spike`).

## Changes

- **Port `Spike.java` and `SpikeAgent.java`** into `org.fractal.jdtls.boot` and `org.fractal.jdtls.agent`, with the spike's `fix` behavior always on.
  - Remove the modes, `spike.worktrees` and `spike.mavenRequester`.
  - Keep only the six hooks in the design §6 table. Drop the spike's logging-only `create` and `ClasspathDescriptor` hooks.
  - Outside any worktree, or without a requester, change nothing (§6).
- **The two jars,** as in §6: the agent jar names Byte Buddy with `Class-Path` and the boot jar with `Boot-Class-Path`. Byte Buddy is not bundled.
- **Loud failures,** as in §6:
  - a hook whose matcher selects no method, or more than one, reported when its class loads;
  - a class that fails to transform;
  - target classes not in place at the checkpoint (the first return from `populateClasspath`), or at shutdown when `populateClasspath` itself was never advised;
  - a prefix collision between two worktrees, reported once.
- **The optional diagnostic log,** off by default, with the events listed in §6. T001.06 asserts on them.
- **Unit tests** for the parts that don't need JDT LS:
  - worktree detection, including a `.git` file and a `.git` folder, and no `.git` at all;
  - naming, and leaving a project outside any worktree unchanged;
  - the collision report;
  - requester selection;
  - the hook-in-place rule: a matcher that selects zero or two methods of a small test class is reported;
  - the built agent jar's `Class-Path` naming the same Byte Buddy version as the root POM and `pin.json` (extending T001.02's test).

## Running JDT LS by hand

The seed's `scripts/lsp_driver.py` can't be used as it is. It hard-codes the **spike** agent (`$SPIKE_HOME/agent/spike-agent.jar`), `-Dspike.mode` and the `org.fractal.spike.jdtls.boot` boot delegation, and by default it runs `~/.local/bin/jdtls`, which is a separate, hand-made install. Used unchanged, it would test the spike agent against the wrong install and still pass.

So either adapt a copy in a scratch folder, or send a minimal LSP `initialize`. Either way:

- run the T001.03 scratch install's `eclipse/bin/jdtls`;
- pass the product agent jar from `lib/`, the product boot delegation (`org.fractal.jdtls.boot`) and the diagnostic log through `--jvm-arg`;
- pass a scratch `-data`, and a scratch `-configuration` so the stock launcher doesn't write into the install (§5);
- open a Maven project from a scratch copy of the seed fixture, with the POMs renamed from `pom.xml.fixture`.

## Acceptance

Record real output for each item.

- **Byte Buddy loads through `Class-Path`.** A JVM started with only `-javaagent:<lib>/fractal-jdtls-agent.jar`, and Byte Buddy beside it, runs `premain` without `NoClassDefFoundError`. Removing Byte Buddy from `lib/` produces a clear failure.
- **Under the real JDT LS 1.63.0 install,** started by hand as above, the diagnostic log shows all six hooks in place by the checkpoint, and nothing reported. Show this both on a fresh import and on a restart with the same `-data`. If any target class hasn't loaded by the checkpoint in either run, stop and report: the checkpoint in §6 is wrong.
- **A broken hook is reported.** With a test-only variant of the agent whose matcher for one target method names a method that doesn't exist, the same run reports that hook on stderr and in the JDT LS log. The product has no switch for this (§6).
- **The jar names are checked.** The unit test for the Byte Buddy version passes against the built jar.
- `mise run validate` passes.
