## Changes

- **Applying edits,** as in §11:
  1. reconcile with the disk;
  2. compute the `WorkspaceEdit`;
  3. under the workspace lock, check that each affected file's content is unchanged;
  4. write the text edits and the file creates, renames and moves;
  5. refresh, build, and return a unified diff and the problems.

  `dryRun` returns the diff only, and a file changed in between is `files-changed` with nothing written. Edits outside the requesting worktree are refused as `internal`, because they would be a defect.
- **The refactorings:**
  - rename of a type (with its file), method, field, local variable or package;
  - organize imports;
  - extract local variable, extract constant, extract method;
  - inline local variable.

  The choices JDT LS asks for interactively become request fields, such as the new name, or whether to replace all occurrences.
- **JDT LS's own refusals,** for example a rename that would clash, become catalogued problems that quote JDT's reason and give a `hint`.
- **Integration tests through HTTP only,** in `wt-a` while `wt-b` holds the same code:
  - each refactoring with `dryRun`, then applied;
  - a clean `build` after each;
  - `wt-b`'s files unchanged;
  - a file changed between computing and applying (`files-changed`);
  - a refused rename.

## Acceptance

Record real output for each item.

- **Each refactoring:** the request, the diff, and the clean build afterwards, in the evidence.
- **Other worktrees untouched:** `wt-b` and `main` file hashes are identical before and after.
- **`files-changed`:** shown with nothing written (hashes identical).
- **A refusal:** shown with its problem body.
- `mise run validate` passes.
