# T002.02 — The API contract and the design after the spike

Step 2 of [T002](T002.md). **Stops for Chris's review.**

## Why now

Fractal Harness builds its MCP tools on this contract, and every later task implements part of it. It must be right, and approved, before code depends on it.

## Depends on

T002.01.

## Design

- [design.md](../design.md) §11.
- [HTTP-FINDINGS](../research/jdtls-http-spike.md) and T002.01's proposed design changes.

## Changes

- **Design §11 updated with the spike's results:**
  - the mechanisms it chose, for loading, the connection, autobuild, the refresh scope and reads during imports;
  - its measurements;
  - its constraints and risks.

  Each change the spike forced goes behind `[REVIEW HERE]`, with its evidence linked.
- **The OpenAPI 3.1 description,** `endpoint/src/main/resources/openapi.json` (the module itself is created in T002.03):
  - every T002 operation in §11, with request and response schemas and an example of each;
  - the `worktree` and `module` fields shared by every operation;
  - the `sync` report;
  - Java names and text anchors, with their syntax described for an LLM;
  - the error catalogue: each `code`, its HTTP status, when it happens, and an example problem with its `hint` and `candidates`.
- **The descriptions are written for an LLM reader,** because Harness passes them on as MCP tool descriptions: what the operation does, when to use it, and what to do with each error.
- **A unit test (pytest)** that checks the description against the OpenAPI 3.1 schema, with a development dependency such as `openapi-spec-validator`, locked in `uv.lock`. It also checks that every operation has an example, and every error code an example problem.
