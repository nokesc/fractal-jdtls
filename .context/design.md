# Fractal JDT LS design

What Fractal JDT LS delivers, and how it is built, verified and released. [README.md](../README.md) says why it exists. The design and the code are authoritative. Task files only order the work.

The decisions below were made by Chris on 2026-11-01, starting from the JDT LS worktree spike. Its findings, [research/jdtls-worktree-spike.md](research/jdtls-worktree-spike.md) (cited below as FINDINGS), are the evidence the agent is built on.

## 1. Scope and boundaries

- **The product:** a verified install of one official Eclipse JDT LS release, and a launcher that is a drop-in for the stock `jdtls` and always adds this project's Java agent. The agent keeps each Git worktree's Maven projects separate inside one JDT LS process.
- **The HTTP endpoint (§11), opt-in.** In HTTP mode, the launcher also loads this project's endpoint bundle, which becomes JDT LS's only client and serves a token-gated REST API on localhost. Several sessions can then share one process through it. Without HTTP mode, the launcher is still the plain drop-in. (Decided by Chris on 2026-11-07.)
- **Unopinionated.** These belong to the tool that launches it, not to this project:
  - how many JDT LS processes run, which worktrees share one, and when they start and stop. In HTTP mode, the endpoint carries out the client's choices: it adds and removes worktrees when told to, and never decides which worktrees share a process;
  - which sessions use a process, and how their requests are routed to it;
  - compiler preferences, such as errors-only diagnostics or keeping `target/classes`;
  - LSP settings and JVM sizing.

  Fractal Harness is the first consumer and owns all of that for itself. It talks to the endpoint over HTTP, and does its own MCP delegation.
- **Never repackage or redistribute Eclipse's files.** The installer downloads them from Eclipse. The same goes for Byte Buddy, which comes from Maven Central (§3).
- **Official JDT LS releases only.** JDT LS publishes its releases under `https://download.eclipse.org/jdtls/milestones/<version>/`. Never use `snapshots/`, or any other pre-release build.
- **Linux only.** Write the Python portably where it costs nothing, but support, test and document only Linux.
- **Interim.** The aim is for m2e and JDT LS to fix these problems upstream. Then the agent goes away, and this project becomes only a verified installer or is retired.

## 2. Releases and the installed layout

- **A release** is a tag `v<jdtls-version>-<n>`, for example `v1.63.0-1`. It pins one JDT LS version, one Byte Buddy version, and the agent, all tested together. A fix that doesn't change the pin is the next `<n>`.
- **The release ID** (`1.63.0-1`) has one source: the `release` field of `pin.json` (§3). The zip's name and top folder, the install folder and the tag the workflow accepts (§9) all come from it, so a local build before any tag has the same identity as the published one.
- **The release asset** is one zip. It holds this project's files only:

  ```
  fractal-jdtls-1.63.0-1/
    bin/install.py     installs this release (§4)
    bin/jdtls          the launcher (§5); called run.py in the discussion that led to this design
    lib/               the agent jar and the boot jar (§6); the endpoint's jar and HTTP mode's preferences (§11)
    pin.json           the pin (§3)
    release-files.json the SHA-256 of every other file in the zip (§4)
    LICENSE  NOTICE
  ```

  **`lib/` also holds HTTP mode's two files.** (T002.12's proposal, a correction of fact; approved by the governor on 2026-11-09 under Chris's delegation; to review.) `lib/fractal-jdtls-endpoint.jar` (since T002.03) and `lib/http-mode-preferences.ini` (since T002.05) are in the zip and in `release-files.json`, as §11 "Inside JDT LS" and "Taking in changes exactly" say; the layout above named only the agent's jars. A correction of fact, outside §10 and §11, so it's marked for the governor.
- **Installed layout:** one folder per release, containing everything ("option A"):

  ```
  ~/.local/share/fractal-jdtls/1.63.0-1/
    bin/  lib/  pin.json  release-files.json  LICENSE  NOTICE     copied from the zip
    lib/byte-buddy-<version>.jar              from Maven Central, verified
    eclipse/                                  JDT LS from Eclipse, verified
  ```

  - The default root is `${XDG_DATA_HOME:-~/.local/share}/fractal-jdtls/`, overridable with a flag and an environment variable.
  - To uninstall, delete the folder.
  - Each release downloads Eclipse again (about 53 MB). That's accepted to keep the model simple.
- **The install stays read-only after it's installed.** Nothing at runtime writes inside it (§5, "Configuration area").

## 3. The pin

**`pin.json` is hard-coded in each release** and read by both `install.py` and `bin/jdtls`. It holds:

- the release ID, `<jdtls-version>-<n>` (§2);
- the JDT LS version, its download URL and the tarball's SHA-256;
- the SHA-256 of **every file** in the unpacked tarball;
- the minimum Java version that release of JDT LS needs to run;
- the Byte Buddy version, its Maven Central URL and its SHA-256.

**The Byte Buddy version is chosen once,** as the `byte-buddy.version` property of the root `pom.xml`, because the agent build compiles against it and writes it into the agent jar's `Class-Path` (§6). `tools/pin.py` reads it from there. A unit test fails unless the POM property, `pin.json` and the built agent jar's `Class-Path` all name the same version; a mismatch would otherwise surface only as the agent failing to load at launch.

**A maintainer tool, `tools/pin.py`, writes it.** It's development tooling, not shipped in the zip. Given a JDT LS version and a release number `<n>` (default 1), it:

1. Downloads the tarball and checks it against Eclipse's published `<tarball>.sha256`.
2. Records the hash of every file.
3. Classifies each jar:
   - signed by the Eclipse Foundation (`jarsigner -verify`, with the signer's chain valid, not self-signed and allowed to sign code; a warning about the timestamp authority alone doesn't disqualify a jar);
   - byte-identical to an artifact on Maven Central (by the artifact's published hash);
   - or **neither**: trusted only through the tarball's checksum.
4. Downloads Byte Buddy from Central, records its hash, and verifies its PGP signature (`.asc`) when `gpg` and the maintainer's key are available.
5. Writes `pin.json` and a pin report. The report goes into the repository as the evidence of how each file was checked.

Hashes we compute ourselves only prove a file hasn't changed since. **What a file should be comes from those outside checks.** The pin is the record of them.

### Verified facts for JDT LS 1.63.0

Only its timestamp authority's chain is invalid and the timestamp expired, so `jarsigner -verify -strict` would reject it and the count would be 57. It is also byte-identical to Maven Central, and the pin report records the warning.

- JDT LS **writes a `configuration/` folder into its install folder** at runtime when launched by the stock script (seen in the hand-made HS-26 install). The cause and the fix are in §5, "Configuration area".

## 4. Installing: `bin/install.py`

- **Python standard library only,** Python 3.10 or newer. It runs without a virtual environment.
- **Installs the release it ships in** into `<root>/<release>/`. The unzipped download can be deleted afterwards.
- **Idempotent.** If the target exists and verifies, it does nothing.
- **Atomic.** It downloads and unpacks into a temporary folder beside the target, verifies everything against `pin.json`, then renames it into place. A failed or interrupted install never leaves a partial target. The tarball's checksum is checked before unpacking, and every unpacked file's checksum after.
- **Byte Buddy** is downloaded from Maven Central into `lib/` and verified against the pin.
- **`--verify`** re-checks an existing install and reports every missing, extra or changed file.
  - **The release's own files are verified too,** through `release-files.json`. `pin.json` can't hold their hashes: it is one of them, and the agent jar is built after the pin. So `release:zip` writes `release-files.json` with the release ID and the SHA-256 of every other file in the zip (`bin/`, the agent and boot jars, `pin.json`, `LICENSE`, `NOTICE`). The installer checks the unzipped release against it before installing, copies it into the install, and `--verify` and the launch check (§5) check those files' contents against it, wherever they run from. Its release ID must equal `pin.json`'s. (Decided by the governor on 2026-11-02 during T001.03, under Chris's delegation; to review.)
  - **Root and concurrency.** The root is `--root`, else `FRACTAL_JDTLS_ROOT`, else, for an installed `install.py`, the root it's installed in, else the XDG default (§2). Installs hold a lock file, `<root>/.<release>.lock`, so a later install can safely remove the partial folder a killed one left beside the target.
  - **A target that exists but fails verification is left alone,** with an instruction to delete it and run again. The installer never repairs or overwrites an install.
- Errors say exactly what failed and what to do. It exits non-zero on any failure.

## 5. The launcher: `bin/jdtls`

**A drop-in for Eclipse's stock `bin/jdtls`.** It accepts the same command line: `--java-executable`, repeatable `--jvm-arg=…`, `-data <dir>`, and any other arguments passed through to JDT LS. It builds the same `java` command, with the Equinox launcher, the shared configuration and `--add-opens` (see `bin/jdtls.py` in the Eclipse tarball). It also always adds the agent:

```
-javaagent:<release>/lib/fractal-jdtls-agent.jar
-Dorg.osgi.framework.bootdelegation=<the boot helper's package>
```

- **Java.** It uses `--java-executable`, then `JAVA_HOME`, then `java` on `PATH`, the stock order. It **only checks** that the version meets the pin's minimum, and fails with a clear message otherwise. Choosing a JDK that suits the project is the client's job.
- **Workspace (`-data`).** Whatever the client passes. When none is given, the default is `${XDG_CACHE_HOME:-~/.cache}/fractal-jdtls/ws/<sha1 of the canonical working directory>`, keyed on the full path. The stock launcher keys on the folder name only, which lets two checkouts with the same folder name share one workspace.
  - A client's `-data` and `-configuration` pass to Equinox unchanged, as with the stock launcher. The launcher resolves them as the pinned Equinox does, and refuses, before starting Java, any that resolves inside the install, and the forms whose folder is ambiguous: `file:` URLs with `?` or `#`, upper-case `FILE:`, other URL schemes and `@` locations. (Decided by the governor on 2026-11-02 during T001.05; to review.)
- **Configuration area.** It passes a writable `-configuration` outside the install, at `<data>/.fractal-jdtls/<release>/configuration`, so the install stays read-only and verifiable. Confirm with a real run that nothing is written inside the install.
  - The stock `bin/jdtls.py` already points Equinox at the install's read-only shared configuration (`-Dosgi.sharedConfiguration.area=<install>/config_linux`, `…area.readOnly=true`, `-Dosgi.configuration.cascaded=true`), but passes no `-configuration`. Equinox then puts its writable area at `<install>/configuration`. Keeping the stock properties and adding `-configuration <writable folder>` is enough; an empty folder works because the cascade supplies `config.ini`.
- **Verification at launch.** Before starting JDT LS, it checks the install against `pin.json` and `release-files.json` (§4). If the cost is more than about half a second, measure it, record it and raise it with Chris.
- **No other options,** except the opt-in HTTP mode's (§11): `--http-port-file` and `--http-settings`. Compiler preferences, LSP settings and JVM sizing belong to the client, through `--jvm-arg`, files the client writes into its own `-data`, or LSP (in HTTP mode, the settings file).
- **In HTTP mode, stdin and stdout don't carry LSP.** The endpoint is the client (§11), and the "stdout belongs to LSP" rule below applies only without HTTP mode.
- It replaces itself with the `java` process, as the stock launcher does on POSIX, so the LSP client's stdin and stdout connect straight to JDT LS.
- **Boot delegation is merged, never replaced.** If the client passes its own `-Dorg.osgi.framework.bootdelegation=…` through `--jvm-arg`, the launcher passes one property: the client's packages plus the boot helper's. The last `-D` would otherwise win, and losing the boot helper's package breaks m2e itself, which the checkpoint (§6) can't catch.
- **stdout belongs to LSP.** The launcher and its checks write only to stderr; anything on stdout before `exec` corrupts the LSP stream.
- **Nothing is written into the install,** including Python bytecode: the launcher doesn't write `__pycache__` for itself or for any module it imports from the install, and it never runs the stock `eclipse/bin/jdtls`, which would.

## 6. The agent

Built from the spike's `Spike.java` and `SpikeAgent.java`, with the behavior of the spike's `fix` mode. FINDINGS "Result" items 1–3 are the specification.

- **Always on.** There are no modes and no off switch in the product. `trace`, `names`, `fix` and `mavenRequester` were switches for the experiment. Anything like them lives only in test code.
- **Naming.** Each Eclipse project is named `<worktree-dir>.<name>`, where `<name>` is m2e's name, always prefixed: m2e computes that name afresh from the POM on each creation, so it never already carries the prefix, and skipping names that look prefixed would make `harness-app` and `wt-a.harness-app` collide.
- **Worktree identity.** The worktree is the nearest ancestor of the project's `pom.xml` that contains `.git`, whether that's a file (a linked worktree) or a folder (a main checkout). Nothing is passed in by the launcher or client: folders added at runtime work the same way. The spike's `spike.worktrees` property is dropped.
- **Outside any worktree** (no `.git` ancestor), the agent changes nothing: the project keeps m2e's name, and lookups it requests keep m2e's choice. Same for a requester that can't be determined.
- **Resolution.** When several workspace POMs share a groupId, artifactId and version, prefer the one in the requester's worktree, using the lookups and requester hooks listed in FINDINGS.
- **The hooks.** These six methods, and no others, are the product's hook targets (FINDINGS "Result"):

  | Class | Method | Role |
  | --- | --- | --- |
  | `org.eclipse.m2e.core.internal.project.ProjectConfigurationManager` | static `getProjectName(ProjectImportConfiguration, Model)` | naming |
  | `org.eclipse.m2e.core.internal.project.registry.EclipseWorkspaceArtifactRepository` | `getWorkspaceArtifact(String, String, String)` | resolution |
  | `org.eclipse.m2e.core.internal.project.registry.BasicProjectRegistry` | `getProjectFacade(String, String, String)` | resolution |
  | `org.eclipse.m2e.jdt.internal.DefaultClasspathManagerDelegate` | `populateClasspath` (4 arguments) | requester |
  | `org.apache.maven.model.building.DefaultModelBuilder` | `readParentExternally` (3 arguments) | requester |
  | `org.apache.maven.project.DefaultProjectBuilder` | `initParent` (5 arguments) | requester |

  The spike's `create` and `ClasspathDescriptor` hooks only logged, and are dropped. `getProjectName` is called only from `create()` (FINDINGS run 02), so its diagnostic event also marks a project creation.
- **Two jars.**
  - **Agent jar:** `premain` and advice, with a manifest that names Byte Buddy as `Class-Path: byte-buddy-<version>.jar`, resolved next to it in `lib/`, with the version from the root POM (§3). Byte Buddy is **not bundled**. The spike always bundled it, so confirm loading through `Class-Path` with a real run first.
  - **Boot jar:** the helper the advice calls. The agent jar's manifest lists it with `Boot-Class-Path`, and its package appears in `org.osgi.framework.bootdelegation`. It uses JDK types only in its signatures.
- **Packages:** `org.fractal.jdtls.agent` and `org.fractal.jdtls.boot`. Compiled with `--release 21`, the minimum Java for JDT LS 1.63.
- **Fail loudly.** It reports clearly, on stderr and in the JDT LS log:
  - any hook that isn't in place (FINDINGS "Constraints and risks"), as defined below;
  - **two worktrees in one process with the same prefix,** once per collision. Making folder names unique within one process is the client's rule. The agent only reports a collision, at no ongoing cost.
  - **a hook that fails while running,** for example because an m2e field it reads was renamed by an update. It's reported once per hook, and that call keeps m2e's own result. Reports go to the process's original stderr, captured in `premain`, because JDT LS replaces `System.err` after it starts.
- **A hook is in place only when its method was advised,** not when its class was transformed. Byte Buddy reports a class as transformed even when no method in it matched, so a changed signature after an upgrade would otherwise pass silently. For each target class, the agent counts the methods its matcher selects, and reports a hook whose matcher selects none, or more than one, as soon as the class loads. A class that fails to transform is reported from Byte Buddy's error listener.
- **When a hook that never loaded is reported.** The target classes load lazily, the Maven ones only when the first Maven project is read, so a missing class can't be detected in `premain`. The checkpoint is the first return from `populateClasspath`: by then a Maven project has been read and configured, and every other target class must have been advised, or it's reported. If `populateClasspath` itself is never advised, the agent reports at JVM shutdown every target still not in place, provided at least one other hook was. A workspace with no Maven projects reaches neither point and reports nothing, which is correct: the hooks don't matter there. T001.04 confirms with real runs, on a fresh import and on a restart, that every target class has loaded by the checkpoint.
  - **"Provided at least one other hook was" becomes "provided a Maven project was read".** (T002.04's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) T002.03 found that with no Maven project, m2e's resolution classes and Maven's requester classes load at startup anyway, so five hooks were in place and the shutdown check reported `populateClasspath` as never loaded, in a workspace that should report nothing. A hook in place doesn't show that a Maven project was read; a naming or requester hook that ran does, so the agent records the first such call, and shutdown reports only after one. The case the shutdown check exists for, Maven projects read while `populateClasspath`'s class is missing, still reports. A unit test fails on the old condition and passes on the new; a broken hook (the test-only broken-hook jar) is still reported as its class loads.
- **An optional diagnostic log,** off by default, enabled by the system property `fractal.jdtls.diagnosticLog`, which names the file. One JSON line per event, which the integration suite asserts on (§8):
  - each hook in place, and each hook not in place;
  - each naming decision: the POM, m2e's name and the result;
  - each GAV lookup at either resolution site: the site, the GAV, the requester (or none), the candidate POMs, m2e's choice and the final choice;
  - each prefix collision.
- **Must be present on every start.** A workspace created without the agent needs a fresh `-data` to use it (FINDINGS runs 06 and 07). Document this for users.

## 8. Testing and the release gate

- **Unit tests** (pytest) cover `install.py`, `bin/jdtls` and `tools/pin.py` against a scratch home and a local fake download server:
  - checksum mismatches;
  - interrupted installs;
  - idempotency;
  - `--verify` reports;
  - Java detection and the minimum version;
  - the exact `java` command line;
  - default `-data` keying.

  These tests never touch the real `~/.local/share`, `~/.cache` or `~/.m2`.
- **Integration tests** port the spike's driver and fixture:
  - they run real JDT LS, installed by `install.py` from a built release zip into a scratch root, and launched through `bin/jdtls`;
  - scenarios: import, edits, reimport and restart across a main checkout and two linked worktrees;
  - the results must match FINDINGS run 05 (each worktree resolves its own modules, with the right diagnostics) and run 06 (restart keeps names and classpaths);
  - they observe JDT LS through LSP (`java.project.getAll`, `java.project.getClasspaths`, diagnostics) and through the agent's diagnostic log (§6), which the tests enable. The log is what shows that every lookup had a requester and stayed in its worktree, and that a restart created no projects (no naming events);
  - a **control run** without the agent, through a test-only launch path, must reproduce the baseline failure (run 01). That proves the fixture still shows the problem.
- **Integration tests use their own Maven local repository,** never `~/.m2`. Each run writes a Maven `settings.xml` whose `localRepository` is a scratch cache that persists between runs, and passes it to JDT LS as the LSP setting `java.configuration.maven.userSettings`. The first run downloads the fixture's plugins from Maven Central, so the suite needs network access, in CI too. Confirm that the scratch repository fills with the fixture's plugins.
- **Keep fixture POMs as `pom.xml.fixture`,** materialized only into scratch folders, so no IDE or language server on this checkout imports them (FINDINGS "IDE side effect").
- **The test scratch folder is on disk, beside the main checkout,** never in `/tmp`. (Chris, 2026-11-08; T002.08; revised after a Codex design review, D9 and D10.)
  - **Where:** `<main checkout>__scratch/`, a sibling of the main checkout (for `~/github/nokesc/fractal-jdtls`, `~/github/nokesc/fractal-jdtls__scratch/`), found from Git's own list of worktrees (`git worktree list --porcelain`, its first entry), so a linked worktree uses the same one. `FRACTAL_JDTLS_TEST_SCRATCH` overrides it; a layout where no main checkout can be found (a bare repository) fails, saying to set it. Before anything is made or pruned, the scratch folder must be owned by the user, not writable by others, and have no `.git` in it or above it. It holds every pytest run's folders, unit and integration: fixture worktrees, scratch installs, `-data`, the large tree, logs and LSP traffic.
  - **Why:** `/tmp` here is a tmpfs, held in memory (7.8 GB in the WSL VM), so test scratch competes with the JDT LS heaps, Maven and the agents for RAM. It filled during T002, and a restart wipes it, with the records of a failed run. On disk, Chris can also browse each run.
  - **Not inside a checkout.** The suite's check for a `.git` above its scratch folder stays: the agent places a file in the nearest folder above it that has `.git` (§6), so anything the fixture means to be outside a worktree would belong to the outer checkout, and a language server on that checkout would import the fixture's POMs. So the scratch folder can't be a checkout's git-ignored `temp/`.
  - **One suite at a time.** This project has one linked worktree at a time (Chris, 2026-11-08), so one folder serves every checkout. A run holds a kernel lock (`flock`) on a lock file at the scratch folder's top, outside the pruned runs, for its whole duration; a second run fails at once, naming the first one's PID, rather than sharing the folder. The kernel releases it when the process dies, so there's nothing stale to recover.
  - **Kept, then pruned:** each pytest session gets a numbered folder, and a `current` link names the newest, through pytest's own numbering and retention (not `--basetemp`, which empties its folder first). A gate is two sessions, unit and integration, so the latest six are kept: three gates. Run folders are for browsing and diagnosis only; evidence stays self-contained, copying the output it cites, because run folders are pruned (Codex D10). CI's scratch goes with its runner; the release workflow uploads the scratch folder as an artifact when a gate fails.
  - **Agents' other intermediate data** (logs, probes, captured output) goes in the checkout's git-ignored `temp/`, where Chris can see it, never in `/tmp`. Nothing that holds a `.git` or a `pom.xml` goes there.
  - **T002.08's details** (T002.08's proposal; approved by the governor on 2026-11-09 under Chris's delegation; to review):
    - **pytest's names, through `PYTEST_DEBUG_TEMPROOT`:** the sessions are `<scratch>/pytest-of-<user>/pytest-<n>/`, and the "current" link is pytest's own `pytest-current`. pytest documents that variable as the temporary root's override; anything else would mean private APIs or `--basetemp`. The lock file is `<scratch>/suite.lock`, above `pytest-of-<user>/`, so pruning never reaches it.
    - **"Not writable by others" means by group or others** (`go-w`). The suite makes the folder with mode 700. A folder someone else made group-writable is refused, and the message gives the `chmod`.
    - **A killed run's pytest `.lock` is removed under the suite's lock.** pytest won't prune a session whose `.lock` is under three days old, and `kill -9` leaves that file behind, so retention would keep seven sessions. While the suite holds its `flock`, no other session can be using that `.lock`.
    - **`--basetemp` is refused, and the override must be an absolute path.** Each fails loudly rather than emptying a folder or resolving against an unexpected working directory.
    - **Python's temporary files and `TMPDIR` go to the session's `tmp/`.** The first gate showed `tools/pin.py`'s unit tests making `TemporaryDirectory` folders in `/tmp`, so every session points `tempfile` and its children's `TMPDIR` into its own folder. Java ignores `TMPDIR`, and `java.io.tmpdir` is out of scope; the JVMs write only their 32 KB `hsperfdata` files (and Maven its `jansi` library) to `/tmp`.
    - **The lock's descriptor is close-on-exec and is never closed.** A JDT LS the run started, if it outlives the run, can't hold the lock. Because the descriptor is never closed, pytest's pruning at the session's end still runs under the lock.
- A downloaded tarball may be cached for tests in a scratch cache, keyed by its SHA-256.
- The agent's own Maven build is ordinary development tooling and uses `~/.m2` as usual.
- **`mise run validate`** is the full gate: unit tests, the agent build, building the release zip, and the integration suite.

## 9. Releasing

- **A GitHub Actions workflow, triggered by a pushed tag:**
  1. checks that the tag is `v<release>`, with `release` from `pin.json` (§2), and fails otherwise; then builds the release;
  2. runs `mise run validate`;
  3. creates a **draft** release for the tag;
  4. attaches the zip;
  5. publishes.
- **Turn on immutable releases** for the repository. That's a setting Chris changes.
- **Agents never tag, push or publish.** The release task prepares and dry-runs everything locally. Chris tags.

## 10. Requirements on consumers

These belong to whoever launches JDT LS. For Fractal Harness, they're recorded here until Harness tracks them:

- **Folder names must be unique** among the worktrees that share one JDT LS process. In HTTP mode, the endpoint refuses to add a worktree whose folder name is already in use (§11).
- **The launcher owns the lifecycle:** how many processes, sharing scope, and when they start and stop.
- **In HTTP mode, a start has failed if the port file doesn't appear** within the harness's own timeout. The harness then stops the process it started, by its PID (§11).
- **Refactoring policy and recovery are the client's** (Chris, 2026-11-08; §11, "Operation folders"). The endpoint has none of these; they're Fractal Harness's choices:
  - optionally, a checkpoint commit before a refactoring (the endpoint never commits or checks for one), and a dry run reviewed before the apply, with `expectWriteSetDigest`;
  - ignoring `temp/` in each worktree, so operation folders stay out of `git status`; and cleaning them up;
  - a failed build or failed tests after a refactoring start normal agent repair, as for any change; after two unsuccessful attempts the worktree is stopped and Chris is told;
  - after a crash or disconnect, finding the operation among the worktree's recent operation folders; a missing `response.json` means the outcome is unknown, and recovery is by Git and the agent.
- **One client per process.** A shared process needs one owner of its LSP connection. In HTTP mode, that owner is the endpoint (§11), and sessions share the process through its API.
- **Adding and removing workspace folders at runtime** (`workspace/didChangeWorkspaceFolders`) wasn't tested by the worktree spike. T002.01 tested it: it works with the agent's naming and resolution intact (HTTP-FINDINGS question 4), and the endpoint's worktree calls depend on it (§11).

## 11. The HTTP endpoint

The endpoint lets one JDT LS process serve many LLM sessions. Fractal Harness decides which worktrees share a process, routes each session's requests to it, and turns the API into MCP tools. The endpoint, inside JDT LS, does everything that needs JDT LS: it tracks how worktrees and modules map to Eclipse projects, keeps JDT LS in step with the disk, handles all threading and queuing, and gives errors an LLM can act on. The harness only makes blocking calls.

The decisions below were made by Chris on 2026-11-07, who approved the planner's proposals the same day and left the Java name syntax to the planner. T002.01's spike chose the mechanisms in "Inside JDT LS" and measured the costs quoted below. Its findings are in [research/jdtls-http-spike.md](research/jdtls-http-spike.md), cited below as HTTP-FINDINGS; each decision taken from them is marked, with its proposal's number there. Every measurement below comes from the spike's machine: WSL2 on an Intel i7-9750H with 12 CPUs and 15.5 GiB, OpenJDK 25.0.1, JDT LS at `-Xmx4G`, on the integration fixture and on a generated large tree of 51 Maven projects and 10,001 Java files.

### Why it's in-process

- **No extra processes,** even lightweight ones. Everything runs inside JDT LS, where the endpoint has full control.
- **Better integrations than LSP alone.** Inside the process, the endpoint can:
  - join Eclipse's build jobs instead of guessing when work is done;
  - read problem markers instead of keeping a cache of pushed diagnostics;
  - resolve Java names with JDT search;
  - create and delete Eclipse projects with the workspace API.
- **Why not stdio or an existing wrapper:**
  - stdio has one ordered stream and one owner, and JDT LS's lifetime is tied to its client's process: JDT LS 1.63.0 keeps running after its stdin closes, and its `ParentProcessWatcher` stops it about 35 s after its parent process ends (HTTP-FINDINGS question 2). (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 13.)
  - generic LSP-to-MCP bridges are position-based, have one session per server, don't understand worktrees or the agent's naming, and usually start a JDT LS per project. That's the cost this project exists to avoid (README).
- **The cost:** more coupling to JDT LS internals, pinned per release like the agent (§6); and a defect in the endpoint affects every session that shares the process. Timeouts and loud failures (below) contain it.

### Inside JDT LS

- **An OSGi bundle,** `lib/fractal-jdtls-endpoint.jar`, our own Apache-2.0 code, shipped in the release zip and listed in `release-files.json` (§4). Package `org.fractal.jdtls.endpoint`. It's named for what it is, the endpoint; "tools" would collide with Fractal Tools, Fractal Agent Tools and the MCP tools Harness builds from it.
  - **No new third-party code.** HTTP comes from the JDK's `com.sun.net.httpserver` (module `jdk.httpserver`), and JSON from the Gson bundle in the pinned JDT LS. lsp4j, LTK, `jdt.core.manipulation`, m2e and Eclipse resources also come from the pinned JDT LS, imported by the bundle.
  - **It compiles against the pinned tarball's jars,** downloaded and verified against `pin.json` into a build cache. Many of them, including `org.eclipse.jdt.ls.core`, aren't on Maven Central. They're never committed or redistributed (§1). There's no real alternative: `org.eclipse.jdt.ls.core` isn't published anywhere else, and compiling against the exact runtime jars is what proves the bundle's imports match the pinned release. Reflection alone would trade compile errors for runtime ones.
- **The endpoint is JDT LS's only LSP client, connected inside the JVM.** The LSP connection never leaves the process: no TCP socket, no named pipe that another process could open. JDT LS's own request handling and threading run unchanged; the endpoint sends it LSP requests and answers its requests back to the client.
- **Loading: Equinox's start list, through a system property.** In HTTP mode, the launcher passes `-Dosgi.bundles=<the osgi.bundles list of the install's eclipse/config_linux/config.ini, with its Java-properties escaping removed>,reference:file:<release>/lib/fractal-jdtls-endpoint.jar@4:start`. The system property wins over `config.ini`, and the stock list is kept because it's copied. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 1.)
  - The launcher reads the list from the verified install at every launch, so no copy can go stale and nothing is written. A later plain-mode start on the same `-data` doesn't load the bundle. `osgi.bundles` in the writable configuration area's `config.ini` works too, but a later plain-mode start on the same `-data` would read it again.
  - The launcher refuses a client's own `-Dosgi.bundles` in HTTP mode, as it refuses the other properties that HTTP mode fixes.
  - Measured: Equinox runs the activator in its start-level thread, before JDT LS's application, in 135–205 ms. JDT LS answers `initialize` 1.6–2.1 s after launch, and the port file appears after 4.2–4.6 s.
- **The connection: stdio swapped for in-heap pipes.** Before JDT LS's application starts, the activator replaces `System.in` and `System.out` with two pipes that live only on the Java heap. `LanguageServerApplication.prepareStreams` captures both when the application starts, and JDT LS's stdio mode then talks to the endpoint. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 1.)
  - The pipes have no file descriptor, so nothing outside the JVM can reach them. `java.io.PipedInputStream` can't be used: it fails with "Write end dead" once a thread that wrote to it ends, and lsp4j and JDT LS write from pooled threads.
  - After `initialize`, the endpoint checks that JDT LS holds its pipes (`getIn()` and `getOut()` of `JavaLanguageServerPlugin.getLanguageServer()`), and fails startup loudly otherwise. A JDT LS that captured stdio earlier would fail the check.
  - No agent hook is involved. JDT LS's client-socket mode (a TCP port) and its `--pipe=` mode (a Unix-domain socket) can be reached by other local processes, and aren't used.
  - `initialize` carries `processId: null`, the registered worktrees as `workspaceFolders` ("Worktrees"), and the capabilities and settings the endpoint fixes ("Launching"). With no folders, JDT LS falls back to `-data` as its root and imports nothing from it.
- **JDT LS's requests back to the client are answered from the endpoint's own state:**
  - `workspace/configuration` from the settings file, with `null` where it has none;
  - `workspace/applyEdit` with `applied: false`, because the endpoint applies edits itself;
  - `window/workDoneProgress/create`, `client/registerCapability`, `window/showMessageRequest` and `window/showDocument` with `null`;
  - anything else with error `-32601`.
- **Process lifetime:** in HTTP mode, the launcher passes `-DwatchParentProcess=false`, so JDT LS doesn't exit when its parent process ends. Without it, JDT LS exited 35 s after its parent did. `processId: null` stops it watching a client process too, and JDT LS's real stdin isn't read at all. It stops on `POST /v1/shutdown`, or when the harness kills the process it started. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 2.)
- **Direct Eclipse API, for what LSP does badly:** refreshing resources, joining build jobs, reading markers, resolving names, creating and deleting projects, and writing refactoring edits under the workspace lock.

### Launching

- **One opt-in flag on the existing launcher:** `bin/jdtls --http-port-file <file>`, with the other options as in §5. Without the flag, the launcher behaves exactly as §5 says.
- **The token** comes from the environment variable `FRACTAL_JDTLS_HTTP_TOKEN`, never the command line, which any user can read through `/proc`. The launcher refuses to start in HTTP mode without a token of at least 32 characters. Java can't remove a variable from its own environment (HTTP-FINDINGS question 2), so the launcher removes it before starting Java: it hands the token to the endpoint over an inherited pipe (for example fd 3, named by `-Dfractal.jdtls.http.tokenFd=3`), which the endpoint reads once and closes. The token is therefore never in the JVM's environment, nor in any process JDT LS or Maven starts. (Decided by the governor on 2026-11-08 after T002.01, under Chris's delegation; to review.)
  - **What "reads it once and closes" can mean in Java, and the token's form.** (T002.03's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Java can't close a file descriptor by number. The endpoint reads the pipe to its end through `/proc/self/fd/<n>` and closes what it opened; descriptor `<n>` itself stays open, holding an empty pipe whose write end is already closed (the launcher closes it before `exec`). Nothing can read the token from it again, and no child process inherits it: the JDK closes every descriptor above 2 in the processes JDT LS starts. Closing `<n>` itself would need reflection into `java.io.FileDescriptor` and another `--add-opens`, for no gain. The token must also be at most 4,096 characters, so the launcher's write into the pipe never blocks, and visible ASCII with no spaces, because it goes into an HTTP header; the launcher and the endpoint both check.
- **Listening:** only on `127.0.0.1`, on port 0 (the kernel picks a free port, so there's no race between choosing and binding). Once it's listening, the endpoint writes `{"port", "pid", "release", "api"}` to the port file, atomically (write and rename) and with mode 0600. The harness waits for the file. Every startup failure is reported on stderr, and the process exits non-zero.
  - **The port file's lifetime, and where the endpoint logs.** (T002.03's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The launcher removes a port file left from an earlier run before it starts Java, so the file appears only once this process listens, and a harness waiting for it never reads a stale port. On a clean shutdown the endpoint removes it, if it still names this process. The endpoint's log, which §11 mentions under "Errors" and "The contract", is `<data>/.fractal-jdtls/<release>/endpoint.log`, beside the configuration area (§5); the launcher passes its path, with the port file, settings file, release and token descriptor, as `-Dfractal.jdtls.http.*` properties, and refuses a client's own.
  - **How a startup failure ends the process.** (T002.03's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Any failure the endpoint sees, from a missing system property to `initialize` failing or the stream check, is written to file descriptor 2 and the endpoint log, and the JVM halts with status 1 (`Runtime.halt`, not `System.exit`, so no shutdown hook can wait on the JDT LS that just failed). The activator never lets an exception reach Equinox, which would log it and start JDT LS without its client. In HTTP mode the launcher also checks that the Java has the `jdk.httpserver` module, which the bundle imports, before starting it.
- **The LSP settings belong to the harness (§1).** The harness passes them as a JSON file, `--http-settings <file>`. The endpoint sends them in `initialize` and answers `workspace/configuration` from them. The endpoint fixes only the settings its contract depends on, and the API documents those; the harness can't override them.
- **What the endpoint fixes.** A settings file that sets one of these to another value is refused at startup, with a message naming it. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 8.)
  - `java.autobuild.enabled: false` ("Keeping in step with the disk");
  - `java.configuration.updateBuildConfiguration: disabled`, since the endpoint sends changed POMs through m2e itself;
  - the client capability `workspace.applyEdit: false`, so commands such as organize imports return their edits instead of pushing them;
  - the client capability `workspace.didChangeWatchedFiles.dynamicRegistration: false`, so JDT LS registers no file watchers.
- **The agent is always added,** as in §5. The endpoint relies on the agent's naming and resolution.

### Security

- **Every request needs `Authorization: Bearer <token>`,** compared in constant time. A missing or wrong token gets `401` with no detail. The token is never logged or echoed back.
- **`Host` must be `127.0.0.1:<port>`.** Requests with an `Origin` header are refused, so a browser page can't reach the endpoint through DNS rebinding.
- **HTTP only, no TLS:** the traffic never leaves the machine.

### The contract

- **JSON over HTTP/1.1, versioned under `/v1/`.** Operations are `POST` with a JSON body. The `GET` calls take no session context: `/v1/status` and `/v1/openapi.json`.
- **The OpenAPI 3.1 description is the contract.** It's committed with the bundle, as `endpoint/src/main/resources/openapi.json`, and served at `/v1/openapi.json`. Fractal Harness generates its MCP tools from it, and a test fails if any route or error code is missing from it. Its descriptions are written for an LLM, because Harness passes them on as tool descriptions.
- **Every operation names its worktree and module, in the body:**
  - `worktree`: the absolute path of a registered worktree's root;
  - `module`: the folder holding the requesting Maven module's `pom.xml`, relative to that root (`harness-app`, or `.` for the root POM).

  Callers never see Eclipse project names. The endpoint maps the pair to the Eclipse project, and checks on every request that:
  - the worktree is registered;
  - the module's `pom.xml` exists;
  - its project is imported, and passed the import health check ("Worktrees");
  - the agent placed the project in that worktree.

  Any failed check is an error that says what to do. The last check catches a wrong nearest `.git`, such as a stray `/tmp/.git`, as a loud error instead of a silent mismatch.
  - **The checks in detail, and an operation that runs only them.** (T002.04's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) `POST /v1/modules/check` takes `worktree` and `module`, makes every check above and returns the module (path, GAV, packaging, state) and `waitedMs`; it changes nothing. T002.04 needed it to test the mapping before any operation that uses it exists, and the harness can use it to ask why a module can't be addressed. The checks, in order:
    - the worktree is registered, by its real path or as given (a deleted one has no real path), else `worktree-not-registered` with the registered ones as candidates; a worktree being removed counts as not registered;
    - its folder still exists, else `worktree-deleted`; its import didn't fail, else `import-failed`;
    - `module` is a relative folder (`.` or `/`-separated segments, none empty, `.` or `..`), else `invalid-request`; it holds a `pom.xml`, else `module-not-found` with the worktree's modules as candidates;
    - JDT LS has a project located exactly at that folder, else `module-not-imported`;
    - the nearest `.git` from the module's folder up is the worktree's own, and the project's name starts with the worktree's folder name and a dot (a `.git` nearer the module when it was imported, since removed, would have named it for another worktree), else `module-in-other-worktree`, naming the stray `.git`;
    - the project passes the import health check now, else `import-failed` for that module.
- **The module is where a request starts. Results never cross worktrees.** A search or rename covers the requesting module and the modules of the same worktree that depend on it. Results from other worktrees are never returned, and a refactoring never edits another worktree's files.
- **Every response that depends on code** carries `sync`, as described in "Keeping in step with the disk".
- **An optional `X-Fractal-Session` header** is recorded in the endpoint's log and nowhere else. The endpoint keeps no state per session.

### Errors

- **Every error is an RFC 9457 problem** (`application/problem+json`), written for an LLM. Its fields:
  - a stable `code` (for example `worktree-not-registered`, `module-not-found`, `ambiguous-member`, `text-not-found`, `text-not-unique`, `files-changed`, `not-ready`, `timeout`);
  - `title` and `detail`: what went wrong, in the caller's terms (worktree, module, Java names, files), never Eclipse's;
  - `hint`: what to do next;
  - `candidates`, when there's a choice to make, written so a candidate can be passed straight back. For example, every overload of an ambiguous method, with its parameter types;
  - `retryable`, and `retryAfter` in seconds.
- **The error catalogue** is part of the OpenAPI description. A test fails if a code that the endpoint can return isn't in it.
- **Unexpected failures** get `500` with code `internal`. The endpoint logs the stack trace and keeps serving; it never returns a stack trace.

### Addressing code

- **Declarations are addressed by Java name:**
  - a type: `com.acme.Foo`, nested types `com.acme.Foo.Bar`;
  - a member: `com.acme.Foo#bar`, or with parameter types `com.acme.Foo#bar(int,java.lang.String)` when it's overloaded;
  - a field: `com.acme.Foo#count`;
  - a package: `com.acme`.

  The rules:
  - **Nested types use `.`,** and `$` is accepted too (`com.acme.Foo$Bar`).
  - **Constructors use the type's simple name:** `com.acme.Foo#Foo(int)`.
  - **Parameter types are optional.** Without them, a name that matches several overloads is ambiguous. With them, the list is comma-separated, and whitespace is ignored. Each type may be simple (`String`) or fully qualified (`java.lang.String`).
  - **Type arguments are ignored** (`List<String>` matches `List`). Java can't overload on type arguments alone, so matching on the erasure loses nothing.
  - **Arrays are written `int[]`,** and varargs `String...`, which is the same as `String[]`.
  - **A field wins a name without parentheses.** `Type#size` is the field `size` if the type declares one; a method that shares a field's name is written with its parentheses, `Type#size()`. That's Javadoc's rule for `#name`, and it means every candidate resolves. (Changed by the governor on 2026-11-08 during T002.06's review, R3, from "a name that matches both a field and a method is ambiguous"; to review.)
  - **A simple parameter type that matches two types** (`Date`) is ambiguous; a fully qualified parameter type matches only that type, never one whose name merely ends the same way.
  - **Anonymous classes, lambdas and local variables have no name:** they're addressed by text anchors (below).

  An ambiguous name is an error that lists every candidate in the fully qualified form, which always resolves. (Syntax decided by the planner on 2026-11-07, as Chris delegated; to review.)
- **How names resolve.** Types come from a JDT `SearchEngine` type-declaration search, scoped to the sources of the worktree's Java projects, which never returns another worktree's copy of a type (a workspace-wide scope found all three worktrees' copies). Members are matched on the `IType` model, with the endpoint's own comparison of erased parameter types, each resolved in the declaring type (`IType.resolveType`). JDT's own method patterns miss varargs (`String...`), constructors written `Type#Type(…)`, and fields. So names address declarations in the worktree's sources, and library elements appear in results; read-only operations can also name library elements (below). Measured: the first search of a session took 3.6 s, while the indexes were built, and later ones 27–231 ms. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 11.)
  - **Library and JDK names, for read-only operations.** If a name matches nothing in the worktree's sources, the read-only operations (definition, references, implementations, the hierarchies, `describe`) also look it up in the requesting module's own classpath (its Maven dependencies and the JDK), as a second scope, still within that worktree's projects. So `describe` on `java.lang.String#join` works without a text anchor. Candidates from the classpath say so in `about`. Refactorings and edits only ever address the worktree's sources. (Decided by the governor on 2026-11-08 after T002.02, in place of T002.02's decision 10; to review.)
- **Code without a name** (a local variable, an expression, statements to extract) is addressed by a file, relative to the module, and `text`: the exact source text, which must occur exactly once in that file, or once within a named member. It's the same idea as an editor's `old_string`. Text found nowhere, or more than once, is an error that shows where it was found.
- **Positions appear only in the LSP passthrough.**

### Keeping in step with the disk

Stability comes before speed. Sessions edit files with their own tools and with shell commands (`git checkout`, `sed`, generated sources), so the endpoint can't be told about every change, and a missed change is silent staleness: FINDINGS run 07 showed diagnostics that were stale and wrong at once. T001.06's review finding R1 showed that waiting for the server to go quiet is a race. So:

- **No file watcher and no timing heuristics.** inotify has watch limits, can overflow and drop events, and doesn't work on WSL2's `/mnt` paths.
- **The endpoint reconciles with the disk at fixed points.** Before every operation that depends on code, for the requesting module's worktree:
  1. the fast path: if nothing in the worktree changed, go straight to the answer (below);
  2. refresh the worktree from disk with Eclipse's `refreshLocal`, under the workspace rule;
  3. send changed POMs through m2e's project update;
  4. run an explicit incremental build;
  5. join the work the fixed point scheduled;
  6. answer.

  This held in T002.01: run 05's errors came out 20 times out of 20 in one process, and 20 out of 20 in fresh processes on fresh copies (HTTP-FINDINGS question 5).
- **The refresh scope is the worktree, for queries too.** (T002.02's proposal, from HTTP-FINDINGS "Recommendations"; approved by the governor on 2026-11-08 under Chris's delegation; to review.) §11 had "the requesting module for queries", and left that scope to the spike.
  - A module-only refresh is about 85 times cheaper on the large tree (3.9 ms against 330 ms). But it misses changes in the modules a query depends on, or that depend on it, so a definition, references search or rename that reaches another module of the same worktree would answer from stale state. Stability first, so the whole worktree, with the cost in `sync`.
  - If the cost matters on the real reactor (T002.05 re-measured it on the large tree: "If refreshing proves too slow", below), one narrowing stays deterministic: the requesting module plus its dependencies and dependents in the same worktree, from m2e's registry.
- **What `changedPaths` does.** (T002.02's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The harness may also name the paths it changed (`changedPaths`). §11 said they narrow the refresh, but with the worktree as the scope (above) there's nothing to narrow. Instead, each named file is taken in even if its modification time didn't change, and a request that names any never takes the fast path. They never replace the refresh.
- **The fast path.** Before the refresh, the endpoint checks every project of the worktree with `IResource.isSynchronized(DEPTH_INFINITE)`, and runs its own check for changes that keep their modification time (below). `isSynchronized` takes no rule, and finds files changed, added or deleted on disk; it makes the same timestamp comparison as `refreshLocal`. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 15.)
  - If every project is in sync, and the endpoint has seen no change to the worktree inside Eclipse since its last full fixed point, it skips the refresh, the build and the join, and reports `sync.skipped`.
  - "No change seen" is a mark per worktree. A resource-change listener clears it on any change other than markers and build output. The fixed point sets it under the workspace rule, before its refresh, so a change that lands during the fixed point clears it again.
  - Measured: the check cost 3.8 ms on the fixture's worktree (3 projects), and 246–251 ms on the large tree. With it, a complete operation on an unchanged worktree took about 12 ms (562 operations, the slowest 65 ms) during another worktree's import, and about 10 ms during its full build.
  - **The mark and the check, exactly.** (T002.05's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The fixed point holds the workspace root rule itself (`IJobManager.beginRule`) from before its refresh until its build ends, with each step an `IWorkspace.run` inside it. Eclipse delivers an operation's resource changes before it releases that operation's rule, and nothing else can change a resource while the root rule is held, so every change delivered while the fixed point holds it is the fixed point's own, or was made before it and its build covers it. Those changes are its `filesChanged`, and they don't clear its mark; any other change to the worktree's files does, except markers, build output (a derived resource, or `target` beside a `pom.xml`) and `.git`. A worktree whose fixed point is still running, its join included, never takes the fast path, and reports `notSkippedBecause: eclipse-changed` (the description says so). The check reads the endpoint's own record first, the cheaper of the two, which the refresh then reuses, and calls `isSynchronized` only if the record is unchanged. A worktree's first fixed point after an add or a restart is `first`, and never skipped.
    - **A lock per worktree, around the check and every answer.** (T002.05's review proposal, R2, R3; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Each worktree has a fair read-write lock. The fast path's check, and the reading of its answer, hold it to read; a fixed point holds it to write from before it takes the workspace rule until its join ends, then holds it to read while its own answer is read. So a fixed point that starts after a fast path's check waits for that request's answer, a request that arrives during a fixed point waits for it and only then checks, and no answer is read while a fixed point, a `clean: true` one included, changes the worktree's markers. Before, a fixed point that started during a check was missed, and its markers could be read half made. The wait counts toward the request's deadline (phase `waiting-for-rule`). The deadline is also checked after the fast path's check and after the answer is read, so a request whose time ran out during them gets `timeout`, not a late answer: on the large tree, a `problems` with a `timeoutMs` of 100 got `timeout` in `syncing` after its 541 ms check. In the gate's test, 20 `problems` asked during 5 clean builds of wt-a all waited, 114–177 ms, and all got run 05's 3 errors.
- **Autobuild is off.** The endpoint fixes `java.autobuild.enabled: false` ("Launching"). Each fixed point that refreshes runs an incremental workspace build (`IWorkspace.build(INCREMENTAL_BUILD)`), then the join. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 8 and question 5.)
  - **Both settings gave run 05's errors every time.** Joining autobuild cost 994–1,111 ms a fixed point on the fixture, almost all of it `AutoBuildJob`'s delay of up to 1 s after a recent build. The explicit build cost 105–163 ms, and nothing builds between fixed points.
  - **A build of only the worktree's projects** was no more exact than the workspace build.
  - **Without a build, there are no markers** (the spike's control), so a fixed point that refreshes must build.
  - **The join waits for `AutoBuildOffJob` too.** (T002.05's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) With autobuild off, Eclipse still schedules "Sending build events with disabled autobuild" (`AutoBuildJob$AutoBuildOffJob`, in the auto-build family, with the root rule) after an operation that changes the tree, with autobuild's delay, to send the pre- and post-build events. It's of a kind the join waits for while it sleeps, so a fixed point that refreshes waits for it: up to 148 ms on the fixture and 8–144 ms on the large tree, most of a fixed point's join. It changes no markers, so not joining it would save that time, but it holds the root rule and runs after the fixed point's build; the join is kept as "Joining the work" says.
- **Taking in changes exactly.** (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 5.)
  - **Eclipse's lightweight auto-refresh is off in HTTP mode** (`refresh.lightweight.enabled: false`). It refreshes a file that something reads while it's out of sync, so with it on, 4 to 10 fixed points in 20 found fewer files changed than were written; with it off, none did. The markers were right either way. The report of what changed wasn't, and a POM change found only through the delta could be missed.
    - **How it's turned off.** (T002.05's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) JDT LS has no setting for it, and Eclipse's resources plugin reads the preference once, when the workspace opens, from every scope, then listens only to the instance scope (`FileSystemResourceManager`). An instance-scope value would be saved under `-data` and reach a later plain-mode start. So in HTTP mode the launcher passes `-Declipse.pluginCustomization=<release>/lib/http-mode-preferences.ini`, a shipped file whose one setting is `org.eclipse.core.resources/refresh.lightweight.enabled=false`. Equinox applies it as a default before the workspace opens, and never writes it anywhere. The launcher refuses a client's own `-Declipse.pluginCustomization` and `-pluginCustomization`. The file is in `release-files.json` and verified like the rest of the install (§2's `lib/` gains it, as it gained the endpoint jar). After `initialize`, the endpoint refuses to start if the preference is still on: a workspace's own instance-scope value would win over the default.
  - **POM changes are found by content too.** The endpoint keeps a hash of each registered worktree's POMs, and compares them at each fixed point. JDT LS's own jobs refresh POMs as well (`MavenProjectImporter`, "Update project"), so a change seen only through the delta can be missed.
  - **A resource filter for `.git`** goes on each worktree's projects when the worktree is added, so a main checkout's refresh neither walks nor reports Git's internals. JDT LS's default filter (`java.project.resourceFilters`) is applied only when that preference changes, so projects imported later don't get it. Without the filter, `main`'s refresh found `.git/index` and `.git/worktrees/*/index` changed after Git ran in the linked worktrees.
    - **The filter, and when it goes on.** (T002.05's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) A regex filter on the name, `^(\.git|__CREATED_BY_FRACTAL_JDTLS_ENDPOINT__)$`, excluding files and folders and inherited by subfolders (JDT LS's own filter's flags), on each project of the worktree that lacks it: after an add and its health check (and repair), after a restart's check of each saved worktree, and at each fixed point, for projects made since. The second name tells it apart from JDT LS's filter, which JDT LS deletes and makes again when its preference changes. The anchors keep `.gitignore` and `.github` in. It's made with no update flags: JDT LS makes its own with `BACKGROUND_REFRESH`, a refresh in a job nothing joins, and in T002.05's first gate one ran after a worktree's folder was deleted from disk and deleted two of its projects. The filter applies from the next refresh, the worktree's first fixed point.
  - **Changed POMs go through m2e's internal multi-project update,** `ProjectConfigurationManager.updateProjectConfiguration(request, true, true, monitor)`, as JDT LS does. The public method throws `IllegalArgumentException` for more than one POM.
- **Joining the work,** without timing. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposals 4 and 16.)
  - **A barrier.** After the requests and notifications that a fixed point or a worktree change sends, the endpoint sends a request JDT LS can't answer, `fractal/barrier`, which gets error `-32601`. lsp4j handles messages in order on one thread, so that answer proves the earlier messages were handled and their jobs scheduled.
  - **A mark.** A job-change listener records the order in which jobs are scheduled. The fixed point takes a mark when it starts.
  - **Rounds of joins,** until a round finds none. Each round joins every job scheduled after the mark that is running or waiting to run, or sleeping if it's an `AutoBuildJob` or an m2e background-queue job (`IBackgroundProcessingQueue`).
  - **Never an implicit job** (`ThreadJob`, a thread that holds a rule outside a job): a join on one never returns, and the spike's hung until its 600 s guard. The jobs that thread schedules are joined once it lets go.
  - **Never JDT's indexer progress job:** JDT search waits for the indexes it needs, and joining "Java indexing…" cost up to 5 s for nothing.
  - **Why not families, or every job.** JDT LS schedules some jobs with no family, such as `MavenProjectImporter`'s "Update Maven project configuration" on a restart. A join by family missed it, `shutdown` then cancelled it, and JDT LS exited with code 1. Joining every running or waiting job waited 27.3 s for another worktree's whole import. Joining only what the fixed point scheduled waited 6.9 s, the wait for the rule.
  - **Every join has a long guard timeout** that reports loudly.
  - **A join waits for the end of the run it found, never the job's next run.** (T002.04's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) In 1 of 3 runs of the same steps, removing a worktree took 301 s, not 0.7 s. Eclipse's "Periodic workspace save" (`DelayedSnapshotJob`) ran during the removal, so a round found it running, but by the time the join reached it, it had finished and rescheduled itself for its 300 s interval, and `Job.join` waits for a sleeping job's next run. So the endpoint doesn't call `Job.join`: it listens for the job's own `done` event, added before it reads the job's state so none is missed, and counts a job that has ended, or gone back to sleep, as joined. The exception is the kinds joined while they sleep (`AutoBuildJob` and m2e's background queue), which are waited for until they run. It's still no timing: the job's event says its run ended. A JUnit test, with Eclipse's own job manager, puts a job in exactly that state; the old join times out on it, and the new one returns at once. A join that lasts more than 10 s is logged every 10 s, naming the job, its state and the other jobs, which is how this one was found. After the fix, 5 runs of the same steps removed in 0.6–1.1 s, joining the save job in 0–18 ms where it had taken 299,968 ms.
- **Problems come from Eclipse's markers,** read after the build has been joined. Diagnostics that JDT LS pushed earlier are never used.
  - **Reading the markers.** (T002.05's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The problems are the markers of type `IMarker.PROBLEM`, subtypes included, on the module's project, or on every project of the worktree, with duplicates dropped. `kind` comes from the marker's type: `org.eclipse.jdt.core.problem` is `java`, `org.eclipse.jdt.core.buildpath_problem` is `build-path`, m2e's `org.eclipse.m2e.core.maven2Problem*` are `maven`, and the rest `other`. The line is the marker's; the column comes from its character offset, counted in the file's text in the file's charset, as JDT counts characters, and the end is exclusive, the column just after the last character. `source` is that line's text. `element` is the enclosing declaration's `JavaName`, from JDT's model (`ICompilationUnit.getElementAt`); a problem on an import, or on the file as a whole, names the file's primary type, and anonymous and local types and lambdas are named by their enclosing declaration. `counts` cover every problem in scope; the list is sorted by module, file, line, column and message.
- **Every such response reports `sync`,** so the cost and any drift are visible. (The fast path and the rule wait: decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposals 14 and 15.)
  - whether the fast path skipped the fixed point, and if not, why;
  - the files found changed, and the POMs updated;
  - the milliseconds spent on the fast-path check, waiting for the workspace rule, refreshing, updating POMs, building and joining.
  - **What `filesChanged` leaves out.** (T002.05's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) With metadata files kept out of the worktrees ("Worktrees"), JDT LS keeps each project's `.project`, `.classpath`, `.factorypath` and `.settings/` under `-data`, but Eclipse's tree shows them at the project's folder. The first fixed point after the large tree's import found 301 files changed, 300 of them these. They aren't the worktree's files, so the report leaves them out, as it leaves out build output and `.git`. They still clear the mark, because a `.classpath` change can need a build.
- **Changes that keep their modification time** (`cp -p`, `rsync -a`, `tar x`, `touch -r`, two writes within one millisecond) are invisible to Eclipse's refresh, which compares millisecond modification times (HTTP-FINDINGS, "Constraints and risks"). Stability comes first, so the endpoint keeps its own record of each file's status-change time (nanoseconds), size and inode from the last fixed point, finds files whose record changed while their modification time didn't, and makes Eclipse take them in. The same check is part of any fast path that skips the refresh. T002.05 built it; its cost is below. (Decided by the governor on 2026-11-08 after T002.01, under Chris's delegation; to review.)
  - **How they're found and taken in.** (T002.05's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The record covers every regular file under the folders of the worktree's projects, walked without following links, except `.git` and Maven build output (`target` beside a `pom.xml`): its modification time, status-change time (both in nanoseconds), size and inode. It's taken before the refresh, under the rule, or by the fast path's check just before, so a change after it shows up at the next fixed point. A file that's new, or whose record changed, and that the refresh didn't report, is taken in with `IResource.touch`, which changes only Eclipse's own record of the file (its content id and modification stamp) and fires a content change, so the build compiles what's on disk. The file itself is never written, and its times never set: the tests compare each file's bytes, size, inode, modification and status-change times before and after the `build` that took it in. `changedPaths` go through the same `touch`. A needless touch only recompiles one file. Measured: the record of the large tree's 10,053 files took 105–175 ms.
  - **The record survives restarts, and a missing one means a clean build.** The endpoint saves each worktree's record under `-data` beside its worktree state, written atomically after each fixed point, so a restart compares against it and finds changes made while JDT LS was stopped, those that kept their modification time included. A worktree with no saved record (a crash before the first save, a damaged file) gets a clean build of its projects at its first fixed point, which is reported in `sync`; an add needs none, because its import builds everything. (Decided by the governor on 2026-11-08 during T002.05's review, R1; to review.)
    - **Where the record is, and when it's taken.** (T002.05's review proposal, R1; approved by the governor on 2026-11-08 under Chris's delegation; to review.) It's saved in `<data>/.fractal-jdtls/records/<first 16 hex digits of the SHA-256 of the worktree's path>.json`, beside `worktrees.json`: `{"version": 1, "worktree": <path>, "files": [[<path relative to the worktree>, <mtime ns>, <ctime ns>, <size>, <inode>], ...], "poms": {<relative path>: <SHA-256>}}`, written to a temporary file and moved into place after each full fixed point. That took 0.3–2 ms on the fixture and 25–48 ms on the large tree (about 1 MB). A file that can't be read, or names another worktree, counts as none. An add takes the worktree's record, and saves it, just before its folder change, so a change made during the import or before the first fixed point, even one that keeps its modification time, differs from it; what came before, the import builds. Removing a worktree deletes its record. A clean build for a missing record is reported as `sync.cleanBuild: no-saved-record`, and `clean: true` as `requested`. In the gate, a `cp -p` change made while JDT LS was stopped was found by the restart's first fixed point with the record (`filesChanged`, and its error), and, with the record deleted, by that fixed point's clean build; the other two worktrees, whose records were there, weren't cleaned.
- **If refreshing proves too slow** on a real-sized tree (T002.01 and T002.05 measure it), the numbers go to Chris. The endpoint doesn't quietly switch to a watcher.
  - **`refreshLocal` with nothing changed,** on WSL2's ext4: one module took 1.0 ms on the fixture and 3.9 ms on the large tree (200 files), and one worktree 6.7 ms and 330 ms.
  - **A whole fixed point on the large tree after one edit,** with the explicit build: 442–494 ms for the worktree.
  - Not measured on WSL2's `/mnt` paths, which are far slower.
  - T002.05's measurements (reviewed by the governor on 2026-11-08; no change). A worktree refresh stays under a second on the large tree, so nothing is raised, but the fast path's check now costs about twice the spike's. On the large tree, 10 times each in the gate: the fast path's check took 442–623 ms (`isSynchronized` 332–435 ms, the record 105–175 ms), against the spike's 246–251 ms without the record; a `build` with nothing changed 559–632 ms, its refresh 462–483 ms (`refreshLocal` 342–417 ms); `problems` after one edit 579–721 ms. On the fixture: the fast path 5–16 ms, a fixed point after an edit 108–175 ms, and one with a POM change 334 ms (m2e's update 254 ms). The narrowing above (the module, its dependencies and its dependents) would cut both, deterministically, if the real reactor needs it.

### Worktrees

- **Worktrees are added and removed at runtime,** as sessions need them (`POST /v1/worktrees/add`, `/remove`, `/list`). The endpoint sends `workspace/didChangeWorkspaceFolders` and waits until the import is done, or returns `not-ready` with `retryAfter` if the caller asked not to wait.
  - JDT LS schedules its "Updating workspace folders" job (`ProjectsManager$2`, under the workspace root rule) inside the notification's handler, so the barrier ("Joining the work") proves it's scheduled, and the join waits for it.
  - Measured: adding the fixture's main checkout and `wt-a` took 3.6 s (8.8 s with an empty Maven repository), adding `wt-b` 1.1 s, and adding the large tree 7–27 s. Removing took 1.4–1.5 s.
- **Adding is refused** when the folder isn't a Git worktree root, or when its folder name is already used by a registered worktree (§10).
- **Nested worktrees are refused, in either direction.** A worktree inside a registered worktree, or one that contains a registered worktree, can't be added: JDT LS's folder removal deletes every project under the removed root, and its import finds every POM under it, so nested worktrees can't be kept apart. The problem names the registered worktree it overlaps. Fractal Harness's worktrees are siblings (workmux's `<repo>__worktrees/`), so this costs nothing there. (Decided by the governor on 2026-11-08 during T002.04's review, R2; to review.)
- **Removing deletes the worktree's Eclipse projects without deleting their files,** and leaves nothing of them in m2e's registry. A worktree already deleted from disk can still be removed.
  - JDT LS deletes the projects with `project.delete(false, true)`, then deletes every project outside the remaining folders (`cleanInvalidProjects`). That's correct while every project belongs to a registered worktree.
- **Restart.** The endpoint keeps its registered worktrees in its own state under `-data`, and passes them in `initialize` as `workspaceFolders`. A restart then creates no projects, and keeps the names and classpaths, as in FINDINGS run 06. Starting with no folders and adding them later would make JDT LS delete every project at startup (`cleanInvalidProjects`, with only `-data` as a root), and create them all again. A saved worktree whose folder is gone is left out of `initialize`, dropped from the state, and reported in the status. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 6.)
  - **Where the state is, and what a restart does with it.** (T002.04's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The state is `<data>/.fractal-jdtls/worktrees.json`, `{"version": 1, "worktrees": [{"worktree": "<real path>"}]}`, written atomically whenever the set changes. It isn't per release, unlike the configuration area and the log: the worktrees belong to the Eclipse workspace, which every release on that `-data` shares. The launcher passes the path as `-Dfractal.jdtls.http.state`, like the endpoint's other files. JDT LS reads the folders from `initializationOptions.workspaceFolders` (URIs), not from `workspaceFolders`, which it ignores (`BaseInitHandler`), so `initialize` carries both. A saved worktree is dropped when its folder is gone, when it no longer holds `.git`, or when another saved one has its folder name. A damaged file stops startup with the reason, rather than starting with no worktrees, which would make JDT LS delete every project. After `ServiceReady`, the restart's check joins every job still running or waiting (nothing else may run yet), then checks each worktree's health, with the same one repair as an add. It's announced before the HTTP API listens, so requests that come after `ready` still wait for it. Measured on the fixture: the join took 1.7–5.6 s, most of it JDT LS's "Check JDK Index" job, which is joined like any other.
- **Listing** returns each worktree with its modules (path, GAV, import state), so the harness can check what the endpoint sees.
- **Imports run alone, for now.** While a worktree is being added, every other request that reaches JDT LS waits, or gets `not-ready` with `retryAfter`, until the import and its health check are done. In T002.01, 5 of 22 large-tree imports with requests running during them silently broke one module, and 0 of 9 without (HTTP-FINDINGS, "An import that silently broke"). (Decided by the governor on 2026-11-08 after T002.01, under Chris's delegation; to review.)
  - **Every worktree change runs alone, and none is cancelled.** (T002.04's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) A removal, and the restart's check, run alone too, like an add: each is announced when it's accepted, from then on new requests that reach JDT LS wait, and it starts once the requests already running are done. Changes run one at a time, in order, on one thread. A removal takes 0.7 s on the fixture, and running it alone keeps the rule simple: no request ever sees a worktree change half done. `not-ready`'s `reason: importing` covers all three, and its `detail` says which. A change that has started is never cancelled: cutting short a folder change, or its repair, would leave JDT LS's projects half made. So `timeoutMs` on `worktrees/add` and `/remove` bounds only the caller's wait: when it passes, the answer is `not-ready`, the change carries on, and adding the same worktree again waits for it. Those two operations no longer list `timeout`. `worktrees/list` and `GET /v1/status` read the endpoint's own state, so they never wait; `status` shows the change in progress (`importing`) and the requests waiting for it (`inFlight`, phase `waiting-for-import`).
- **Import health is checked after every add and every restart.** Each module's project must be at the module's own folder, with an m2e facade and the Java nature. If one fails, the endpoint makes one repair (removing and adding the worktree again, which repaired every broken import in T002.01). It reports the repair loudly in the response, the status and its log. If the repair fails too, the worktree's modules report `import-failed`. The import is never reported as done while a module fails the check. Finding the cause is not part of T002; it's recorded as a risk. (Decided by the governor on 2026-11-08 after T002.01, under Chris's delegation; to review.)
  - **What "every module" is, and what the check reads.** (T002.04's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The modules are found as JDT LS's Maven importer finds them, with its own classes: the topmost `pom.xml` folders under the worktree (`BasicFileDetector`, not nested, `target` and JDT LS's import exclusions skipped), then each one's reactor through m2e's `LocalProjectScanner`, which follows `<modules>`. For each, the project must be located exactly at the module's folder, be open, have an m2e facade, and have the Java nature unless its packaging is `pom` (m2e gives a `pom` project no Java nature). The GAV and packaging come from the facade, else from the POM. The repair is two folder changes, a removal then an add, each with its barrier and join.
    - **The endpoint also reads the POMs itself.** (T002.04's review proposal, R1; approved by the governor on 2026-11-08 under Chris's delegation; to review.) m2e's scanner leaves out a POM it can't parse, and only reports why, so the endpoint also follows `<modules>` (the project's and each profile's) from the same top folders with the JDK's XML parser, with no external entity or DTD loaded. A module either finds is a module. One whose POM can't be read keeps the parser's reason, fails the check (no project, or no facade), and its failure quotes the reason. A malformed root POM and a malformed child both end in `import-failed`.
  - **A POM that m2e can't read fails the check too.** (T002.04's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) A module whose parent POM can't be resolved never gets an m2e facade or the Java nature, however often it's imported, so the repair can't help, and the worktree reports `import-failed`. That's correct by the rule above (the import is never reported done while a module fails), but the cause is the user's POM, not JDT LS, so the failure quotes m2e's error markers on that `pom.xml`, and the problem's `hint` says to fix them, then remove and add the worktree. Finding this before the repair would save its 1.3 s, but would mean telling a POM error from the silent breakage the repair exists for; not done.
- **No metadata files in worktrees.** In HTTP mode, the launcher passes `-Djava.import.generatesMetadataFilesAtProjectRoot=false`, so JDT LS writes no `.project`, `.classpath` or `.settings/` into the worktrees, sessions' `git status` stays clean, and removing a worktree leaves nothing behind. The endpoint's contract depends on it, so the harness can't override it, and the launcher refuses a conflicting `--jvm-arg`. T002.04's import health check runs with it in place. (Decided by the governor on 2026-11-08 after T002.01, under Chris's delegation; to review.)

### Builds and problems

- **`build`** reconciles the worktree with the disk, runs an incremental build, and returns the requesting module's problems, and optionally the worktree's. Problems can be filtered by severity. Each problem has: file, 1-based line and column, severity, message, and the source line.
- **`problems`** returns the same after reconciling with the disk.
- **What tells `build` and `problems` apart, with autobuild off.** (T002.02's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) §11 had `problems` "without forcing a build". But with autobuild off, every fixed point that refreshes also builds, because markers come only from a build. So the difference is:
  - **`problems`** runs the ordinary fixed point, which takes the fast path when nothing changed;
  - **`build`** never takes the fast path: it always refreshes, checks the POMs, builds and joins. With `clean: true`, it first cleans the worktree's projects, for build output that might be stale.

### Refactorings and edits

- **JDT LS computes a refactoring as a `WorkspaceEdit`** (text edits per file, plus file creates, renames and moves). The LSP client applies it, and here the endpoint is the client. The harness never applies edits.
- **Applying edits:**
  1. reconcile the worktree with the disk;
  2. take the baseline: the state of the worktree's files at that fixed point, which is what JDT computes the edit from;
  3. compute the edit;
  4. under the workspace lock, check that every affected file still matches the baseline, and is in sync with Eclipse's view (`IFile.isSynchronized`);
  5. write the files;
  6. refresh, build, and return a unified diff and the resulting problems.

  If a file changed in between, it's `files-changed`, and nothing is written. `dryRun: true` returns the diff without writing. Git is the undo.
- **The baseline is taken before the edit is computed.** Taken afterwards, it would accept a file that changed during the computation, and the edit's offsets would then overwrite the newer content. The spike's baseline was a sync, then a hash of every file in the worktree. The endpoint's own record of each file's status-change time, size and inode ("Keeping in step with the disk") would serve the same purpose without reading every file; T002.07 chose the record, and measured both ("The baseline, and the apply as one fixed point", below). In the spike, a line that another session inserted after the edit was computed was refused by both checks, and nothing was written. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 18.)
- **What JDT LS returns.** `textDocument/rename` returns a `WorkspaceEdit` with both `changes` and `documentChanges`. The endpoint applies `documentChanges` when they're present, as the spike did. A rename of a type also renames its file, and file operations reach the endpoint only in `documentChanges`. With the client capability `workspace.applyEdit: false`, commands such as organize imports return their edit as the result.
- **T002's refactorings:**
  - rename of a type (with its file), method, field, local variable or package;
  - organize imports;
  - extract local variable, extract constant, extract method;
  - inline local variable.

  Choices that JDT LS asks the user for interactively become request fields.
- **Which engine computes each refactoring.** (T002.07's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Each runs JDT LS's own engine directly, under the worktree's read lock after the fixed point, rather than its LSP handler, because each handler drops something the contract needs:
  - rename: JDT LS's `RenameSupport` with the flags its `textDocument/rename` handler uses (references, and a renamed field's getter and setter), checked with all conditions, and converted by its `ChangeUtil` into the `WorkspaceEdit` with file operations. The handler refuses only a fatal status, so a rename JDT rates an error, such as a clash with an existing method, would be written; the endpoint refuses every error;
  - organize imports: JDT LS's `OrganizeImportsHandler.organizeImports`, with a chooser that answers from the request's `choices` instead of asking the client; a simple name with no choice is `ambiguous-import`, whose candidates set `/choices/<name>`, and a choice that isn't one of its types is `invalid-request`;
  - extract local variable, extract constant, extract method and inline local variable: JDT's LTK refactorings (`ExtractTempRefactoring`, `ExtractConstantRefactoring`, `ExtractMethodRefactoring`, `InlineTempRefactoring`), the engines of JDT LS's `java/getRefactorEdit`, with the requested name set before the change is made (§11 decision D6: the name arrives in the one edit, checked against one baseline; no second rename). The handler names the new element itself (`extracted`), checks only the initial conditions, and returns nothing, without a reason, when they fail;
  - a refusal quotes JDT: an error in the initial conditions, which are about the selection, is `not-applicable`; an error in the name's check or the final conditions is `refactoring-refused`. JDT's warnings come back in `warnings`, and don't stop it. Nothing is ever half applied.
- **The baseline, and the apply as one fixed point.** (T002.07's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The baseline is the worktree's record as the fixed point before the computation left it (each file's status-change time, size, inode and modification time, which the fixed point takes anyway), plus each affected file's bytes, read right after the edit is computed and required to be exactly the text JDT computed it from (the compilation unit's buffer), else `files-changed`. The apply is one more fixed point: under the worktree's write lock and the workspace root rule, each file the edit reads must still have its baseline record, its bytes and `IFile.isSynchronized`, and each file it creates must still not exist, else `files-changed` and nothing is written; then the writes, the refresh, the build and the join, before the problems are read under the read lock. No other request sees a half-applied edit. The record costs nothing more than the fixed point already does; hashing every file, the spike's baseline, took 134–467 ms per refactoring on the large tree (10,053 files, 4.1 MB), against 105–293 ms for the record. The check itself took 0.12–0.43 ms on the fixture.
- **Writing all or nothing, and `write-failed`.** (T002.07's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Every file is written in place (keeping its inode, owner and permissions), in its own charset and byte order with its byte order mark, decoded and encoded again as JDT reads it (UTF-16 and UTF-32 in either byte order, with or without a mark), and nothing outside the edit's text changes; a rename moves the file first, never over an existing one, and a package's emptied folder is removed (never a module's or source folder). Every file an edit reads, writes, creates, moves or deletes is checked by its real path (symbolic links resolved; for a file that doesn't exist yet, its nearest existing folder's) against the worktree's real root, when the edit is computed and again at the apply: outside it is `edit-outside-worktree`, nothing written. A file the edit would make, and so change or delete as its own (JDT LS's package rename makes a `.temp` file in the new package's folder, `ignoreIfExists`, and deletes it at the end), that already exists is `refactoring-refused`, naming it, nothing written: the endpoint never deletes a file the edit didn't create or JDT didn't ask to delete as its own. (These three: T002.07's review, R1, R2 and R5, decided by the governor on 2026-11-08.) Each step is journaled in memory, while the process lives (a crash is left to Git and the agent: "Operation folders"); if one fails, every step already taken is undone, newest first, to the exact earlier bytes, and the answer is a new code, `write-failed` (409), whose `detail` has the system's error and says if anything couldn't be put back. A file that isn't valid in its charset is `refactoring-refused`. The deadline is checked after the files are checked, immediately before the first write (`timeout` with `phase: applying`, nothing written; T002.07's review, R4), and the diff, whose memory is linear in the files' size, is made while the edit is computed, under the deadline (R3); once written, the apply isn't cancelled, so its answer always reports what it wrote. An edit that changes nothing isn't applied (`applied: false`).
- **An edit outside the worktree is `edit-outside-worktree`,** (T002.07's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) as the contract has it (422, `files` listing them, nothing written), not `internal` as T002.07's task said: the contract, written after the task, made it its own code so the harness can tell it from other defects.
- **The diff stays Myers' linear-space search** over the files' lines, with its deadline checks (T002.07's review, R3). Building it from JDT's own edits instead was considered (no search, cost in proportion to the change) and set aside while the search measures well: 0.8 s and 32 MB for a 12,000-line rename. T002.11 didn't measure the search on its own; in its 10-minute soak a rename's median was 338 ms, dry runs and applies together, and it wasn't among the hot spots it reported. (Decided by the governor on 2026-11-08; to review.)
- **Each refactoring is recorded in an operation folder** the endpoint creates (next section), and an apply can optionally be checked against its dry run.
- **Later series:** move, change signature, the rest of JDT LS's code actions, quick fixes and source generation, then the refactorings Eclipse has but JDT LS doesn't expose (pull up, push down, encapsulate field), through LTK.

### Operation folders

(Chris's design, 2026-11-08, from the governor's minimal proposal v5; T002.10. Larger variants, with journals, recovery and saved plans, are parked as future proposals, not part of this design, in [.context/future/operation-folders/](future/operation-folders/README.md).)

JDT LS provides semantic code operations; Fractal Harness manages worktrees and recovery; agents handle ordinary engineering failures; Git is the recovery mechanism. Chris chose operational simplicity over transactional guarantees. So a refactoring is a blocking call that leaves an inspectable record, an apply can optionally be checked against its dry run, and there is no transaction journal, backup, automatic rollback, writer coordination or crash-recovery protocol.

- **A blocking call.** Every refactoring is one HTTP request that answers only after the apply has finished: the writes, the refresh, the build and the problems ("Refactorings and edits").
- **An operation folder per refactoring.** Once the request's first fixed point is done (so the folder's own files don't make that fixed point a full one; decided by the governor after T002.10's measurements), the endpoint makes `<worktree>/temp/fractal-jdtls/<id>/`. It generates the ID itself, `<UTC time to the millisecond>-<8 random hex digits>` (for example `20261108T235501.123Z-3f9a2c41`), so folders sort by time; the caller neither supplies nor needs it. The folder is created exclusively (on the rare clash, a new random part), and its real path must be exactly `<the worktree's real root>/temp/fractal-jdtls/<id>` (`edit-outside-worktree` otherwise), so a `temp` that links anywhere, outside the worktree or inside it, is refused: the endpoint never writes outside the worktree, and its records are always where the record's skip expects them (T002.10's review, R2).
- **What it holds, written in this order:**
  1. `request.json`: the time it was received, the operation (`refactor/rename`, …), and the request body (worktree, module and arguments; the token is never in it);
  2. `diff.patch`: the full unified diff, as soon as the edit is computed, before any source file is written;
  3. `response.json`: the final answer, success or problem, written to a temporary name in the folder and renamed, so a reader never takes half a file for the answer.
- **Finding an outcome after a crash or disconnect.** An agent or its harness that didn't get the answer looks at the worktree's recent folders, matching `request.json`'s details and time. `response.json` is the outcome. **Without `response.json`, the outcome is unknown** by the files alone: that proves neither that JDT LS stopped nor that the operation failed; `/v1/status` says whether it's still running (below). `diff.patch` shows which files to look at, and Git shows what changed. There's no lookup operation; the files are the interface, plus one fact only the process knows: whether the operation is still running.
- **Is it still running?** `GET /v1/status` lists each refactoring in flight with its ID (`operation`). The ID is in the in-flight list before the folder is created, and leaves it only after `response.json` is written, so there's no moment when a running operation looks stopped. IDs are never reused, and a worktree has one JDT LS process (§10), so the worktree's current process answers for it; after a restart the old process is gone, and nothing it started can still be running:

  | `response.json` | ID in `/v1/status`'s operations | Meaning |
  |---|---|---|
  | present | — | finished, with that answer |
  | missing | yes | still running: wait |
  | missing | no | stopped without answering: check the files `diff.patch` names, and Git |

- **The answer** to a successful request carries `operation` (the ID) and `operationFolder` (the folder's path relative to the worktree), for convenience.
- **An optional dry-run check.** Every refactoring's answer carries `writeSetDigest`: a SHA-256 over the prepared write set, as a deterministic, length-framed sequence of entries, one per file operation in order, each `(kind, path, from, result bytes)` with paths relative to the worktree, `from` only for a move or rename, and no bytes for a delete (so a delete differs from an empty file). An apply may send `expectWriteSetDigest`: the endpoint computes the edit as always, and if the digest differs, writes nothing and answers `edit-changed` (409), with the new diff, so the caller can review it. The comparison is made even when the recomputed edit changes nothing. The digest is of the writes, not the diff, because the printed diff doesn't fix the written bytes (a byte order mark, or a change outside the diff's hunks, prints the same diff). Equal digests mean the same writes, not that the result is correct: the build, the tests and the agent cover that. Whether to dry-run first is the caller's policy.
- **The endpoint's own files aren't reported as disk changes:** the file record skips the worktree root's `temp/fractal-jdtls/`, and only that one (a module's folder of the same name elsewhere is recorded as usual; T002.10's review, R1). Eclipse's own sync check still sees the new files, so the first fixed point after a refactoring is a full one (a refresh and build, about 120–170 ms on the fixture); that's accepted. Filtering the folder out of Eclipse too, which writes a filter into the root project's `.project`, is parked as future hardening, for if the numbers call for it.
- **What's accepted.** A crash or kill mid-apply can leave some files edited and one truncated, and the outcome unknown until someone looks; Git, the build, the tests and the agent recover. A reference added elsewhere during an apply, or an editor writing a file during it, can be missed (the per-file checks catch changes to the edit's files made before the writes, not during them); the build, the tests and agent repair catch what matters. A `temp` replaced by a link after the check can redirect a record.
- **New code:** `edit-changed`.
- **T002.10's details** (T002.10's proposal; approved by the governor on 2026-11-09 under Chris's delegation, except its first item, the Eclipse filter, which is removed: Chris's design defers it, and only the governor's own acceptance item had called for it; to review):
  - **`/v1/status`'s entries:** the field that held the route's path was called `operation`; it's now `path`. `operation` is now a refactoring's ID, the same name as in its answer.
  - **When the folder is made:** after the waits, the mapping and the request's first fixed point. The ID goes on the in-flight entry first, then the folder is made. A request refused before that has no folder: invalid fields, an unregistered or deleted worktree, a wrong module, `not-ready`, or a deadline that passes while it waits. It never started, and its answer comes at once.
  - **What the files hold:**
    - `request.json`: `id`, `received` (ISO 8601, UTC, to the millisecond: the request's arrival, the time in its ID), `operation` (`refactor/rename`) and `request`, the body as received.
    - `diff.patch`: exactly the answer's `diff`. It's empty for an edit that changes nothing, and absent when JDT refused before there was an edit.
    - `response.json`: the body the caller is sent, success or problem; a problem has `code` and `status`. An unexpected failure records the `internal` problem the caller gets.
    - If `diff.patch` can't be written, the request fails before any source write. If `response.json` can't be written, that's logged and the caller still gets the answer, since by then the edit may be written.
  - **The digest's framing:** the number of entries as decimal text, then for each file operation, in the order `files` lists them: its kind (`modified`, `created`, `deleted` or `renamed`, as `files[].change` says), its path, the path it's moved from for a rename, and its new bytes, except for a delete. Each field is preceded by its length as 8 bytes, big-endian. The digest is SHA-256, in lowercase hex. `expectWriteSetDigest` must be 64 lowercase hex digits, else `invalid-request`. It's compared on a dry run too, as the same check.
  - **`edit-changed` carries the edit as it is now,** in two new problem fields, `diff` and `writeSetDigest`; the folder's `diff.patch` is that diff.
  - **A test pause `after-first-write`** (`TestPauses`), after the first file's step in `EditWriter`, lets the integration suite kill JDT LS mid-apply. The launcher never passes the property.

### Navigation and search

- Definition, references, implementations, type hierarchy, call hierarchy, and symbols in a file or a worktree, plus Javadoc and the signature of a named element.
- Answers are in the caller's terms: Java names, files relative to their module, and 1-based lines with the source line.
  - **Which engine answers each operation.** (T002.06's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Every navigation operation runs the fixed point first, with its fast path, reports `sync`, and reads its answer under the worktree's read lock. JDT LS's own LSP handlers answer through the in-JVM client wherever the target has a position in the worktree's sources: `textDocument/definition` (for a text anchor), `/references`, `/implementation`, `typeHierarchy/subtypes` (with an item made from the type's JDT handle, the `data.element` the handler resolves) and `textDocument/documentSymbol` (the endpoint's `initialize` now asks for hierarchical symbols). Their URIs and 0-based positions become Java names, modules, files and 1-based lines. JDT answers directly only where a handler can't express the contract:
    - resolving a name or a text anchor to an element (above); a name's definition is the declaration it resolved to;
    - a library or JDK element (`from the classpath`), which may have no source and so no position for a handler: references through a JDT search of the covered modules' sources, implementations through a JDT type hierarchy of them. So a JDK with or without `src.zip` gives the same answers, and its signatures always come from JDT's model;
    - supertypes, through `IType.newSupertypeHierarchy`, which `typeHierarchy/supertypes` reads too: the handler leaves out a library supertype (`java.lang.Object`, `java.lang.Record`) unless the client opens `jdt://` class files, a capability the endpoint doesn't claim;
    - the call hierarchy, through `CallHierarchyCore`, the engine of JDT LS's `CallHierarchyHandler`: the handler finds each item's element again from its URI and position, which a library method without source doesn't have, so a callee's Java name, which the contract requires, would be lost;
    - `symbols`, through a JDT declaration search of the worktree's sources (types, methods, constructors and fields; a `*query*` pattern and camel case, ignoring case): `workspace/symbol` finds only types (methods only with a client setting), never fields, and searches every worktree;
    - `describe`'s Javadoc, from `JavadocContentAccess2.getMarkdownContent`, which JDT LS's hover uses: the hover itself appends a "Source:" line with the Eclipse project's name and the file's URI. Its signature is the declaration's source up to its body, comments dropped and whitespace collapsed, and for a library element JDT's model.
  - **What "the module and the modules that depend on it" is, and when a type is ambiguous.** (T002.06's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) A search (references, implementations, subtypes and callers) covers the requesting module's project and every Java project of the worktree whose resolved classpath requires it, directly or not (`IJavaProject.getRequiredProjectNames`). A module that isn't a Java project, such as the root `pom` (`.`), covers every module in its folder. Results outside the worktree are dropped (none were, in the gate: JDT LS's workspace-wide searches matched only the asking worktree's elements), and definitions and callees, which aren't searches, keep anything in the worktree or on the classpath. A type that two modules of the worktree declare is the requesting module's own, else the one its classpath sees (`IJavaProject.findType`), else `ambiguous-type`. A name with no `#` is a type first, then a package with sources in the worktree; a name that is neither is `package-not-found` when its last segment starts in lower case and no type has its simple name, else `type-not-found`.
  - **Text anchors, exactly.** (T002.06's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) `file` is relative to the module; a file of another module is `file-in-other-module`, whose candidate sets `module` and the file together. `text` must occur once in the compilation unit's text (JDT's buffer, which the fixed point made the file's), or once within `within`'s source range; a line break in it matches `\n` or `\r\n`. `select` must occur once in `text`. The element is what JDT's `codeSelect` finds at `select` (or at all of `text`); nothing there is `not-applicable`, whose hint says to use `select`. `text-not-found` offers, as candidates, the occurrences with other whitespace (the same characters, any whitespace between them), and otherwise quotes in `detail` up to 3 lines that share the longest run of characters with the text's first line, at least half its length. `text-not-unique` lists every occurrence, and offers `within` for each enclosing declaration that holds exactly one.

### The LSP passthrough

- **`POST /v1/lsp`** takes `worktree`, `module`, an LSP `method` and its `params`. It reconciles with the disk first and sends the request to JDT LS unchanged.
- **It's an expert escape hatch.** It uses LSP's own URIs and 0-based positions, its results aren't filtered by worktree (its requests' URIs are checked: "T002.09's details"), and its errors are JDT LS's raw errors, wrapped in a problem with code `lsp-error`.
- Requests that would break the endpoint's ownership of the connection are refused: lifecycle methods, folder changes, and document synchronization.
- **The passthrough sends requests only, and refuses two more kinds.** (T002.02's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Notifications get no answer to return, so the passthrough doesn't send them; `$/cancelRequest` is the endpoint's own, on timeout. It also refuses:
  - `workspace/didChangeConfiguration`, which would override the settings the endpoint fixes ("Launching");
  - `workspace/executeCommand` with a command that changes projects or the workspace behind the endpoint's back: `java.clean.workspace`, `java.project.import`, `java.project.changeImportedProjects`, `java.project.addToSourcePath` and `java.project.removeFromSourcePath`. T002.09 checked the pinned JDT LS's command list for others (below).
- **T002.09's details** (T002.09's proposal; approved by the governor on 2026-11-09 under Chris's delegation, with its review's two fixes: a `jdt:` URI's project checked against the worktree's registered projects, not a name prefix, and `java.edit.handlePasteEvent` refused, since the pinned JDT LS's handler leaks a working copy; to review):
  - **Everything is classified, and only what's allowed is sent.** `LspPassthrough` lists every method the pinned JDT LS serves, as an allowed request or a refusal with what to use instead. Its `JDTLanguageServer` serves 102 methods, by lsp4j's own `ServiceEndpoints.getSupportedMethods`. It also lists all 33 commands JDT LS 1.63.0 advertises in `initialize`, all from its one delegate handler. An allow-list, not a deny-list, because a wrong allow breaks sharing and a wrong refusal costs only a request: a method or command a later JDT LS adds is refused as "not classified yet", and so is one JDT LS doesn't serve. The refusal comes before any wait or reconcile.
    - After `initialize`, the endpoint logs how both lists compare with what JDT LS really serves, naming anything unclassified. The integration suite fails unless that's none, so a re-pin has to classify what's new. The evidence has every entry with its reason.
    - Refused, beyond the five commands above: `java.project.updateClassPaths`, `updateSourceAttachment`, `updateSettings`, `updateJdk`, `refreshDiagnostics`, `upgradeGradle` and `createModuleInfo`, `java.protobuf.generateSources`, `java.reloadBundles` and `java.completion.onDidSelect`.
    - Refused, beyond the kinds above: the builds `java/buildWorkspace` and `java/buildProjects`, the project updates `java/projectConfigurationUpdate` and `java/projectConfigurationsUpdate`, and the file operations `workspace/willCreateFiles`, `willRenameFiles` and `willDeleteFiles`.
    - Allowed: 72 requests that read, or compute an edit and return it; and 19 commands that read, or compute and return.
  - **URIs must be in the named worktree.** Every `file:` URI in `params` is compared with the worktree's root after normalizing it. A `jdt:` URI whose handle names a project must name one of the worktree's projects (`<worktree folder name>.`). Otherwise the answer is a new code, `uri-outside-worktree` (422), whose candidate sets `worktree` and `module` to the registered worktree that holds the file. A malformed `file:` URI is `invalid-request`. The check runs after the reconcile, under the read lock, because it needs the mapped worktree. Results stay unfiltered.
  - **`applyEditsRefused`, always in the answer.** It lists every `workspace/applyEdit` that JDT LS sent while the request ran, each refused with a reason that says the passthrough returns it. JDT LS doesn't say which request an edit belongs to, so one is listed in every passthrough request in flight when it arrived.
    - With the endpoint's `applyEdit: false`, JDT LS 1.63.0 sends none for an allowed request. Its only callers are `java.edit.organizeImports` when the client can apply edits, and the type-rename fix-up on `workspace/didRenameFiles`, which is refused. So the field is tested in JUnit against a fake server.
  - **It runs like a read:** the default `timeoutMs` is 120 s, like navigation's, and its deadline sends `$/cancelRequest`. Like every read, a caller that disconnects isn't noticed ("Threading and queuing"), so only the deadline cancels.
    - T002.09's evidence shows the cancel reaching JDT LS. A test-only hold, `TestJobs`, schedules a job of JDT LS's `DocumentLifeCycleJobs` family, which `textDocument/documentSymbol` joins before it answers. JDT LS answered the cancel with -32800 while the hold still ran: 1.4 ms after the endpoint sent it in one run, and 1.9 ms in the gate.
  - **The endpoint never opens documents.** `textDocument/semanticTokens/full` answered from the file on disk.
  - **The endpoint's jar is always rewritten** (`forceCreation`). The jar plugin doesn't compare the manifest file with the jar, so a manifest-only change, here one new import, left the old jar in place. A unit test now checks that every package the bundle's classes use (by `jdeps`) is imported.

### Threading and queuing

The endpoint handles all of it. The harness makes one blocking call per operation.

- **A fixed pool of HTTP worker threads,** separate from JDT LS's threads. A request beyond the pool's queue gets `503` (`busy`) with `retryAfter`. The pool and queue sizes come from T002.11's measurements ("T002.11's details"), for Chris to review.
  - **No caller without the token can hold a worker, or a thread for long.** (T002.03's review proposal, R2; approved by the governor on 2026-11-08 under Chris's delegation; to review.) The JDK's server reads each request's headers and body, and writes its answer, on a connection thread; only a request that passed the token, `Host` and `Origin` checks, with its body read in full, reaches the worker pool, and the quick lifecycle routes (`status`, `openapi.json`, `shutdown`) don't use it at all. The JDK server's own limits, documented in its `jdk.httpserver` module, bound the rest; the launcher passes them and the endpoint refuses to start without them: `sun.net.httpserver.maxReqTime=10` (seconds from a request's first byte to the end of its body; a caller that stops sending is disconnected), `sun.net.httpserver.maxRspTime=3900` (from the end of the request to the end of the answer, so above the longest `timeoutMs`, 3,600 s), `sun.net.httpserver.drainAmount=0` (a refused request's unread body is never drained: it's answered and disconnected), and `jdk.httpserver.maxConnections=256`. A local process without the token can still open up to 256 connections and keep each for up to 10 s at a time; it can't make an authenticated request wait for a worker.
- **Reads run concurrently.** Operations that change the workspace run one at a time, under Eclipse's workspace scheduling rule: refactorings that apply, worktree changes, and the refresh-and-build at each fixed point. That's needed: when a worktree's add and another worktree's fixed point ran at once, a join waited on an implicit job, which never returns ("Joining the work").
- **A fixed point that refreshes or builds waits for the workspace root rule,** so it runs one at a time with every other worktree's imports, builds and fixed points. `sync` reports the wait. (Decided by the governor on 2026-11-08 after T002.01; to review. HTTP-FINDINGS proposal 14.)
  - `refreshLocal` on a project takes its parent's rule, which is the root; every build takes the root (`buildRule()`); and JDT LS's imports and builds hold it. Every rule conflicts with the root, so nothing narrower avoids the wait.
  - Measured: a complete operation on a changed `main`, with the join of only what it scheduled, took 6.9 s while the large tree imported, and 4.5 s during its full build, against 127 ms when idle.
  - **An unchanged worktree doesn't wait,** through the fast path ("Keeping in step with the disk").
- **Plain LSP requests take no rule.** Ten requests sent while the root rule was held for 5 s didn't wait for it, from `textDocument/definition` to `textDocument/rename`'s computation. `textDocument/definition` stayed at a median of 5–9 ms while other worktrees imported or built. JDT search waits for the indexes it needs: `workspace/symbol` took up to 5.4 s on the session's first query, and while the large tree was indexed.
- **Readiness:** until JDT LS has finished starting, and while any worktree is importing (imports run alone, "Worktrees"), requests wait, up to their timeout, or get `not-ready` with `retryAfter`, as the caller asks. The problem's `detail` says which of the two it is.
- **Every operation has a timeout,** with a default and an optional `timeoutMs` in the request. When the timeout passes, the endpoint cancels the LSP request (`$/cancelRequest`) or the Eclipse job's progress monitor, and returns `timeout`. A caller that disconnects isn't noticed, so its work is cancelled at its deadline ("T002.11's details"). Measured: `$/cancelRequest` sent 200 ms into a references search that takes 9.1 s was answered 1.6 ms later, and a cancelled monitor stopped a full build of 57 projects 31 ms after it was cancelled.
  - **A fixed point's timeout.** (T002.05's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Its Eclipse operations (the wait for the rule, the refresh, m2e's update and the build) get a progress monitor that's cancelled at the request's deadline. The join then stops waiting, and cancels no job, because the jobs are JDT LS's. The answer is `timeout`, with `phase` `waiting-for-rule` or `syncing`. A fixed point that's stopped clears its worktree's mark, so the next one refreshes in full. A caller that disconnects isn't noticed: the JDK's HTTP server gives no sign of it before the answer is written, so the work goes on to its deadline. T002.11 revisited it and kept it ("T002.11's details").
  - **A request whose time is up never runs.** (T002.04's review proposal, R3; approved by the governor on 2026-11-08 under Chris's delegation; to review.) Its deadline counts from its arrival, so time spent queued for a worker thread counts. It's checked when a worker takes the request, after it waited for JDT LS to start, and after it waited for a worktree change. Past it, the answer is `not-ready` when JDT LS's start or a change is what the request waited for, else `busy` (the description says so under `busy` and each `timeoutMs`).
- **JDT LS never waits on HTTP I/O.** The endpoint answers JDT LS's requests back to the client from its own state, without calling out.
- **T002.11's details** (T002.11's proposal; approved by the governor on 2026-11-09 under Chris's delegation, with the review's three changes below; to review):
  - **A request waiting in the queue is answered at its deadline** (the review's R1). It gets the `busy` problem a worker gives a request that waited past its `timeoutMs` ("waited … for a worker thread", `retryAfter: 1`) at its deadline, not when a worker reaches it, and no worker runs it after that.
  - **`timeout` has no `retryAfter`** (the review's R3). The endpoint can't estimate when the work would finish; the problem's hint says to send it again with a larger `timeoutMs`, or narrower. `busy` and `not-ready` carry `retryAfter`.
  - **JDT LS's cancel limitation is accepted** (the review's R2), with what bounds it stated below: when JDT LS's document life-cycle jobs run, which of them the endpoint's own requests start, and so whether abandoned handlers can pile up outside a test.
  - **The pool: 16 worker threads, and 64 requests queued for them, in order; a request beyond them gets `busy` at once, with `retryAfter: 2`.** Measured on the fixture's three worktrees, on this machine's 12 CPUs, with a probe build whose pool (64) never limited: C concurrent clients, each looping over eight fast-path reads (`definition`, `references`, `describe`, `symbols`, `type-hierarchy`, `call-hierarchy`, `outline`, `problems`), 15 s at each C.

    | C | Requests a second | p50 (ms) | p95 (ms) | Heap used, no GC forced |
    | --- | --- | --- | --- | --- |
    | 1 | 15.6 | 20.8 | 330 | 417 MB |
    | 4 | 63.8 | 18.2 | 332 | 400 MB |
    | 8 | 94.9 | 23.5 | 449 | 929 MB |
    | 12 | 110.8 | 35.7 | 553 | 1,281 MB |
    | 16 | 119.3 | 53.2 | 642 | 1,275 MB |
    | 24 | 117.4 | 98.3 | 923 | 957 MB |
    | 32 | 115.7 | 146.2 | 1,219 | 1,297 MB |
    | 48 | 113.1 | 234.8 | 1,801 | 1,675 MB |

    With three of the clients editing a file and calling `build` in a loop, the rate was 44 to 46 requests a second at every C from 6 to 48, and the reads' p50 grew from 92 ms to 909 ms.
    - **16 workers:** the rate levels off at 16 concurrent requests, and more threads only add latency and garbage. A request that waits (for its worktree's lock, the workspace rule, an import, or JDT LS's answer) keeps its worker, so fewer than 16 would let a few waiting sessions hold up the others' fast reads sooner.
    - **64 queued:** at the measured 45 to 119 requests a second, a full queue is 0.5 to 1.4 s of work. With the pool that's 80 requests, well under the server's 256 connections, and at most 64 MiB of queued bodies (1 MiB each). `retryAfter: 2` is the slower drain time, rounded up.
    - Tested: `HttpApiTest.aRequestBeyondTheQueueIsBusyWithRetryAfter`, and `test_concurrency.py` in JDT LS, with every worker taken by requests waiting for a worktree's lock.
  - **A disconnect isn't noticed; the deadline is the cancel.** The JDK's `com.sun.net.httpserver` API (`HttpExchange`, `HttpServer`, `HttpContext`, `Filter`) has no callback or query for a closed connection. The request body, once read in full, answers end-of-stream without touching the socket. Only the server's internals (`sun.net.httpserver.ServerImpl`) see the socket, and the endpoint doesn't reach into them. So a disconnected caller's work goes on until its deadline, and is cancelled then like any other's. `test_concurrency.py` shows it: a `build` waiting for the rule, whose caller closed its connection 0.3 s in, stopped at its 3 s deadline. A caller should send a `timeoutMs` no longer than it will wait. To revisit if the endpoint ever moves to another HTTP server.
  - **The deadline's monitor wasn't seen by Eclipse's wait for the rule; fixed.** The endpoint's deadline monitor extended `NullProgressMonitor`. JDT LS's progress provider (`ProgressReporterManager.monitorFor`) replaces any `NullProgressMonitor`, subclasses included, when `JobManager.beginRule` is called. So a fixed point waited for the workspace rule past its deadline, until the rule was free: 296 s past a 2 s `timeoutMs`, behind a held refactoring. The monitor now implements `IProgressMonitor` itself, and the wait stops 5 to 6 ms after the deadline (`DeadlineTest`, `test_concurrency.py`).
  - **JDT LS doesn't stop a handler that waits for its document life-cycle jobs (a JDT LS limitation, version-pinned).** `$/cancelRequest` reaches JDT LS, which answers -32800 at once. A handler that checks its progress monitor itself stops: a references search over the large tree's 10,000 references, cancelled 1.5 s into its 9.9 s, left no thread in `ReferencesHandler` (`test_imports.py`). But JDT LS's own `CancellableProgressMonitor` is a `NullProgressMonitor` too, which the same provider replaces inside `JobManager.join`. So a handler in `waitForLifecycleJobs` (`definition`, `documentSymbol` and others) keeps waiting, abandoned, until those jobs end, and its answer is dropped. The endpoint answers `timeout` at the deadline either way, and frees its worker. `test_concurrency.py` pins JDT LS's behaviour, so an upgrade that fixes it shows.
    - **What bounds it** (the review's R2; from JDT LS 1.63.0's bytecode, and checked in the suite's logs):
      - **One job.** The family `DocumentLifeCycleJobs` has a single job, `BaseDocumentLifeCycleHandler`'s "Validate documents" (`validationTimer`), which reconciles the documents queued by `triggerValidation`. Every other class that names the family joins it: `JDTLanguageServer`, `DiagnosticsCommand`, `InlayHintsHandler`, `OrganizeImportsHandler`, `SemanticTokensHandler` and `SyntaxLanguageServer`.
      - **Only for open documents.** `triggerValidation` is called by `didOpen` and `didChange` (`handleOpen`, `handleChanged`, `checkPackageDeclaration`). It's also called by `ClasspathUpdateHandler` and `WorkspaceDiagnosticsHandler`, but only for primary working copies: `JavaCore.getWorkingCopies(null)`, and `isWorkingCopy()`.
      - **None in HTTP mode.** The endpoint never sends `didOpen`, `didChange`, `didSave` or `didClose`. The passthrough refuses every document-synchronization method, `java/validateDocument`, `java.project.refreshDiagnostics` and every notification. And the endpoint makes no working copy. The only other primary working copies in JDT LS are made and discarded within one call: `JDTUtils.getWorkingCopy(IClassFile, …)`, `ProjectUtils.refreshDiagnostics`, `NewCUProposal.constructNewCUChange` and `FileEventHandler.computeMoveEdit`. A validation could be scheduled only if a classpath change or a marker change landed inside such a call. It would then reconcile that one file, so a handler would wait for one reconcile.
      - **Checked.** Fixed points log every job they join. Across the gate's integration suite (373 fixed points that joined jobs) and the 10-minute soak (1,731), none was "Validate documents", and neither the endpoint's log nor JDT LS's named it. In the soak, 689 `definition` and 689 `outline` requests, which join the family, had no `timeout` (the longest took 1,072 ms).
      - So abandoned handlers pile up only while that job runs. In HTTP mode it doesn't run outside the test hold (`TestJobs`), so they don't pile up there.

### Status and shutdown

- **`GET /v1/status`:** the release, the API version, whether JDT LS is ready, the registered worktrees with their import state, the import in progress, any import repairs and dropped worktrees ("Worktrees"), and the operations in flight, each with its operation folder's ID for a refactoring ("Operation folders"). `?wait=ready&timeoutMs=` blocks until JDT LS is ready.
- **`POST /v1/shutdown`:** answers first, then shuts JDT LS down through LSP `shutdown` and `exit`, so it saves the workspace state. The process then exits.

### Constraints and risks

From T002.01's spike (HTTP-FINDINGS "Constraints and risks" and "Not tested").

- **Version-pinned internals,** like the agent's hooks (§6), re-checked on every JDT LS upgrade. The endpoint relies on:
  - `LanguageServerApplication.prepareStreams` capturing `System.in` and `System.out` when the application starts (the identity check after `initialize` catches a change);
  - the `watchParentProcess` property;
  - JDT LS's job classes and families (`ProjectsManager$2`, `MavenProjectImporter`), and `ThreadJob` and `IBackgroundProcessingQueue` by class;
  - JDT LS deleting every project outside its folders (`cleanInvalidProjects`), at startup and on each folder change;
  - m2e's internal `ProjectConfigurationManager.updateProjectConfiguration(request, true, true, monitor)`.
  - From T002.05, three more (approved by the governor on 2026-11-08; to review): Eclipse's resources plugin reading `refresh.lightweight.enabled` once, with Equinox's `eclipse.pluginCustomization` defaults; `IResource.touch` changing only Eclipse's tree, never the file; and JDT LS's metadata files showing in Eclipse's tree at the project's folder. The endpoint's startup check and the integration tests catch a change to the first two.
- **A large import can break silently.** In 5 of 31 imports of the large tree, one module was left unknown to m2e, with its metadata written to `<data>/<project>`, and every module after it failed with "Missing artifact". All 5 had endpoint requests running during the import; none of the 9 without requests broke. The cause wasn't found. Imports running alone and the health check with one repair ("Worktrees") contain it. In T002.04, with them, none of 40 large imports with requests held during them broke, nor the gate's, and no repair ran.
- **Changes that keep their modification time** are invisible to `refreshLocal`, which compares millisecond modification times (`RefreshLocalVisitor`). The endpoint's own record finds them ("Keeping in step with the disk").
- **The refresh cost grows with the worktree:** 330 ms for 10,001 files, at every fixed point that doesn't take the fast path, and 250 ms for the fast path's own check.
- **A bundle Equinox can't resolve starts JDT LS without its client.** (T002.03's proposal; approved by the governor on 2026-11-08 under Chris's delegation; to review.) If the endpoint bundle doesn't resolve, Equinox logs it in the configuration area and starts JDT LS on the process's real stdin and stdout, and the activator that would stop it never runs; no port file appears, and the harness must stop the process it started. Three checks make it unlikely: the launch check verifies the bundle's hash (§5), a unit test checks every package the bundle imports against what the pinned JDT LS exports, and the launcher checks for `jdk.httpserver`. Catching it inside the process would need the agent to hook JDT LS's application start, coupling the agent to HTTP mode; not done. So that such a JDT LS can't talk LSP to anyone, the launcher in HTTP mode also starts Java with stdin from `/dev/null` and stdout sent to stderr, and never passes JDT LS's other transports (`CLIENT_PORT`, `CLIENT_HOST`, their `-D` forms, `--pipe=`). The harness treats a port file that hasn't appeared within its own timeout as a failed start, and stops the process it started (§10). (Decided by the governor on 2026-11-08 during T002.03; to review.)
- **The bundle lives in JDT LS's process.** A hang in it, like the join on an implicit job, blocks the operation that hit it. Every join has a long guard timeout that reports loudly.
- **Not yet measured:**
  - the real Harness reactor, Gradle, nested multi-level reactors, and a root POM change that must reach every child;
  - worktrees on WSL2's `/mnt` paths, and memory use with many worktrees: T002.11's soak held four of the fixture's worktrees for 10 minutes, with the heap after a full GC at 192 MB at the start and 200 MB at the end.
