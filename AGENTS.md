# Fractal JDT LS: agent guide

This file is for every coding agent working in this repository. The [Fractal conventions](https://github.com/nokesc/fractal/blob/master/CONVENTIONS.md) are the shared authority; this guide adds Fractal JDT LS's project-specific instructions within them.

## What the project is

Fractal JDT LS is a verified install of one official Eclipse JDT Language Server release, plus a launcher that is a drop-in for the stock `jdtls` and always adds a small Java agent. The agent keeps each Git worktree's Maven projects separate when several worktrees of one project share a JDT LS process. [README.md](README.md) says why it exists; [.context/design.md](.context/design.md) says what it delivers and how, and is authoritative together with the code.

## Repository structure

- `bin/`: the shipped Python scripts, `install.py` and the `jdtls` launcher (design §4, §5).
- `agent/`: the Maven modules for the agent jar (`agent/agent/`) and the boot jar (`agent/boot/`), built from the root `pom.xml` (design §6), with their JUnit tests. The root POM's `byte-buddy.version` property is the only place the Byte Buddy version is chosen.
  - The agent's diagnostic log is enabled with `-Dfractal.jdtls.diagnosticLog=<file>` (one JSON line per event; see `DiagnosticLog`).
  - The build also makes a test-only `agent/agent/target/fractal-jdtls-agent-broken-hook.jar` (`BrokenHookAgent`: one hook's matcher names a missing method). It is never in the release zip; put it in a copy of an install's `lib/` to check that a broken hook is reported.
- `endpoint/`: the HTTP endpoint (design §11), an OSGi bundle (`endpoint/target/fractal-jdtls-endpoint.jar`, shipped as `lib/fractal-jdtls-endpoint.jar`) with a hand-written manifest (`src/main/manifest/MANIFEST.MF`) and its JUnit tests. Package `org.fractal.jdtls.endpoint`.
  - Its contract is the OpenAPI 3.1 description `endpoint/src/main/resources/openapi.json`, which `tests/unit/test_openapi.py` validates (every operation with examples, every error code with an example problem, every example against its schema). The description is the contract: edit it directly. It's also the error catalogue at runtime, and a JUnit test fails if a registered route or a `Code` isn't in it.
  - It compiles against the pinned JDT LS's own jars, system-scoped from the build cache `.cache/jdtls/<tarball SHA-256>/`, which `tools/jdtls_cache.py` downloads once and verifies against `pin.json` on every build (`mise run build` runs it before Maven; after the first fill it works offline). Eclipse's jars never go into `~/.m2`. A new import in the manifest needs its jar in `endpoint/pom.xml`; `tests/unit/test_endpoint_bundle.py` checks the POM's paths against `pin.json`, every imported package against what the pinned JDT LS exports, and that every package the bundle's classes use (by `jdeps`) is imported: a missing import fails only inside JDT LS, when the class loads.
  - The endpoint logs to `<data>/.fractal-jdtls/<release>/endpoint.log`; a startup failure goes to stderr, and JDT LS exits 1. It keeps the registered worktrees in `<data>/.fractal-jdtls/worktrees.json` (not per release), and passes them to JDT LS on a restart; each worktree's file record, which a restart compares with the disk, is in `<data>/.fractal-jdtls/records/`. Its worktree operations are in `WorktreeOps`, the request-to-project checks in `Mapping` (read only: its health check finds m2e's facade in m2e's registry, never through `getProject(IProject)`, whose `getPom` refreshes the POM, so only fixed points take disk changes in), its own reading of POMs in `Poms`, `build` and `problems` in `ProblemOps`, the navigation operations' routes in `NavOps`, the refactorings' in `EditOps` and the LSP passthrough's in `LspPassthrough` (every method and `workspace/executeCommand` command JDT LS has, allowed or refused, checked after `initialize` against what JDT LS serves by `ServedMethods`; the startup log names any unclassified) (all through `CodeRequest`, the waits, the mapping and the fixed point every operation on code shares; a refactoring's apply is one more fixed point, `DiskSync.apply`; each refactoring is recorded in its operation folder, `<worktree>/temp/fractal-jdtls/<id>/`, by `OperationFolder`: `request.json`, `diff.patch`, then `response.json`, which the endpoint never reads back or removes; the file record skips the worktree root's `temp/fractal-jdtls/`, and only it, but Eclipse's sync check sees the new files, so the fixed point after a refactoring is a full one), an edit's effect worked out in memory in `EditPlan`, written all or nothing in `EditWriter`, and shown by `UnifiedDiff`, the Java name syntax in `NameSyntax` and text anchors' matching in `TextAnchors`, and everything that uses Eclipse's workspace in `Workspace`, `Jobs`, `DiskSync` (the fixed point that keeps JDT LS in step with the disk, with `FileRecords`, its own record of each file's status-change time, size and inode), `Markers`, `JavaNames`, for navigation `Targets` (names and anchors to elements, with every addressing error), `Locations` and `Navigation` (each operation's answer, from JDT LS's LSP handlers through the in-JVM client, or JDT where design §11 "Navigation and search" says why), and for refactorings `Refactorings` (each edit, from JDT LS's and JDT's own engines) and `Edits` (JDT LS's `WorkspaceEdit` read, checked against its baseline, and written), so no Eclipse class loads before JDT LS has started. In HTTP mode the launcher also passes `-Declipse.pluginCustomization=<release>/lib/http-mode-preferences.ini` (from `endpoint/src/main/preferences/`), Eclipse preference defaults that turn lightweight auto-refresh off; the endpoint refuses to start if it's on. Operations run on `HttpApi`'s pool of 16 worker threads, with 64 requests queued for them; a request beyond them is `busy` with `retryAfter`, and one still queued at its deadline (its `timeoutMs`, or the default its route registers with `HttpApi.route`) is answered `busy` then, by one timer thread, and never run (design §11 "Threading and queuing", sizes from T002.11's measurements). A request's deadline reaches Eclipse through `DiskSync.Deadline`, a plain `IProgressMonitor`: JDT LS's progress provider replaces a `NullProgressMonitor` in `JobManager.beginRule`, so it must never be one (`DeadlineTest`). It refuses to start without HTTP mode's JDK HTTP server limits (`ServerLimits`: `-Dsun.net.httpserver.*`, `-Djdk.httpserver.maxConnections`), which the launcher passes and `endpoint/pom.xml`'s surefire configuration sets for the JUnit tests.
- `pin.json`: the pin of the one JDT LS release and Byte Buddy version this release installs (design §3). It's written by `tools/pin.py`, never by hand, and its evidence, the pin report, is in `.context/pins/<jdtls-version>.md`.
- `tools/`: maintainer tooling that isn't shipped: `tools/pin.py` (design §3), `tools/release_zip.py` (design §2), `tools/release_tag.py`, the release workflow's tag check (design §9), and `tools/jdtls_cache.py`, the endpoint's build cache (design §11).
- `.github/`: the release workflow, `workflows/release.yml` (design §9), and each release's notes, `release-notes/v<release>.md`, which the workflow uses as the release's body.
- `tests/`: pytest suites.
  - **The test scratch folder** (design §8) holds every pytest session's folders, unit and integration: `<main checkout>__scratch/`, beside the main checkout (here `~/github/nokesc/fractal-jdtls__scratch/`), the main checkout being the first entry of `git worktree list --porcelain`, so every linked worktree uses the same one. `FRACTAL_JDTLS_TEST_SCRATCH` (an absolute path) overrides it, and a bare repository needs it. `tests/conftest.py` (with `tests/scratch_folder.py`) makes it if missing, mode 700, and refuses it, before anything is made or pruned, unless it's yours, not writable by group or others, and has no `.git` in it or above it (so it's never inside a checkout, `temp/` included). A run holds a kernel lock (`flock`) on its `suite.lock` for its whole duration: a second suite run, from any checkout, fails at once naming the first one's PID, command and checkout. The kernel lets go when the process dies, so a killed run leaves nothing to clean up. Under it are pytest's own numbered sessions, `pytest-of-$USER/pytest-<n>/`, with `pytest-current` naming the newest; the latest six are kept (`tmp_path_retention_count` in `pyproject.toml`: three gates of two sessions), so evidence copies the output it cites rather than pointing into them. `--basetemp` is refused, since it empties its folder. Python's temporary files (`tempfile`, as `tools/pin.py` uses) and `TMPDIR` for the suite's children go to the session's own `tmp/`. Java ignores `TMPDIR`: JUnit's `@TempDir` folders are small and stay in `/tmp` (`java.io.tmpdir`), as does what JDT LS's own JVM and Maven write there (each JVM's `hsperfdata_$USER/<pid>`, 32 KB until it exits, and Maven's `jansi` library).
  - `tests/unit/` runs in `mise run test`, each test with a scratch `HOME` and XDG folders (`tests/unit/conftest.py`).
  - `tests/integration/` runs in `mise run test:integration` (design §8): real JDT LS, installed by `install.py` from a freshly built release zip into a pytest scratch root, launched through the installed `bin/jdtls` on a scratch main checkout and two linked worktrees made from `tests/integration/fixture/` (its POMs stay `pom.xml.fixture`). It reproduces the spike's runs 05 and 06, and run 01 without the agent through the test-only `launch_without_agent.py`. `test_http.py` starts the installed release in HTTP mode (`endpoint_client.py` drives it over HTTP, checks every answer against the served description, and stops only the PID it started; its `RELEASE`, from `pin.json`, names the endpoint's folder under `-data`). `test_full_loop.py` runs T002's overall acceptance loop on the installed release, through HTTP only (start, add two worktrees, an edit on disk and `build`, a rename by name and a clean `build`, a removal, the shutdown), and checks that every file and folder of the install is unchanged and that `--verify` passes. `test_http_worktrees.py` adds, checks and removes worktrees and restarts, through HTTP only; `test_import_repair.py` forces the import health check's repair (by damaging a stopped workspace's project description under `-data`, a test-only mechanism) and a module that stays broken; `test_concurrency.py` runs concurrency's deterministic cases in one process: a POM edited on disk taken in only by the next fixed point, a `build` waiting for the workspace rule (held by a rename paused at `before-write`) past its `timeoutMs`, a caller that disconnects, `busy` beyond the queue, and `definition` held inside JDT LS past its `timeoutMs` (thread dumps by `jcmd`, beside the PID's own `java`), while the other sessions' requests are answered. `test_sessions.py` runs four sessions at once, one per worktree (wt-c added during the run, then removed and added again by its own session), each checking every answer against a single-client run of the same steps, with each operation's latency and the heap at the start and the end; the gate runs it for a minute. `test_imports.py` imports `large_tree.py`'s generated reactor (51 projects, 10,001 Java files) while requests for another worktree are held, and measures the fixed point's costs on it, and real work cancelled at a deadline: a references search through `$/cancelRequest`, and a clean build through the cancelled monitor. `test_http_sync.py` changes files on disk without reporting them (run 05's edits, a `git checkout`, a POM that adds a dependency, a deletion, and changes that keep the modification time) and reads them back through `build` and `problems`; `test_run05_fresh.py` repeats run 05 through `build` on fresh copies. `test_refactoring.py` runs every T002 refactoring in wt-a as a dry run and applied, each followed by a clean `build`, JDT's refusals, `files-changed`, `write-failed` and a `timeout` just before the writes, and checks that wt-b's and main's files never change; its races use the endpoint's test-only pauses (`-Dfractal.jdtls.endpoint.testPauses=<folder>`, `TestPauses`: a test arms a point, `before-apply`, `before-write` or `after-first-write`, with `<folder>/<point>.armed`, and the refactoring waits at it until `<folder>/<point>` is deleted; the launcher never passes the property). `test_operation_folders.py` runs the operation folders on wt-a: a dry run and its apply checked by `expectWriteSetDigest`, `edit-changed` (a change inside the diff's hunks, and one only outside them), an apply held at `before-apply` while `/v1/status` lists its ID, a refusal, a `temp` that links out of the worktree or inside it, and JDT LS killed at `after-first-write`, its worktree restored by `git checkout` of the files `diff.patch` names, then a second JDT LS on the same `-data`. `test_navigation.py` runs every navigation operation, by Java name and by text anchor, JDK and Maven names on a module's classpath, every addressing error with its corrected request, and the same requests in each worktree, which each answer from their own files; the fixture's `Names`, `Step`, `EchoStep`, `Greeter` and `PrintStep` are its sources. `test_lsp.py` runs the LSP passthrough: `textDocument/documentSymbol`, run 05's classpath check through `java.project.getClasspaths`, every refused method and command, JDT LS's error as `lsp-error`, a URI of another worktree, edits returned unapplied, and a request held inside JDT LS past its `timeoutMs` (the test-only hold `TestJobs`, armed through the same test pauses folder at the point `lsp-hold`) so its `$/cancelRequest` is answered by JDT LS. Each run's snapshots, LSP traffic, diagnostic log and JDT LS log stay in its session's folder in the test scratch folder, under `runs/<run>/` (`pytest-of-$USER/pytest-current/` there for the latest).
- `.context/`: the design (`design.md`), the technical architecture every task links to; new technical tasks (`tasks/`) and their evidence (`tasks/evidence/`); the completed T001 and T002 series and their evidence, which stay in `planning/` and `planning/evidence/` as history, not as the active work order; the pin reports (`pins/`) and research evidence (`research/`), such as the JDT LS worktree spike's findings, cited by the design as FINDINGS, and the HTTP endpoint spike's, cited as HTTP-FINDINGS. Both spikes' code is retired, and in Git history (HTTP-FINDINGS says where).
- `scripts/bootstrap.sh`: sets up a fresh clone. `.agents/skills/` holds the repository's skills; `.claude/skills` is a committed link to it.

## Implementation rules

- **Scope (design §1).** Ship a verified install of one official JDT LS release and a launcher that always adds the agent. Leave process counts, sharing, lifecycle, brokers, compiler preferences, LSP settings and JVM sizing to the client.
- **Never repackage or redistribute Eclipse's files or Byte Buddy.** The installer downloads them, from Eclipse and Maven Central, and verifies them against `pin.json`.
- **Official releases only:** `https://download.eclipse.org/jdtls/milestones/<version>/`. Never `snapshots/` or any other pre-release build.
- **Linux only.** Write Python portably where it costs nothing; support, test and document only Linux.
- **Shipped scripts use the Python standard library only** (Python 3.10 or newer). pytest and other dependencies are for development.
- **No IDE-importable fixture POMs.** Test fixture POMs are committed as `pom.xml.fixture` and materialized only into scratch folders, so no IDE or language server on this checkout imports them. The root `pom.xml` and `agent/*/pom.xml` are the only real POMs.
- **Tests never touch the real `~/.local/share`, `~/.cache` or `~/.m2`.** They use a scratch home or pytest temp folders in the test scratch folder, and integration runs use their own Maven local repository.
- **Agents' own intermediate data** (logs, probes, captured output, scripts) goes in the checkout's git-ignored `temp/`, never in `/tmp`, which is a tmpfs held in memory here. Nothing that holds a `.git` or a `pom.xml` goes in `temp/`: a language server on the checkout would import it. Anything that needs one (a fixture, a scratch install, a JDT LS `-data`) belongs to a pytest run, in the test scratch folder.
- **Licensing (design §7).** Apache-2.0; every source file starts with an `SPDX-License-Identifier: Apache-2.0` line, which a unit test checks.
- **Processes.** Never stop a process you didn't start: another checkout, or an editor, may be running its own JDT LS. Stop only processes whose PIDs you recorded when you started them, never by port or executable name.
- **Agents never push, merge, tag or publish.** Chris tags releases: pushing a tag `v<release>` runs `.github/workflows/release.yml`, which checks the tag, runs `mise run validate` with the repository's mise toolchain (all of `mise.toml`'s pins except `workmux`, a developer tool the release doesn't need, which the job skips with `MISE_DISABLE_TOOLS: workmux`), creates a draft release with the notes, attaches the zip and publishes. A new release needs its notes in `.github/release-notes/` before the tag; the actionlint check is `mise exec actionlint@1.7.12 shellcheck@0.11.0 -- actionlint`.

## Commands and validation

Commands are mise tasks; `mise tasks ls` lists them.

- `./scripts/bootstrap.sh`: trusts and installs the mise toolchain and runs `mise run setup`, for a fresh clone.
- `mise run setup`: installs the locked Python dependencies into this checkout's own `.venv`.
- `mise run test`: the unit tests. It runs `build` first, which runs the agent's JUnit tests, then pytest, which checks the built jars.
- `mise run build`: builds `agent/agent/target/fractal-jdtls-agent.jar`, `agent/boot/target/fractal-jdtls-boot.jar` and `endpoint/target/fractal-jdtls-endpoint.jar`, running their JUnit tests. It first fills and verifies the build cache of the pinned JDT LS (`.cache/jdtls/`, about 53 MB, downloaded once; if it's empty and there's no network, the build fails naming the cache). Plain `mvn package` works only once the cache is filled.
- `mise run release:zip`: builds the jars, then the release zip, `build/fractal-jdtls-<release>.zip` (design §2). Install from it with `python3 fractal-jdtls-<release>/bin/install.py --root <scratch root>`; check an install with `<root>/<release>/bin/install.py --verify`. Start JDT LS from an install with `<root>/<release>/bin/jdtls` (`--help` lists its options); it verifies the install first, and refuses to start if it fails. HTTP mode is `--http-port-file <file>` with `FRACTAL_JDTLS_HTTP_TOKEN` set (32 or more visible ASCII characters); stop it with `POST /v1/shutdown`, or by killing the PID you started, never by port or name. Inside this checkout, the mise `python3` shim that its `#!` line finds sets `JAVA_HOME` to mise's Java, so pass `--java-executable` (or run it with `/usr/bin/python3`) to choose another Java.
- `mise run test:integration`: the integration suite alone (after `build`). It needs network access: each session downloads the JDT LS tarball (about 53 MB) and Byte Buddy, and the first one fills the suite's Maven local repository from Maven Central. That repository persists in `$FRACTAL_JDTLS_TEST_CACHE`, else `.cache/integration/` in this checkout; JDT LS gets it through `java.configuration.maven.userSettings`, and a scratch `user.home`, so it never touches `~/.m2`. Like every pytest run it uses the test scratch folder, holds its lock, and fails, naming the folder, if a `.git` sits in it or above it. An empty `/tmp/.git` has appeared in agent sessions (another project's sandbox): the suite no longer runs there, but the agent's JUnit tests do, so remove it.
- `mise run test:imports`: the 20 large-tree imports of T002.04, each in a fresh process and `-data`, with requests held during each (about 10 minutes; `FRACTAL_JDTLS_IMPORTS` sets the count). The tests are marked `imports`; `test:integration` leaves them out and runs one large import itself. Each run's numbers are in its session's folder in the test scratch folder, under `runs/imports-*/`.
- `mise run test:soak`: the several-sessions scenario of `test_sessions.py` for 10 minutes (`FRACTAL_JDTLS_SOAK_SECONDS` sets the time). Marked `soak`; `test:integration` leaves it out and runs it for a minute. Its numbers are in its session's folder in the test scratch folder, `runs/sessions-soak/result.json`.
- `mise run test:run05`: run 05 through `build` on 20 fresh copies, each a fresh fixture, process and `-data` (about 5 minutes; `FRACTAL_JDTLS_RUN05` sets the count). Marked `run05`; `test:integration` leaves them out and runs 2. The summary is in its session's folder in the test scratch folder, `runs/run05-summary.json`.
- `mise run validate`: the full release gate: the build with the agent's JUnit tests, the unit tests, the release zip and the integration suite. It must pass before any task that changes the build, the shipped files or the tests is complete; a documentation-only task checks its Markdown links, its diff and `git diff --check` instead.
- `mise run release:check-tag -- <tag>`: the release workflow's first step: the tag must be `v` plus `pin.json`'s `release`, and `.github/release-notes/<tag>.md` must exist.
- `mise run pin -- <jdtls-version> [--release <n>]`: rewrites `pin.json` and the pin report (maintainers only). It downloads the tarball (about 53 MB), runs `jarsigner` on every jar and queries Maven Central, which takes several minutes; pass `--cache-dir <dir>` to keep the tarball between runs. Byte Buddy's PGP signature is checked only when its signer's key is in your GnuPG keyring.

Technical work here uses the design and `T` tasks directly, with no Notion Solution or work packet. New work is always a series in `.context/tasks/`, with the next unused `T` number (T001 and T002 are used). Its overview, the unsuffixed `T003.md`, is never executable: it gives the shared context, design links, scope, constraints, the links to every task in explicit work order, their dependencies and the series' overall acceptance criteria. Its executable tasks are numbered from `.01`, even when there is only one: a one-task series is `T003.md` plus `T003.01.md`. Each task links back to the overview and is one bounded step, with its own changes, acceptance criteria and evidence location. A task records the real output of every acceptance item in `.context/tasks/evidence/<task>.md` (`T003.01.md`), committed with the work in one commit whose subject starts `<task>: ` (`T003.01: `); the overview links to its tasks' evidence. T001's and T002's files keep their names and places. Evidence is self-contained: it copies the output it cites, since the test scratch folder's sessions are pruned.
